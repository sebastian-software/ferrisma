# ADR-0020: Kernel crate, runtime ISA dispatch and the `unsafe` boundary

- **Status:** Proposed
- **Date:** 2026-11-05
- **Last reviewed:** 2026-11-05
- **Supersedes:** None
- **Related:** [0006](0006-cpu-first-gpu-capable-execution.md), [0007](0007-correctness-and-performance-evidence.md), [0016](0016-working-color-space-and-transform-boundaries.md), [0018](0018-optional-codec-and-cms-dependencies.md), ADR-0021 (working precision policy, in preparation), ADR-0022 (tiled fused executor, planned), [M2 milestone](../milestones/M2-performance-architecture.md) work package 3, [M1 benchmark protocol](../benchmarks/M1-protocol.md), [fuzzing policy](../fuzzing.md)

## Context

The M1 executor ([`src/quality_execute.rs`](../../src/quality_execute.rs)) is a scalar, `f64`, single-threaded row loop: every output pixel runs through the horizontal taps in `sample_rgba`, a `VecDeque` of cached rows for the vertical taps and `final_rgba` for quantization. It is the oracle that M2 keeps. Work package 3 of the M2 milestone asks for `ferrixel-kernels`: horizontal and vertical resample, transfer LUT apply, pack/unpack and premultiply/unpremultiply as width-agnostic kernels with a scalar reference and NEON, SVE2, AVX2 and AVX-512 variants chosen at run time. Two project rules constrain how that can be built:

- The core crate keeps `#![forbid(unsafe_code)]` ([`src/lib.rs`](../../src/lib.rs), `Cargo.toml` `[lints.rust] unsafe_code = "forbid"`). The M2 acceptance contract repeats it: intrinsics live in a separate, audited crate with a safe API, differential tests and a scalar fallback.
- MSRV is Rust **1.98** on the stable channel (ADR-0018), and a binary built on one machine must be correct and fast on another ("dispatch by runtime detection, never by build flags alone").

The question is therefore not *whether* to use SIMD but where the `unsafe` may live, which stable-Rust mechanism reaches which ISA level, how the chosen level becomes visible in the plan, and how scalar/SIMD equivalence is proven.

### Verified on 2026-11-05 with `rustc 1.98.0 (88d9e12ae 2026-08-18)`

Small probe programs were compiled with the pinned MSRV toolchain on the development machine (Apple M1 Ultra, `aarch64-apple-darwin`) and for `x86_64-unknown-linux-gnu`:

1. **Safe `#[target_feature]` functions and safe intrinsics.** A safe `fn` with `#[target_feature(enable = "avx2")]` may call `_mm256_add_epi16` without `unsafe`; the same holds for `vaddq_u16` under `neon`, `_mm512_add_epi16` under `avx512bw` and `_mm256_cvtepi16_epi8` under `avx512bw,avx512vl`. A same-feature function may call another without `unsafe`. Rust 1.86.0 (2025-04-03) stabilized safe `#[target_feature]` functions, 1.87.0 (2025-05-15) made most `std::arch` intrinsics safe inside a matching feature context, and 1.89.0 (2025-08-07) stabilized the AVX-512 target features and intrinsics.
2. **Two things stay `unsafe`.** Intrinsics that take raw pointers (`_mm256_loadu_si256`, `vld1q_u16`, `vst1q_u16`) remain `unsafe fn`. Calling a `#[target_feature]` function from a function without that feature requires an `unsafe` block, and the compiler says so even when the feature is part of the build baseline: for NEON on `aarch64-apple-darwin` the error reads "the neon target feature being enabled in the build configuration does not remove the requirement to list it in `#[target_feature]`". The dispatch call site is therefore always an `unsafe` block whose justification is the preceding runtime detection.
3. **ISA coverage on stable.** `is_x86_feature_detected!("avx512bw")`, `is_aarch64_feature_detected!("sve2")`, `avxvnni` and `avx512vnni` target features all compile. `#[target_feature(enable = "avx10.1")]` fails with "the target feature `avx10.1` is currently unstable" (E0658). `#[target_feature(enable = "sve2")]` is accepted, and `rustc -O --emit=asm` turned a plain `axpy` loop under that attribute into scalable-vector code (`rdvl` to read the vector length, `fmul`/`fadd` on `z` registers, no NEON `v` registers), but the SVE intrinsics and types (`svint16_t`, `svadd_s16_x`) are behind the unstable `stdarch_aarch64_sve` feature. `is_aarch64_feature_detected!("sme")` is unstable (`stdarch_aarch64_feature_detection`).
4. **`std::simd` is nightly-only.** `#![feature(portable_simd)]` is rejected on stable (E0554); the standard library documents the module as "a nightly-only experimental API" under tracking issue rust-lang/rust#86656.
5. **Compile-time baselines are narrow.** `rustc --print cfg` for `x86_64-unknown-linux-gnu` enables only `fxsr`, `sse` and `sse2`; `-C target-cpu=x86-64-v3` adds `avx`, `avx2`, `fma`, `f16c`, `bmi1`, `bmi2`, `lzcnt`, `movbe`, `popcnt`; `x86-64-v4` adds `avx512f/bw/cd/dq/vl`. `aarch64-unknown-linux-gnu` enables only `neon`; `aarch64-apple-darwin` additionally enables `dotprod`, `fp16`, `fcma`, `rdm`, `sha3` and others. Anything compiled with `-C target-cpu=native` on the dev machine assumes an Apple baseline that a Graviton does not have.
6. **Development machine at run time.** `is_aarch64_feature_detected!` on the M1 Ultra reports `neon`, `dotprod` and `fp16` true and `sve`, `sve2`, `i8mm` false. No SVE2 hardware is available to this project today; every SVE2 statement below is an expectation to be tested on Graviton4 or an `ubuntu-24.04-arm` runner.

Whether it holds or not, it is the wrong property to rely on: the project's rule is about auditability of `unsafe`, and `unsafe` that a proc macro expands into the core crate is invisible to the lint and to reviewers alike.

### Hypotheses (not verified)

- SVE2 code produced by LLVM autovectorization under `#[target_feature(enable = "sve2")]` may or may not beat hand-written NEON intrinsics on Neoverse V2 with 128-bit vectors. Nothing in this project has run on SVE2 hardware.
- AVX-512 with 512-bit vectors is expected to win on Zen 5 and Granite Rapids and to be neutral or worse on older Intel parts with frequency licensing; the level choice therefore stays a planner policy, not a hardware fact.
- GitHub's `ubuntu-24.04-arm` runners are documented by Arm as Cobalt 100 (Neoverse N2) with SVE2; `ubuntu-latest` x86-64 runners expose AVX2 and may or may not expose AVX-512 depending on the backing VM. Both must be read from the runner at run time and printed in the job log.

## Decision

1. **A separate first-party crate, `ferrixel-kernels`.** The repository becomes a Cargo workspace with the existing package at the root and `crates/ferrixel-kernels`. The core keeps `#![forbid(unsafe_code)]` and depends on the kernel crate unconditionally: kernels are the engine, not an optional codec. The kernel crate has `#![deny(unsafe_code)]` at the crate root, `#![deny(unsafe_op_in_unsafe_fn)]`, `clippy::undocumented_unsafe_blocks` and `clippy::multiple_unsafe_ops_per_block` as errors, and exactly three modules carry `#[allow(unsafe_code)]`: `dispatch` (detection proof → call), `mem` (unaligned load/store wrappers over `&[T; N]` and `&mut [T; N]`), and the per-ISA `lanes` implementations. Every other file in the crate is safe Rust; `grep -rn unsafe crates/ferrixel-kernels/src` is the audit list. The split exists for the `unsafe` boundary, not to lower the core MSRV (ADR-0018 rule 5); both crates declare `rust-version = "1.98"`. The kernel crate has no third-party dependencies at first; `safe_unaligned_simd` is the first candidate if `mem` grows beyond a handful of shapes, and `archmage`/`magetypes` the candidate if the lane trait grows into a general vector library.
2. **`std::arch` intrinsics behind a safe API, hand-written dispatch.** The public surface of `ferrixel-kernels` is safe: `IsaLevel` (an enum, see 4), `detect() -> IsaLevel` (cached in a `OnceLock`), and `Kernels::for_level(level) -> Result<Kernels, UnsupportedLevel>`, a table of function pointers to thin safe wrappers. Each wrapper holds one `unsafe` block that calls the `#[target_feature]` variant and whose `SAFETY` comment names the invariant: `for_level` only succeeds when `level <= detect()`. This is the `zune-jpeg`/`rav1e` pattern. The `multiversion` crate is not adopted: five levels on two architectures do not justify a proc-macro dependency, and its SVE targets would only wrap the autovectorized path that the project can write by hand.
3. **One kernel body per kernel, width-agnostic.** Each kernel is written once against an internal `Lanes` trait: an associated `LANES` constant and the vector types and operations the five kernels need (u8↔i16↔i32 widening and narrowing, `i16` multiply-add into `i32`, `f32` multiply-add, interleave/deinterleave, saturating pack). The implementations are `Scalar` (`LANES = 1`, the reference), `Neon`, `Avx2` and `Avx512`; each kernel body is monomorphized inside a `#[target_feature]` entry per level. Kernels take rows or tiles as slices plus coefficient tables that the core precomputes (taps and fixed-point weights per ADR-0021); they allocate nothing, require no buffer padding, and finish the tail with the scalar body. Buffers padded to the lane width are an optimization the planner may offer later, not a requirement. SVE's scalable width cannot be a `const LANES`; an SVE2 variant is therefore the scalar body compiled under `#[target_feature(enable = "sve2")]` and is kept only if it measures better than the NEON variant on SVE2 hardware.
4. **ISA levels and floors.** `IsaLevel::{Scalar, Neon, Sve2, Avx2, Avx512}` in that order. `Avx2` requires `avx2` and `fma` detected; `Avx512` requires `avx512f`, `avx512bw`, `avx512cd`, `avx512dq` and `avx512vl` (the x86-64-v4 set used by `rav1e` and `multiversion`). NEON and AVX2 are the floors from the M2 milestone; an x86-64 machine without AVX2 runs `Scalar` and the report says so. No SSE4.1 variant is planned. AVX10 and APX are not representable on stable Rust 1.98 and are recorded as a review trigger. The default choice is the highest implemented level; the planner may pin a lower level by a measured policy (ADR-0007), never by a build flag.
5. **The chosen level is part of the plan and the report.** The execution plan records, per kernel family, the detected machine level, the chosen level and the reason (`Detected`, `Policy`, `Forced`, or `Fallback` when a variant is not implemented at that level). `ProcessingReport` exposes the same, so a benchmark line can state "AVX2, 16-bit fixed point, 64-row bands" as the milestone requires. Processing options gain a `kernel_level_ceiling`, a safe setting that can only lower the chosen level; it is how differential tests, benchmarks and bug reports pin a variant, in the spirit of libvips' `VIPS_VECTOR` and `fast_image_resize`'s `set_cpu_extensions` but without `unsafe`.
6. **Kernels that exist first**, each with scalar reference plus NEON and AVX2 variants before any AVX-512 or SVE2 work:

   | Kernel | Input → output | Working type | Equivalence class |
   | --- | --- | --- | --- |
   | Horizontal resample | one source row (u8, u16 or f32, 1–4 channels) + tap table → one intermediate row | `i16` taps/`i32` accumulators or `f32` per ADR-0021 | integer: bit-exact; float: ULP bound |
   | Vertical resample | n intermediate rows + tap weights → one output row | same as horizontal | same |
   | Transfer LUT apply | u8 or u16 encoded samples → linear `u16` or `f32` through a verified table | table lookup; may stay scalar-unrolled where SIMD gathers lose (NEON has no gather, AVX2 gather is slow), decided by measurement | bit-exact (table) |
   | Pack / unpack | interleaved RGB8/RGBA8 ↔ planar or lane-ordered `i16`/`f32`; 3→4 channel expansion | integer permutes | bit-exact |
   | Premultiply / unpremultiply | straight ↔ premultiplied alpha in linear light | `f32`, or fixed point only where ADR-0021 proves the bound | float: ULP bound; integer: bit-exact |

   The fused per-tile chain (ADR-0022) composes these; fusion does not change the equivalence classes.
7. **Equivalence contract and tests.** For every kernel and every level available on the test host, the differential test compares against the `Scalar` implementation of the same body: integer paths must be bit-exact; `f32` paths must agree within **4 ULP** per sample, with the reference using `f32::mul_add` so that FMA in the NEON (`vfmaq_f32`) and AVX2 (`_mm256_fmadd_ps`) variants is not itself a difference, and with identical tap order. The 4 ULP figure is the initial contract; the first differential run either confirms it or the amendment log records the measured bound and why. Agreement with the M1 `f64` oracle and the error budget of 16-bit fixed point are ADR-0021's contract, not this ADR's. Inputs cover random data, every width from 1 to 3×lanes+1, odd strides, extreme values (0, 255, 65535, NaN, ±inf, subnormals), Lanczos tap sets with negative lobes and zero crossings, weights that do not sum to one, and alpha 0 and 1. A `cargo fuzz` target per kernel family compares levels on fuzzer-generated rows. A level that the host cannot run is reported as **untested** in the test output, never silently skipped; CI jobs print `detect()` and the levels exercised.
8. **MSRV and CI matrix.** The MSRV job builds the workspace with all features on 1.98.0. Clippy runs with `-D warnings` on both crates. Jobs: `ubuntu-latest` (x86-64, AVX2 expected, AVX-512 if present), `ubuntu-24.04-arm` (NEON, SVE2 expected), `macos-15` (Apple Silicon, NEON). AVX-512 and SVE2 coverage that these runners do not provide is a prerequisite for work package 6 (self-hosted or cloud runners), and until then those variants are labeled dev-machine-untested in `docs/benchmarks/`. Miri on the scalar body and the `mem` wrappers is an expectation to try, not a gate, because Miri's intrinsic coverage is partial.
9. **Rejected for this milestone:** `std::simd` (nightly), `-C target-cpu`/`target-feature` build flags as the mechanism (correct only on the build machine), compile-time wrapper crates (`wide`, `safe_arch`), hand-written assembly, and a separate kernel copy per ISA in the style of `fast_image_resize`.

## Consequences

+ The core stays `#![forbid(unsafe_code)]` with zero third-party dependencies by default; all `unsafe` in the engine is in three named modules of one crate and is enumerable.
+ One kernel body per kernel means one place to review the arithmetic and one differential test per kernel instead of one per ISA copy.
+ The plan and report name the ISA level and the reason, so a benchmark number can never hide which path ran.
+ Every variant is compiled into every build for its architecture; adding a level is a `Lanes` impl and a match arm, not a new kernel.
- Writing the `Lanes` trait and its three implementations is up-front work that a wrapper crate would have provided; the trade is a smaller, audited surface against reuse.
- Binaries carry all variants for their architecture (code size), and compile time grows with each level.
- SVE2 is reachable only through autovectorization on stable Rust, so its quality depends on LLVM, and it cannot be validated in this repository until SVE2 hardware or a runner is available.
- AVX10 and APX cannot be targeted on the pinned toolchain; the x86 ceiling is AVX-512 until Rust stabilizes them.
- The workspace conversion touches `Cargo.toml`, the lockfile, CI and the license inventory script; it is a prerequisite step of work package 3.

## Alternatives considered

- **(a) Separate kernel crate with `std::arch` intrinsics and runtime detection: chosen**, with hand-written dispatch rather than `multiversion`. `multiversion` 0.9.2 would clone each kernel per target, including `aarch64+sve2`, and resolve through an atomic function pointer; it is a sound mechanism but adds a proc-macro dependency for something that is five match arms, and it cannot change the fact that SVE intrinsics are unavailable.
- **(b) Safe portable-SIMD wrapper crates on stable.** `wide`/`safe_arch` are compile-time only and cannot reach AVX2 in a baseline x86-64 binary. `pulp` 0.22.3 (no declared MSRV, 1,639 `unsafe` lines), `macerator` 0.5.2 (MSRV 1.94), `fearless_simd` 1.2.0 and `archmage`/`magetypes` 0.9.30 all do runtime dispatch and reach NEON, AVX2 and AVX-512, which is the same ceiling as intrinsics; none reaches SVE2 or AVX10. They would replace the `Lanes` trait with a larger, externally versioned surface whose `unsafe` the project does not audit, and `archmage` is pre-1.0 with announced signature changes. Deferred, with `archmage` + `safe_unaligned_simd` as the first candidate if the in-house trait grows beyond what the five kernels need.
- **(c) `std::simd`.** Rejected: nightly-only (verified), which conflicts with MSRV 1.98 stable and with the sister ports' adoption gate "stable toolchain" in ADR-0018.
- **(d) Autovectorization with `-C target-cpu`.** Rejected as the mechanism: the cfg baseline for `x86_64-unknown-linux-gnu` is SSE2, and a binary built with `target-cpu=x86-64-v3` faults on a machine without AVX2 while one built for the baseline never uses it. Autovectorization is kept where it belongs: inside each `#[target_feature]` entry, LLVM may vectorize the scalar tail and, for SVE2, the whole body.
- **One hand-written kernel copy per ISA (`fast_image_resize` style).** Rejected: four copies of five kernels multiply the review and test surface, and the per-variant checksum testing it leads to does not state cross-variant agreement.
- **SSE4.1 variant for pre-AVX2 x86-64.** Deferred: the M2 target matrix has AVX2 as the floor; add it only if a measured workload runs on such hardware.
- **Keeping the kernels inside the core crate with `#[allow(unsafe_code)]` modules.** Rejected: `forbid` cannot be overridden, and the crate boundary is what makes the audit list, the fuzz targets and the dependency story visible from the outside.
- **Inline assembly or a vendored Highway/FFI port.** Rejected per the M2 non-goals; FFI would reintroduce a native toolchain into the core build.

## Validation

- **Prototype before expansion.** Implement the horizontal resample for RGBA8 with `i16` taps in `Scalar`, `Neon` and `Avx2` through the `Lanes` trait; measure against the M1 executor and against `fast_image_resize` 6.1.0 on the dev machine and on an x86-64 runner using the work-package-0 harness. If the width-agnostic body is more than ~20 % slower than a hand-written intrinsic version of the same kernel on either ISA, this ADR is amended toward per-ISA bodies for that kernel.
- **Differential tests** as in decision 7 for every kernel, run on every CI job, with the level list printed. The first run fixes or amends the 4 ULP bound.
- **`unsafe` budget.** The number of `unsafe` blocks in `crates/ferrixel-kernels/src` is recorded in the crate README with each release of the crate; growth without an amendment here is a review finding.
- **Build-portability check.** A release binary built on the dev machine must run the full test corpus on an x86-64 runner without AVX-512 and on an Arm runner, each reporting its own detected level.
- **Falsifiers.** A kernel whose integer variants cannot be made bit-exact across levels (for example because of saturation order), a `Lanes` trait that needs more than a few dozen operations, or a measured SVE2 regression against NEON would each force an amendment.

Existing evidence: the probes and sources cited in Context; no Ferrixel kernel has been written or measured yet.
