# ADR-0022: Parallel row pipeline and an engine for many images

- **Status:** Accepted
- **Date:** 2026-11-06
- **Last reviewed:** 2026-11-27
- **Supersedes:** None
- **Related:** [0003](0003-demand-driven-regions.md), [0004](0004-buffer-ownership-and-budget.md), [0006](0006-cpu-first-gpu-capable-execution.md), [0020](0020-kernel-crate-and-isa-dispatch.md), [0021](0021-working-precision-policy.md), [M2 milestone](../milestones/M2-performance-architecture.md) work package 4, [M2 baseline](../benchmarks/M2-baseline.md)

## Context

After work packages 1–3 the transform stage runs on one core. On the Apple M1 Ultra (20 cores) a 48 Mpx JPEG to 1600-wide AVIF spends 170 ms decoding, 191 ms transforming and 140 ms encoding with all encoder cores; CPU/wall is 3.8. The transform is the largest stage that does not yet use the machine. Its work splits into independent pieces (measured on 48 Mpx, `sample`): per **source row**, linearization (about 24 %) and the horizontal pass (about 57 %); per **output row**, the vertical pass (about 10 %) and quantization (about 9 %).

Verified constraints:

- Decoders deliver rows **sequentially** through a borrowing callback (`DecodeSource::read_region`, ADR-0012). JPEG and AVIF adapters decode the full frame first and then stream rows; JPEG XL renders a region. The callback cannot hand a borrowed row to another thread.
- The AVIF sink requires rows **in order** (`AvifSink::write_row`).
- The core crate forbids `unsafe` and has one unconditional dependency, the first-party kernel crate. `rayon` is already in the lockfile through `rav1e`, but not a dependency of the core.
- Every horizontal row and every vertical row is a pure function of its inputs and the plan. The `f32` kernels are deterministic per level; the order of taps within a row is fixed.
- `MemoryBudget` is a shared atomic counter, already safe across threads (ADR-0004).

The M2 plan sketched *bands with filter halos*: split the output into horizontal bands, give each band to a worker that decodes, filters and emits its rows. That shape fits a decoder with random row access; ours stream once from the top.

## Decision

1. **A batched row pipeline with driver-local buffer pools, not bands.** The thread that drives the decoder copies each needed source row (found via an O(1) advancing cursor over `plan.needed`) into a pooled, budgeted buffer, pairs it with a pre-allocated horizontal output buffer, and submits batched *horizontal strips* (up to 8 rows per job, scaled down on small images). Workers apply any deferred source conversion (ADR-0023), linearize each row, and run the horizontal kernel into the driver-supplied horizontal row, shared read-only (`Arc`). As soon as a strip of output rows has all of its horizontal inputs, the driver pre-allocates its output buffers and submits a *vertical strip* (up to 8 output rows, scaled down by the vertical downscale ratio so steep downscales do not retain extra horizontal rows, sharing one deduplicated slice of horizontal `Row` references), prioritized ahead of horizontal strips in the single-mutex bounded job deque so horizontal rows and output buffers recycle promptly. Workers run the vertical kernel, quantize into the driver-supplied output buffers, and reclaim uniquely-owned horizontal buffers via `Arc::try_unwrap` back to the driver's pool. The driver reorders finished strips, hands rows to the sink strictly in order, and returns emitted output buffers to its pool. Worker scratch is allocated up front on the calling thread before spawning, so worker hot loops never allocate from `MemoryBudget`. No row is computed twice and no halo is duplicated.
2. **Bit-identical to the sequential executor.** Each job runs exactly the kernels and operation order of the sequential path; only the thread differs. A test compares both executors byte for byte across geometries, crops, alpha, depths, and levels for 1, 2, 3, 8, 12, 16, and 20 threads.
3. **Bounded memory, paced backpressure, and documented parallel peak contract.** Jobs travel through a single-mutex bounded deque with waiter-aware signaling (`Condvar` notified only when a worker is parked). In-flight horizontal strips (`threads + 2`), total horizontal rows (retained, in-flight, pending, deferred, and incoming) past `next_vertical`'s required ranks (`plan.capacity + 2 * (threads + 2) * h_batch`, checked in O(1) via `RowPlan::ready` so a stalled early strip cannot let the decoder advance unboundedly ahead of vertical work and deferred rows cannot bypass the cap), and in-flight vertical output rows (`(threads + 2) * v_batch`, counting each incoming strip before submission so `next_vertical - next_emit <= max_vertical_in_flight` never overshoots even after decoder EOF) are all explicitly capped: when any window is full, the driver blocks on `done.recv()`, absorbs completions, recycles buffers, and emits finished rows inside `Driver::advance` before admitting more work (preventing unbounded `OutputBuffer` accumulation on upscales, issue #210). Horizontal rows are dropped as soon as no remaining output row references them (`future_min`). Every live and pooled buffer remains charged to the shared cache-line-padded `MemoryBudget` (`#[repr(align(128))]`); because all per-row allocations live on the driver and `OrientedSource::emit_parallel` pre-allocates and reuses `1..=min(threads + 1, blocks)` gather blocks for transposing orientations before row callbacks begin — allocating block 0 mandatorily and additional optional blocks only while `budget.available() >= block_bytes + downstream_headroom` (where `DecodeSource::set_downstream_headroom` carries the exact minimum downstream working set `1 source row + plan.capacity horizontal rows + 1 output row`) — gather workers never allocate from `MemoryBudget` once callbacks start, tight budgets can gracefully use fewer gather blocks, and budget admission stays strictly monotonic. Budget pressure clears idle pools, drains completions, flushes ready partial vertical strips (shrinking a strip if needed), lazily reserves a dedicated `reserved_output` buffer on the first delivered needed row (so it does not overlap with full-frame decode scratch, keeping `reserved_output` intact for deferrable horizontal rows during `read_region` and releasing it only as a last resort after `read_region` or on non-deferrable allocations when no work is in flight and no vertical row is ready yet), and defers horizontal `Row` allocation past `DecodeSource::read_region` if decoder-held buffers leave no room during the callback (allocating them right after `read_region` drops those buffers while propagating any sink error immediately). With one transform thread, `ProcessingReport::peak_managed_bytes` is deterministic; with multiple transform threads it is strictly bounded by the queue, strip, row-retention, and pool caps, while the exact observed high-water mark can still vary slightly with scheduling (which strip recycles first). Output bytes are unaffected.
4. **Errors and cancellation stop everything.** A worker error, a decoder error or a sink error (including `Cancelled`) closes the queue via an RAII guard, clears unstarted queued jobs, wakes all waiting workers, and `std::thread::scope` joins them before the call returns. No thread outlives the call (`std::thread::scope`).
5. **Standard library only.** `std::thread::scope`, `std::sync::{Condvar, Mutex, mpsc}`, and `Arc`. No `rayon` in the core: the pipeline needs prioritized strip dispatch, ordered emission, and bounded backpressure more than work stealing, and adding a scheduler crate is a separate decision.
6. **Threads are an option, defaulting to all cores.** `TransformOptions::transform_threads` (the typed `Threads`: automatic = all available cores, 1 = the sequential path). Because the output is bit-identical, the default does not trade determinism for speed. Small images (fewer than 64 needed source rows) take the sequential path. The report names the threads used.
7. **An `Engine` for many images (second step) — long-lived worker pool rejected with measurements.** An `Engine` holds its thread count and offers a batch call that schedules *images* across scoped worker threads with one transform and one encoder thread each, which the encoder experiment showed to be the most byte-efficient setting. A long-lived worker pool across calls was evaluated and **rejected** (2026-11-27, issue #59): spawning and joining 20 scoped threads on the M1 Ultra costs `0.28–0.32 ms/call` (`279–319 µs/call` over 100 iterations) — ~3 % of a 24 Mpx transform, ~1.6 % of a 48 Mpx transform, and `0.003 ms/image` amortized across a 100-image `Engine::transcode_batch`. Under `#![forbid(unsafe_code)]`, a long-lived pool cannot accept borrowed `&RowPlan`, `&[BatchItem<'_>]`, or `&dyn EncoderBackend` references without `unsafe` lifetime erasure or copying every compressed input into owned allocations (which would exceed `0.3 ms` on real photos), while scoped threads guarantee zero lingering idle threads and deterministic teardown. Its API is specified in this ADR's amendment log.

## Consequences

+ The transform stage scales past 8 cores (7.6×–9.7× at 20 threads and up to 9.9× at 12 threads across 24–48 Mpx workloads on the 20-core M1 Ultra) without changing a single output byte.
+ The decoder contract, the sink contract and the budget semantics stay as they are.
+ Memory is bounded by the plan's row window plus the capped retained-and-in-flight horizontal row window (`plan.capacity + 2 * (threads + 2) * h_batch` past `next_vertical`'s required ranks) and the paced in-flight vertical strip window (`(threads + 2) * v_batch`), preventing both stalled-strip horizontal growth and unbounded `OutputBuffer` pileup on upscales (#210).
+ Cache-line-padded `MemoryBudget` atomics (`#[repr(align(128))]`), driver-local buffer pools, `allocate_copied` (no redundant zero-fill), and vectorized `HiddenColorProbe` eliminate steady-state allocator, zero-fill, and false-sharing bottlenecks on the serial driver thread.
- One extra copy per needed source row (the decoder's borrowed row into a pooled buffer): about 18 KB per 6000-pixel RGB row, small against the horizontal work on it.
- `peak_managed_bytes` remains scheduling-dependent within its tight bounded window when `transform_threads > 1` (documented on `ProcessingReport::peak_managed_bytes`).
- The driver thread is serial: for decoders that stream slowly, the decoder becomes the limit, which is the decode-side work of package 5.
- Thread creation per call (`~0.28–0.32 ms` for 20 threads on M1 Ultra) stays outside `MemoryBudget`; `Engine::transcode_batch` amortizes it over whole batches.

## Alternatives considered

- **Bands with halos (the M2 sketch).** Rejected for now: it needs random row access or a full decoded frame shared across workers, duplicates halo rows at every band edge (about 23 rows per edge at a 3.75× Lanczos3 downscale), and makes in-order emission a cross-band handoff. Reconsider for decoders with region access (JPEG XL, decode-side scaling in package 5).
- **`rayon`.** A fine work-stealing pool, and already compiled for `rav1e`. Not needed for a pipeline of independent row jobs with ordered output; not used; deferred until the `Engine` needs nested parallelism.
- **Parallelize only the horizontal pass.** Simpler, but leaves the vertical pass and quantization (about 19 %) serial on the driver.
- **Split the decoded frame into strips for JPEG and AVIF**, since those adapters hold the full frame anyway. Faster for those two, but it bypasses the decoder contract and does not apply to JPEG XL; the row pipeline covers all three.

## Validation

- Byte-identical output between the sequential and the parallel executor for every test input of the ADR-0021 differential suite, at every available kernel level and for 1, 2, 3 and 8 threads.
- Cancellation from the sink and budget exhaustion release all memory (`live == 0`) and return the same errors as the sequential path.
- Scaling of the transform stage from 1 to all cores on the dev machine and on the CI runners, recorded in the M2 baseline. The decision is falsified if the transform does not get at least 4× faster on 20 cores for the 24 Mpx case, or if peak memory grows by more than the queue depth times a row.

## Review when

Decode-side scaling (package 5) gives decoders region access; the `Engine` needs nested or prioritized parallelism; the allocator shows up in profiles; a GPU backend (ADR-0024) needs a different job granularity.
