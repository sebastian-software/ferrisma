# JPEG XL encode against the original in three columns, x86-64, 2026-11-20

**Question.** The encoder selects its AVX2 path by default on x86-64
(`ENCODER_SELECTS_SIMD`, port
[ADR 0004](../../codecs/libjxl-rs/docs/adr/0004-simd-paths.md), "Encoder
selection"). Condition (e) of that ADR asks for the encoder's AVX2 speed on
x86-64 hardware. How does the port's encode compare with libjxl's on hosted
x86-64 runners?

**Answer, for these runners and these inputs.** Single-threaded, the port's
default (AVX2) encode is in the range of libjxl's AVX2 build (column (b)) for
both the lossy and the lossless profile, and faster than libjxl's scalar
build on the lossy profile (column (a)). With all threads (column (c)) the
port is slower, because its encoder runs one thread. The lossy encode is
byte-identical with libjxl's AVX2 build on both runners. The ratios are in
the table; this record states no other figure.

These are same-runner ratios on shared hosted machines. There is no
performance gate for v1.0 (ADR-0041, decision D3); this record is evidence,
not a release claim.

## Notes on the columns

- Every column runs the port's default selection, the AVX2 path. Column (a)
  is the original's scalar build (`HWY_COMPILE_ONLY_SCALAR`); the port's
  scalar path is gated byte for byte against it elsewhere (the scalar gate),
  so "differs" in column (a) of the lossy row is the expected difference
  between the two paths, not a defect.
- Lossless "differs, header": the benchmark's cjxl call writes a slightly
  different file than the engine's `LosslessThunderConfig` call sequence
  (`jxl-checks.json` records it as "not a gate"; it was the same in the
  previous run of this benchmark, 43773306968). The lossless profile's byte
  identity with the original's AVX2 build is shown by
  `tests/simd_encoder_public.rs` (532 encodes per target).
- (c) uses one libjxl worker per CPU; the port's encoder is serial (#106).
