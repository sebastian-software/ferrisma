# JPEG XL decode against the original in three columns, AArch64, 2026-11-14

**Question.** Since the [records of 2026-11-12/13](v1.0-three-column-2026-11-13.md)
the port's whole decode path was translated to SIMD (port
[ADR 0004](../../codecs/libjxl-rs/docs/adr/0004-simd-paths.md)) and the decoder
selects NEON by default on AArch64 (`47a44e0c`). Is the port's decode now in
the same range as libjxl's, or still many times slower?

**Answer, for this machine and these eight inputs.** Single-threaded, the
port is now **1.3–2.9× the time of libjxl's NEON build** (column (b)):
2.2–2.3× on the two cjxl-made lossy VarDCT photographs (12 and 24 MP),
2.8–2.9× on the three lossy conformance files, and 1.3–1.4× on the
lossless (modular) files. Against libjxl's scalar build, scalar path against
scalar path (column (a)), it is 1.3–3.3×. With all ten threads (column (c))
the port is 3.2–15× slower, because the port's decoder does not run its
tasks in parallel (see "Column (c)"). Every timed output was **bit-identical**
with the original's output of the same build kind, on every input, in every
column.

These are same-machine ratios from one Apple M1 Pro, AArch64 only, on an idle
but not isolated desktop. There is no performance gate for v1.0 (ADR-0041,
decision D3); this record is evidence, not a release claim.

## Reading the numbers

- **Lossy VarDCT, one thread: 2.2–2.9× libjxl's NEON build.** The
  2026-11-13 CI record had 3.6–4.1× on Linux ARM64 and 3.7× on macOS ARM64
  for the same kind of input, through djxl and the `ferrisma-jxl-decoder`
  bridge, before the decoder selected NEON (those runs are context only:
  other hosts, other harness). The two cjxl photographs are closest to the
  original (2.2–2.3×); the conformance files, which exercise more of the
  format (LF frame, HF passes, Squeeze), are at 2.8–2.9×.
- **Scalar against scalar is not closed.** Column (a) is 1.5–1.7× on the
  photographs and 2.4–3.3× on the conformance files. On `progressive` and
  `grayscale_public_university` the port's scalar path is further from the
  original's scalar build than its NEON path is from the original's NEON
  build, so the remaining loss there is translation overhead, not SIMD.
- **Lossless modular: 1.3–1.4× in (a) and (b) alike.** libjxl's NEON build
  is no faster than its scalar build here (1,549 against 1,575 ms at 12 MP),
  so this path is entropy decoding and prediction, where SIMD does not help
  either side.
- **The harness is representative of djxl.** The C harness and djxl on the
  same NEON build differ by 0–5 % on every input (djxl additionally converts
  to big-endian float and runs DecodeImageJXL's bookkeeping), so the ratios
  do not depend on the harness.

## Column (c): what is and is not comparable

Both sides are given the same runner (the original's `JxlThreadParallelRunner`
and its translation, 10 workers, the default `hardware_concurrency` on this
host) through `JxlDecoderSetParallelRunner`. libjxl decodes 2.4–6.3× faster
with it than with 0 workers. The port's time does not change (photo24-e7d1: 1,083
ms with 0 workers, 1,084 ms with 10): its decoder calls the runner, but every
RunOnPool call in the decoder goes through `run_on_pool_exclusive`, which
serializes all task bodies behind one lock
(`codecs/libjxl-rs/src/jxl/base/data_parallel.rs`; port ADR 0003, the
`Rc`/`RefCell` owners the task bodies borrow). Column (c) therefore measures
a parallel original against a serial port. The column is reported as
measured, since it is what a caller gets from the same API call, but it is
not a measure of the port's threading code: the port has no parallel decode
to compare. The outputs with 10 workers are identical to those with 0
workers on both sides.

## Where the port's NEON decode time goes (photo24-e7d1)

`/usr/bin/sample` at a 1 ms interval, one thread (0 workers), the whole
timed decode repeated in one process (`JXL_BENCH_REPEAT`: 16 decodes of the
original, 8 of the port), the builds and input of column (b) (harnesses
rebuilt with that switch).
Self time per decode, grouped by stage; sampling under-counts both sides by
a similar factor (351 and 855 sampled ms per decode against 477 and 1,083 ms
timed; the ratio 2.4 matches the timed 2.27). Shares are indicative.
Release builds without line tables, so inlined helpers count to their
caller.

| Stage (self time) | libjxl NEON, ms/decode | Port NEON, ms/decode | Difference |
| --- | ---: | ---: | ---: |
| Entropy decoding (ANS, AC tokens, `LoadBlock`, bit reader) | 152 | 160 | +8 |
| Render-pipeline row handling (`simd_rows::read`, `prepare_io_rows`, `RenderRect`/`process_buffers`, borders) | 9 | 149 | +140 |
| `memmove`/`memset` | 25 | 96 | +71 |
| `malloc`/`free` (with the allocator's `mach_absolute_time`) | <1 | 85 | +85 |
| EPF | 29 | 111 | +82 |
| Write to output | 6 | 59 | +53 |
| Dequantization and IDCT | 64 | 91 | +27 |
| Gaborish, FromLinear, XYB | 59 | 67 | +8 |
| Modular (DC and AC metadata) | 3 | 22 | +19 |

The three largest differences:

1. **Copying every input row of every SIMD render stage into a new `Vec`.**
   `render_pipeline::simd_rows::read` (EPF, Gaborish, XYB, FromLinear call
   it for each row span they read) allocates and fills a fresh vector per
   call, and falls back to a per-sample bounds-checked loop when the
   whole-vector span reaches outside the row slice (the left border, which
   the original reads from row padding). The original passes row pointers.
   Its self time (about 100 ms per decode) plus the `memmove` (38 ms) and
   allocator time (27 ms) it causes are about 165 ms per decode; the
   stages' own further allocations add about 50 ms. This is most of the
   "row handling", `memmove` and `malloc` rows above, about 0.25 s of the
   0.6 s gap.
2. **The EPF stage itself**: 111 against 29 ms per decode, excluding the
   copies above (`EpfStageSimd::process_row` and its `EpfRow` NEON kernel).
3. **The output stage**: `WriteToOutputStage::output_buffers` 59 ms plus 23
   ms `memmove`, against 6 plus 15 ms in the original
   (`WriteToOutputStage::OutputBuffers` / `ProcessRow`).

Entropy decoding, the largest cost of the original (43 % of its time), is at
parity (160 against 152 ms), and Gaborish, FromLinear and XYB together are
within 15 % (FromLinear alone 27 against 22 ms). Nothing was optimized in this work.

## Method

- **Source.** `origin/main` at `7152fb41`; library code unchanged. Branch
  `v1/jxl-bench` adds only measurement tooling:
  [`scripts/bench/ci-perf/jxl_decode_bench/`](../../scripts/bench/ci-perf/jxl_decode_bench)
  (a C harness, `jxl_decode_bench.c`, and its Rust counterpart, `src/main.rs`,
  in a separate Cargo workspace),
  [`jxl_decode_three_column.sh`](../../scripts/bench/ci-perf/jxl_decode_three_column.sh)
  (builds the harnesses, records equivalence, runs the interleaved plans with
  `run_interleaved.py`) and
  [`jxl_decode_table.py`](../../scripts/bench/ci-perf/jxl_decode_table.py).
  The `JXL_BENCH_REPEAT` switch used for the profile was added to both
  harnesses after the timed run; it defaults to one decode, which is the
  timed code path unchanged.
- **Original.** libjxl `a16d32d0ac113f5e54125e49bb571281c5d0b704` (the port's
  pinned submodule), built by
  [`codec_jxl.sh`](../../scripts/bench/ci-perf/codec_jxl.sh) with `OPS=none`
  (builds and reference inputs only), Apple Clang 21.0.0 (clang-2100.4.1.1),
  CMake 4.5.0, Ninja, static libraries:
  - **scalar reference build, column (a):** `-DHWY_COMPILE_ONLY_SCALAR=1`
    in C and C++ flags, upstream's own `-fno-slp-vectorize -fno-vectorize`
    (the differential-oracle configuration); `cjxl --version` reports
    `[_SCALAR_]`.
  - **NEON release build, columns (b), (c):** CMake Release, Highway dynamic
    dispatch with `-DJPEGXL_ENABLE_HWY_{AVX3,AVX3_DL,AVX3_ZEN4,AVX3_SPR,SVE,SVE2,SVE_256,SVE2_128,NEON_BF16}=OFF`
    (ADR-0041 section 4: NEON_BF16 is Highway's target with DotProd, and SVE
    targets are off); `cjxl --version` reports `[_NEON_]`. The CPU offers
    `asimddp` (DotProd), which this build does not use; it has no SVE, I8MM
    or BF16 (`build/cpu-features.json`). No `-march`/`-mcpu` flags.
- **Port.** `libjxl-rs` built by the harness's own workspace with the
  repository's release profile (`panic = "unwind"`, opt-level 3, no LTO),
  toolchain `nightly-2026-09-07` (rustc 1.100.0-nightly `5a2be9f5f`), no
  `RUSTFLAGS`, default features (no `cpp-oracle`).
  - column (a): `hwy::set_decoder_simd_for_test(Some(false))` before the
    decoder is created (the switch the port's scalar-reference tests use);
  - columns (b), (c): the default selection; the harness prints
    `path=NEON` (`hwy::decoder_default_target()`).
  - **Verified per run:** the harness prints `simd_selections`, the number of
    times the decoder's dispatch selected a SIMD target on the calling thread
    (`hwy::simd_selections_on_this_thread`). With 0 workers every task runs
    on that thread; it is 0 for every scalar sample and 35–289,900 per decode
    for every NEON one-thread sample (in the `stdout` of each sample in
    `timing/`). With 10 workers the count on the calling thread drops (for
    example 48 against 289,900 on photo24-d0e7): the tasks run on the
    runner's worker threads, one at a time.
- **Entry points.** Both harnesses make the same public-API calls: read the
  file; then, timed, `JxlThreadParallelRunnerCreate(workers)`,
  `JxlDecoderCreate`, `JxlDecoderSetParallelRunner`, subscribe
  `BASIC_INFO | COLOR_ENCODING | FULL_IMAGE`, set and close the input,
  process until `JXL_DEC_SUCCESS`, allocating the zeroed output buffer
  (`calloc` / `vec![0f32; n]`) at `NEED_IMAGE_OUT_BUFFER` and setting it with
  `JxlDecoderSetImageOutBuffer` (format: color channels plus alpha if
  present, `JXL_TYPE_FLOAT`, native endian, no alignment), destroy decoder
  and runner. No file is written in the timed region. Workers: 0 for one
  thread (every task on the calling thread, as `djxl --num_threads=0`), 10
  for column (c). djxl (`--disable_output --num_threads=0`, its MP/s line
  turned into milliseconds by the wrapper of `codec_jxl.sh`) runs as a
  context candidate.
- **Equivalence.** Before the timed run, each of the six harness candidates
  decoded each input once more and wrote its F32 output after the timer;
  `timing/jxl-decode-equivalence.json` holds the SHA-256 per input and
  candidate. Port and original are compared within a column: scalar port
  against the scalar build, NEON port against the NEON build, both at 0 and
  at 10 workers. All 24 comparisons are identical; 10 workers give the same
  output as 0 on both sides.
- **Inputs.**
  - `photo12` and `photo24`: the masters of
    [`make_masters.sh`](../../scripts/bench/ci-perf/make_masters.sh)
    (`dog_exif_extended_xmp_icc.jpg` from the libavif tree, and the
    `mountain` photograph fetched from Wikimedia Commons and checked against
    its pinned SHA-256), decoded with `djpeg` built from the repository's
    pinned libjpeg-turbo submodule (`7b499378`; no system djpeg exists on
    this host). `codec_jxl.sh` encoded them with this host's NEON cjxl:
    `-e 7 -d 1` (VarDCT) and `-e 7 -d 0` (lossless modular). The VarDCT
    files are not byte-identical with the CI record's (the SIMD encoder's
    output depends on the target).
  - Conformance: the libjxl conformance repository's `testcases/<name>/input.jxl`
    for `bike`, `progressive`, `grayscale_public_university` and
    `lossless_pfm` (the corpus verified on 2026-11-13). File sizes and
    SHA-256 are in `timing/jxl-decode-equivalence.json`.
- **Timing.** `run_interleaved.py`: one plan per input with the seven
  candidates, a fresh process per sample, order forward on even and reversed
  on odd repetitions, one warm-up repetition, 9 timed. Tables use the median
  of the harness's own timer, with min–max; process wall time, max RSS and
  the 1-minute load average before and after each sample are in the JSON.
- **Commands.**

  ```sh
  git submodule update --init codecs/libjpeg-turbo-rs/upstream/libjpeg-turbo
  # djpeg from that submodule (CMake Release, static) placed on PATH, then
  INPUTS=target/ci-perf/inputs bash scripts/bench/ci-perf/make_masters.sh
  INPUTS=target/ci-perf/inputs WORK=target/ci-perf/jxl-work OUT=target/ci-perf/jxl-out \
    JOBS=8 OPS=none bash scripts/bench/ci-perf/codec_jxl.sh
  WORK=target/ci-perf/jxl-work OUT=target/ci-perf/jxl-decode-out CONFORMANCE=<conformance checkout> \
    CASES="bike progressive grayscale_public_university lossless_pfm" REPS=9 WARMUPS=1 \
    bash scripts/bench/ci-perf/jxl_decode_three_column.sh
  python3 -I scripts/bench/ci-perf/jxl_decode_table.py target/ci-perf/jxl-decode-out
  ```

## Host

- Apple M1 Pro (`MacBookPro18,1`), 8 performance and 2 efficiency cores, 10
  threads, 32 GB, macOS 27.2.1 (Darwin 27.2.0), AArch64 native.
- Load average (1 min): 3.17 before (08:22 UTC), 4.50 after (08:33 UTC);
  2.4–5.1 across the samples. The other agents had stopped; the desktop's
  own background work did not: Time Machine (`backupd`, up to 120 % CPU
  shortly before the run, about 20 % during it) and Backblaze (`bztransmit`
  about 100 % at the end), recorded in `timing/host-*.log`.

## Limits

- One machine, AArch64 only, one OS. No x86-64 numbers; x86-64 selects the
  scalar decoder path by default (port ADR 0004) and needs its own run.
- Eight inputs: two photographs in two encodings each, made by cjxl at one
  setting (`-e 7 -d 1` and `-e 7 -d 0`), and four conformance files. No
  alpha, animation, JPEG reconstruction or small-image inputs. The ratio
  depends on the input (2.2–2.9× in (b) for lossy).
- Not an isolated benchmark host: background desktop processes ran (above).
  The interleaving makes the ratios robust to slow drift; the spread is
  within ±5 % except column (c) of the original (lossless 24 MP: 376–495 ms),
  which uses all cores and is the most sensitive to other load.
- Column (c) compares a parallel original with a serial port (see above);
  its ratio is mostly the original's thread scaling.
- The P/E core mix: the one-thread runs are scheduled by macOS, presumably
  on a performance core (not pinned); column (c) uses all ten cores.
- The profile is one input, one run per side, 1 ms sampling; shares are
  indicative.
