# v1.0 performance against the original in three columns, 2026-11-13

Decision D2 of 2026-11-13 reports performance per codec and operation
against the original the port translates, in three columns measured in the
same job on the same machine:

- **(a)** the original built **scalar**, one thread: the translation loss;
- **(b)** the original's release build **with SIMD**, one thread, restricted to
  the v1.0 SIMD scope of decision D6 (NEON on AArch64; AVX2 and the lower x86
  levels the original selects itself on x86-64; nothing above);
- **(c)** that SIMD build with **all threads** the original can use ("n/a"
  where it has no threading for the operation).

Third-party libraries (jxl-oxide, dav1d) are context columns, kept apart.
The optimization order D2 sets is top-down: close (a) first, then (b), then
(c). There is no performance gate for v1.0 (D3); this record is evidence,
not a release claim.

- **Source:** `origin/main` at `e4038a4a` (the integration state of decision
  D9) plus only the measurement tooling of this record: the extended
  `scripts/bench/ci-perf/` scripts, the workflow change and a new example
  `codecs/libjxl-rs/examples/encode_lossless.rs`. No library code differs
  from `e4038a4a`. Other agents are changing the JPEG XL port tonight; every
  JPEG XL row describes `e4038a4a`, which on non-AArch64 targets runs the
  pre-work scalar render stages (commit `d91cbc48`).
- **Run:** [43338832841](https://github.com/sebastian-software/ferrisma/actions/runs/43338832841)
  on `bench/v1.0-perf` (head `0e57bf4f`, an empty commit over the tooling
  commit `9161c466`). 18 codec jobs, all successful, 1.5–22 minutes each.
- **Platforms:** GitHub-hosted `ubuntu-24.04` (GH x86-64),
  `ubuntu-24.04-arm` (GH ARM64), `macos-15` (GH macOS ARM64), and
  Blacksmith `blacksmith-4vcpu-ubuntu-2404` (BS x86-64) and `-arm` (BS
  ARM64). AVIF runs only where the generated libavif/AOM port builds (x86-64
  Linux and macOS ARM64).
- **Evidence:** [evidence-2026-11-13-ci-three-column](evidence-2026-11-13-ci-three-column/),
  one directory per workflow artifact (`codec-<codec>-<runner>`), complete
  and unmodified (2.8 MB of JSON and host text).

## Method

- **Workflow:** [bench-v1-perf.yml](../../.github/workflows/bench-v1-perf.yml),
  job `codec`, one job per codec and platform; the head commit carried
  `[bench codecs-only]`, which skips the engine matrix. Scripts:
  [codec_jpeg.sh](../../scripts/bench/ci-perf/codec_jpeg.sh),
  [codec_webp.sh](../../scripts/bench/ci-perf/codec_webp.sh),
  [codec_jxl.sh](../../scripts/bench/ci-perf/codec_jxl.sh),
  [codec_avif.sh](../../scripts/bench/ci-perf/codec_avif.sh).
- **Timing** (unchanged from the
  [2026-11-12 CI record](v1.0-ci-performance-2026-11-12.md)):
  [run_interleaved.py](../../scripts/bench/ci-perf/run_interleaved.py) runs
  every sample as a fresh process; all candidates of one operation and input
  are in one plan, one warm-up round and 7 repetitions, order alternating
  forward and reversed. The JPEG XL lossy encoder (about a minute per 12 MP
  sample) runs at 12 MP only, 3 repetitions, no warm-up. Tables use the
  median of each program's own timer around the core operation (file I/O
  outside on both sides); min–max, process wall time, max RSS, load averages
  before and after each sample, and every raw sample are in the evidence.
  The port is the repository release profile without `RUSTFLAGS`, on one
  thread; its own SIMD dispatch is whatever it does by default.
- **Inputs:** the two photographs of the earlier CI record (`photo12`, the
  4032×3024 libavif test photograph, and `photo24`, the 6000×4000
  `mountain` photograph), as 8-bit RGB masters; every codec input is encoded
  from them by the original's own SIMD build.
- **Host record:** `host-before.txt` / `host-after.txt` (`lscpu` or
  `sysctl`, load), `cpu-features.json` (the SIMD extensions the CPU offers,
  the highest D6 level and what lies above it) and `<codec>-build.json`
  (flags, compiler, revisions, and a `columns` block naming each column's
  build and the SIMD level of column (b)) per job.

### How each column is built

| Codec | (a) scalar, one thread | (b) SIMD at the D6 level, one thread | (c) all threads |
| --- | --- | --- | --- |
| JPEG (libjpeg-turbo 3.2.1) | `build_oracle.py` variant `release`: CMake Release, `WITH_SIMD=0` (no SIMD code compiled), `-ffp-contract=off` | variant `simd`: `WITH_SIMD=1`; libjpeg-turbo has no code above AVX2/NEON, so no restriction is needed | n/a: the decoder has no threading |
| WebP (libwebp 1.6.0) | CMake Release with `WEBP_ENABLE_SIMD=OFF` (no `WEBP_HAVE_*` SIMD define, so no SIMD path; on x86-64 also `-mno-sse2 -mno-sse4.1 -mno-avx2`) | CMake Release with SIMD; libwebp has nothing above AVX2/NEON | `-mt`: libwebp's only threading, one extra worker (at most two threads); n/a for lossless decode |
| JPEG XL (libjxl `a16d32d0`) | the repository's differential-oracle configuration: Clang, `HWY_COMPILE_ONLY_SCALAR=1`, libc++ on Linux; `--num_threads=0` | CMake Release with Highway dynamic dispatch and `JPEGXL_ENABLE_HWY_{AVX3,AVX3_DL,AVX3_ZEN4,AVX3_SPR,SVE,SVE2,SVE_256,SVE2_128,NEON_BF16}=OFF`; `--num_threads=0` | the same build, default runner (one worker per CPU) |
| AVIF (libavif 1.4.2 + libaom 3.15.2) | libaom `AOM_TARGET_CPU=generic` (no SIMD, no assembly; every RTCD entry is the `_c` function), libavif without dav1d | libaom release with run-time CPU detection and `-DENABLE_AVX512=0 -DENABLE_NEON_DOTPROD=0 -DENABLE_NEON_I8MM=0 -DENABLE_SVE=0 -DENABLE_SVE2=0` | the same build, `maxThreads` = CPUs (autotiling for encode) |

Which switches give a true scalar build:

- **libjpeg-turbo:** `WITH_SIMD=0` compiles no SIMD code. `JSIMD_FORCENONE=1`
  would select the same C functions at run time in the SIMD build; the
  separate build was chosen because it is the repository's reference oracle.
- **libwebp:** `WEBP_ENABLE_SIMD=OFF` is a true scalar build. `-noasm` is
  not: with SSE2 (x86-64) and NEON (AArch64) as compiler baseline, libwebp
  omits the C versions of the kernels that have such a variant
  (`WEBP_DSP_OMIT_C_CODE`), so `-noasm` still runs SSE2/NEON code.
- **libjxl:** `HWY_COMPILE_ONLY_SCALAR` compiles only Highway's scalar
  target. libjxl's own CMake adds `-fno-slp-vectorize -fno-vectorize` for
  Clang in every build, so neither column is auto-vectorized.
- **libaom:** `AOM_TARGET_CPU=generic` is a true scalar build.
  `AOM_SIMD_CAPS_MASK=0` is not: libaom's RTCD generator treats MMX/SSE/SSE2
  on x86-64 and NEON on AArch64 as required baseline and calls those
  variants regardless of the mask.
- The scalar builds of libjpeg-turbo, libwebp and libaom are compiled with
  the compiler's default auto-vectorization (CMake Release, `-O3 -DNDEBUG`
  as recorded in the build files). "Scalar" therefore means
  "no hand-written SIMD", not "no vector instructions"; on AArch64 the
  compiler may emit NEON for plain loops. libjxl is the exception (above).
- dav1d (context) keeps its full assembly, AVX-512 included; it is not on
  the engine's path and is not restricted.

## Where the loss sits, per codec

Reading rule: (a) above 1 is translation loss (the port is slower than the
same algorithm in plain C); (b) above (a) is the part the original gains from
its hand-written SIMD that the port does not match; (c) above (b) is what the
original gains from threads. Ranges below cover Linux hosts unless stated;
macOS rows are noisier (see the limits).

- **JPEG decode: no loss left at one thread.** (a) 0.44–0.65: the port is
  1.5–2.3× faster than the scalar original, so its SIMD works. (b)
  0.99–1.06 on Linux, 1.07–1.17 on the macOS VM. (c) n/a: libjpeg-turbo
  decodes on one thread, so a multi-threaded decode would be a new feature
  rather than a port gap.
- **WebP decode.** Lossy: no translation loss ((a) 0.62–0.75); the SIMD gap
  is on x86-64 ((b) 1.26–1.45 against 1.05–1.12 on Linux ARM64); `-mt`
  (one extra thread) adds a further 1.5–2.3×. Lossless: on x86-64 the port
  matches the scalar original ((a) 0.91–0.97) and loses only against SIMD
  ((b) 1.23–1.30); on ARM64 (a) and (b) are equal (1.19–1.35 / 1.27–1.32),
  so there the whole gap is translation loss and libwebp's NEON adds
  nothing measurable. No threading in the original.
- **WebP lossy encode: translation loss on x86-64, SIMD loss everywhere.**
  On x86-64 the port is slower than the *scalar* original ((a) 1.22–1.42),
  which means its x86 path (SIMD included) loses to plain C; (b) 2.21–2.61.
  On ARM64 (a) 0.85–0.96 and (b) 1.32–1.35. `-mt` adds only 2–8 %.
  **Lossless encode:** (a) 1.03–1.26 and (b) 1.03–1.37 are close on every
  host, so the loss is translation; libwebp's SIMD and `-mt` gain almost
  nothing at the default method.
- **JPEG XL VarDCT decode: the largest loss, and on x86-64 mostly
  translation.** x86-64: (a) 6.0–7.2 — the port is six to seven times slower
  than libjxl's *scalar* build, which is the pre-work scalar render stages
  that `e4038a4a` runs on non-AArch64 targets; (b) 14–21; (c) 36–69. ARM64:
  (a) 1.5–1.6, (b) 3.6–4.1, (c) 13–15. So on ARM64 about 1.5× is
  translation, about 2.5× the missing SIMD and about 3.5× the missing
  threads; on x86-64 the translation part alone exceeds the whole ARM64 gap
  to SIMD. jxl-oxide (context) is 1.7–1.75× faster than the port on Linux
  ARM64 and 6.3–8.3× faster on x86-64.
- **JPEG XL lossless decode: translation loss only.** (a) and (b) agree to
  within 0.04 on every Linux host (1.29–1.47): libjxl's SIMD does not speed
  up this modular path. (c) 3.5–5.8: libjxl's threads are the larger gap.
  jxl-oxide decodes within 3–8 % of the port.
- **JPEG XL lossy encode (e7 d1, 12 MP).** x86-64: (a) 3.3–3.5, (b)
  15.6–16.5, (c) 29–33. ARM64: (a) 1.4–1.8, (b) 4.7–6.0, (c) 15–19. Both
  translation and SIMD are large, more so on x86-64. On GH ARM64 the
  restriction to NEON made the reference *faster* than the earlier
  unrestricted build (cjxl one thread 6.7 s against 10.9 s with Highway's
  SVE2_128 target in the 2026-11-12 runs), so (b) is now 4.7 instead of 2.9.
- **JPEG XL lossless encode (e2): translation loss only.** (a) ≈ (b),
  1.07–1.31; (c) 1.9–2.9.
- **AVIF decode (libaom): SIMD loss, no translation loss.** (a) 0.68–0.79,
  (b) 1.35–1.45. (c) 0.86–1.58: libaom's decoder gains nothing from threads
  on these one-tile stills and is *slower* with them on GH x86-64, so (c) is
  not a target here. dav1d (context) is 2.2–2.7× faster than the port on one
  thread and 3.4–4.0× with threads.
- **AVIF encode: SIMD and threads.** (a) 0.48–0.52, (b) 1.33–1.38, (c)
  3.0–4.7. The port's encoder is twice as fast as scalar libaom; it trails
  libaom's SIMD by about a third and libaom's threads (autotiling) by a
  further 2–3.5×.

Top-down order of D2 (close (a) first): the operations with translation loss
are JPEG XL VarDCT decode (x86-64 especially), JPEG XL lossy encode, JPEG XL
lossless decode and encode, WebP lossy encode on x86-64, WebP lossless
encode, and WebP lossless decode on ARM64. JPEG decode, WebP lossy decode,
and AVIF decode and encode have none.

## Correctness side checks

Recorded by the scripts, not a gate here (the gate is D4/D8 in the
repository's oracle tests).

- **JPEG:** the scalar original, the SIMD original and the port give the
  same FNV-1a checksum for every input on every host.
- **WebP:** 28 of 28 checks identical on every host: the port, the scalar
  build and `-mt` produce the same files and pixels as the SIMD build on one
  thread.
- **JPEG XL lossy encode (12 MP, e7 d1):** the port's codestream (2,057,281
  bytes, `d65d5c60e5aa…`) is still byte-identical to the scalar original on
  all five hosts. The SIMD build differs (2,057,280 bytes on ARM64; same
  size, different content on x86-64), as before.
- **JPEG XL lossless encode (e2):** the port's codestream is 51 bytes
  smaller than cjxl's with `-d 0 -e 2 --codestream_level=10 --buffering=0`
  (12 MP: 9,701,462 against 9,701,513; 24 MP: 25,574,493 against 25,574,544),
  on every host; scalar and SIMD cjxl agree with each other. These cjxl
  flags evidently do not reach exactly the `LosslessThunderConfig` path (the
  port's own oracle tests compare against an adapter, not cjxl), so this row
  compares the same algorithm with a small difference in the written
  stream. Not attributed here.
- **JPEG XL decode:** port against jxl-oxide F32 maximum difference
  1.66e-4 (VarDCT) and 6e-8 (lossless), as before; djxl's lossless round
  trip is pixel-identical to the master.
- **AVIF encode:** on both x86-64 hosts the port's file is byte-identical
  to *both* C builds (scalar and SIMD), which also agree with each other.
  On macOS ARM64 scalar and SIMD libaom agree with each other but the port
  differs from both. The earlier record attributed the macOS difference to
  libaom's dotprod/i8mm kernels; with those disabled and in the scalar build
  it remains, so that explanation does not hold. The C builds here use the
  compiler's default floating-point contraction (Apple Clang fuses
  multiply-adds on ARM64), unlike the repository's `-ffp-contract=off`
  oracle; that is the likely cause, but it was not verified.
- **AVIF decode:** decoded RGB identical across every candidate (scalar and
  SIMD libaom, threads, dav1d, the port) on every host.

## Limits of this evidence

- **One run, shared VMs.** Linux spreads (min–max in the per-platform
  tables) are mostly within a few percent; the macOS VM (3 vCPUs, load
  averages up to 34 during samples) has spreads up to 1.5× and is the least
  reliable platform.
- **CPU models differ between jobs.** GitHub-hosted x86-64 gave four
  different CPUs to the four codec jobs (AMD EPYC 9V45 and 9V74, Intel Xeon
  Platinum 8370C and 8573C), and the Blacksmith x86-64 JPEG job ran on an
  Intel Xeon while its other jobs ran on AMD EPYC. Ratios are within one job
  and comparable; absolute times across codecs or against earlier records
  are not.
- **The D6 restriction mattered only where the CPU offered more.** Every
  x86-64 job except BS x86-64 JPEG had AVX-512; every ARM64 host offers
  dotprod (GH ARM64 also SVE/SVE2/BF16/I8MM, BS ARM64 BF16/I8MM). libjxl and
  libaom were restricted by their own switches; libjpeg-turbo and libwebp
  have nothing above AVX2/NEON. The selected level is recorded per job:
  libjxl reports `AVX2` on x86-64 and `NEON` on all ARM64 hosts.
- **"Scalar" is not "no vector instructions"** for libjpeg-turbo, libwebp
  and libaom (compiler auto-vectorization at `-O3`); it is for libjxl. See
  the method.
- **The port side is not restricted.** The port runs its default dispatch;
  whether that stays inside D6 on every AVX-512 host is a property of the
  port, not checked here.
- **Thread columns use what the original offers:** two threads for libwebp
  `-mt`; all 4 (3 on macOS) vCPUs for libjxl and libaom, which on GitHub
  x86-64 are 2 cores with SMT. AVIF encode (c) uses autotiling, so it codes
  a different bitstream than (a), (b) and the port.
- **Two photographs; one 12 MP sample per lossy JPEG XL encode** (3
  repetitions). AVIF encode at 12 MP only. No AVIF on Linux ARM64.
- **JPEG XL is `e4038a4a`.** The x86-64 VarDCT and encode rows describe the
  pre-work scalar render stages; any later JPEG XL change needs a new run.
- **Timer scopes** are the same as in the 2026-11-12 record (djxl/cjxl from
  their MP/s line; WebP tools at 1 ms resolution).

## Proposed follow-ups

- Attribute the x86-64 JPEG XL VarDCT translation loss ((a) 6–7×) to render
  stages, now that a scalar libjxl reference exists on the same host.
- Check whether the macOS ARM64 AVIF encoder difference disappears against
