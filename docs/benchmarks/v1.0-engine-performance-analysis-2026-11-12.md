# v1.0 engine performance analysis, 2026-11-12 (indicative; loaded host)

**Every timing in this record is indicative and was taken on a loaded host.**
The Apple M1 Ultra was shared with other agents that built and tested in
parallel; the 1-minute load average was between about 7 and 33 and is stated
per table. Profile *shares* and interleaved *ratios* (port versus C,
before versus after) are the primary results: both sides of a ratio ran
alternately under the same load. Absolute milliseconds are inflated by the
load (for example the 24 MP JPEG decode stage read 135 ms in the
[baseline](v1.0-baseline-2026-11-12.md) at load 7–9 and 134–360 ms here) and
are not release-grade numbers; a separate CI benchmark owns those.

This record answers where the time and memory go in the engine and in the
JPEG, WebP and AVIF paths (JPEG XL is covered elsewhere), compares each port
with its original C library, and ranks fixes. Raw data, scripts and trimmed
profiles are in [evidence-2026-11-12-engine-perf](evidence-2026-11-12-engine-perf/).

## Summary

- **JPEG decode** is 1.56–1.85× slower than C libjpeg-turbo 3.2.1 on 4:2:0 and
  4:2:2 photos, and 1.10–1.24× on a 4:4:4 photo. About 80 % of the gap is the
  Huffman decoder: the port's `HUFF_DECODE_FAST` helper is not inlined and
  takes its bit-buffer state through `&mut` references. Forcing it inline (one
  attribute) brought the port to 1.03–1.11× of C, 29–44 % faster, with
  identical output checksums. This is the largest and cheapest win in this
  record (#76, #221).
- **Rendered-ICC transform** (#219): about three quarters of its cost is moxcms evaluating the
  transfer curve per sample (`extended_linear_tristimulus`). For 8-bit
  matrix-shaper input, a 768-entry per-channel contribution table built from
  moxcms itself cut the transform stage from 565 to 132 ms at 24 MP on one
  thread. Its largest difference from moxcms over all 2^24 RGB triplets is
  1.2e-7 linear for five profiles. Not committed: 10-bit AVIF output bytes
  changed (the WebP output of the test image did not), so it needs the owner's acceptance of a
  bound.
- **AOM encode** (port of libaom 3.15.2, NEON) is 1.23–1.30× C libaom 3.15.3
  on ordinary photos and 1.51–1.72× on the 42 MP `elcito` photo, **with
  byte-identical output**. The `elcito` anomaly (#220) is content: libaom's
  palette search runs on this photo, in C as well, and the port lacks the
  NEON `av1_calc_indices_dim{1,2}` kernels, which alone account for about
  750 ms of its 1.2 s gap. Other gaps: zero-initialized C locals (`memset`,
  +170 ms of a 450 ms gap on the dog photo), `c2rust` bitfield accessors
  (+40–60 ms), and `_c` fallbacks for kernels that have NEON upstream
  (`av1_cnn_convolve_no_maxpool_padding_valid`, Hadamard, CfL, `get_nz_map_contexts`,
  `nn_predict`; #121, #125).
- **AVIF decode** (port of libavif + libaom decoder) is about 1.37× C. It holds
  about 320 MB of opaque memory at 24 MP; 271 MB of it is a single libaom
  allocation, the decoder's 4×4 mode-info grid (11.3 bytes per pixel). C
  libavif + libaom holds the same (445 MB RSS), so #199 is a property of
  libaom, not of the port. The decode ran on one thread including libavif's
  YUV-to-RGB conversion; **prototype committed:** the conversion now splits
  across the transform threads (byte-identical, no memory change), saving
  about 100 ms of a 690 ms decode stage at 24 MP with all cores. Giving libaom
  itself more threads halved the decode stage but raised RSS from 0.42 to
  1.8 GB, so the commit leaves it single-threaded.
- **WebP**: decode is 1.14–1.20× C libwebp 1.6.0; encode about 1.4–1.5×
  (approximate settings match). The largest port-only cost is an
  out-of-line NEON helper `load4x4_neon` (14 % of encode self time) and a
  CPU-feature lookup on every dispatch (1–3 %).
- **Engine**: on one thread at 24 MP to 1600 px the transform (linearize,
  resize, quantize) is 13–31 % of CPU; with all cores it is 3–4 % of wall.
  The serial part with all cores is the decoder on the driver thread (JPEG:
  42 % of wall for 24 MP to 1600 px AVIF), not the driver's row handoff
  (#59). Orientation 6 at 24 MP costs 16 % of one-thread CPU; a tiled gather
  removed 57 % of it in an experiment.

## Host, build and method

- Apple M1 Ultra (Mac13,2), 20 cores, 64 GiB, macOS 27.0.1, Darwin 27.0.0
  arm64; `rustc 1.100.0-nightly (5a2be9f5f 2026-09-06)`.
- Source: base commit `93c5281f`. Release profile with
  `CARGO_PROFILE_RELEASE_DEBUG=line-tables-only` for symbolized profiles (code
  generation otherwise unchanged); `cargo build --locked --release -p ferrisma
  --features cli --bin ferrisma`.
- Profiler: `samply 0.13.1` (`record -s --unstable-presymbolicate -r 2000` or
  `4000`), summarized by [prof.py](evidence-2026-11-12-engine-perf/prof.py):
  self and inclusive shares weighted by thread CPU time, and a *stage*
  attribution that assigns each sample to the first matching frame from the
  leaf up (ICC, orientation, resize, quantize, linearize, RGB→YUV, encoders,
  decoders, synchronization). One misattribution is known: libwebp-rs's
  `webp::dsp::cpu::features`, called from the encoder, is counted under
  `webp-decode` in the stage tables.
- Live allocations: `lldb` stops the CLI at `avifImageYUVToRGB` (AV1 decode
  done, conversion not started) under `MallocStackLogging=1`, then
  `malloc_history -allBySize` ([memsnap.py](evidence-2026-11-12-engine-perf/memsnap.py),
  [memsum.py](evidence-2026-11-12-engine-perf/memsum.py)). Instruments'
  Allocations template hung on launch and was abandoned.
- C references, all from Homebrew because the ports' oracle submodules
  (`upstream/libjpeg-turbo`, `upstream/libwebp`) are not initialized in this
  worktree and no network fetch was made:
  - libjpeg-turbo **3.2.1** (the port's pinned tag), NEON, timed through the
    port's own C probe `tools/oracle/probes/wp9/bench.c` against the port's
    `examples/bench.rs`; output checksums compared.
  - libwebp **1.6.0** (the pinned tag), `cwebp`/`dwebp -v` internal timers.
  - libaom **3.15.3** (port pin: 3.15.2) with the **vendored** C libavif 1.4.2
    source (`codecs/libavif-rs/upstream/libavif`, CMake Release, static,
    `AVIF_CODEC_AOM=SYSTEM`, no libyuv), timed through the port's
    `tools/encode_still.c` with a timer added
    ([patch](evidence-2026-11-12-engine-perf/encode_still-timing.patch))
    against `examples/encode_still.rs`; and a small decode timer
    ([c_avif_decode_time.c](evidence-2026-11-12-engine-perf/c_avif_decode_time.c)).
    Encoded outputs were byte-identical between port and C in 5 of 6 cells.
- Inputs: the baseline's `in19` set (12 MP dog with sRGB ICC, 24 MP mountain
  without ICC, the same pixels as WebP and AVIF, orientation 1/2/6 variants,
  and the mountain with the dog's sRGB ICC) and the corpus photos `elcito`
  (7952×5304, 4:2:2, q100) and `beach` (9504×6336, 4:4:4, restart interval
  1188). Hashes are in the [baseline inputs](evidence-2026-11-12-baseline/inputs.sha256).
- Interleaved runs alternate candidate order per repetition (forward,
  reversed). The CLI stage matrix used 3 repetitions; port-versus-C 3–7; the
  prototype A/B the baseline's [run_interleaved.py](evidence-2026-11-12-baseline/run_interleaved.py)
  with one warm-up and 7 repetitions.

## 3. Port versus original C

### JPEG decode: libjpeg-turbo-rs versus libjpeg-turbo 3.2.1

`bench` (port) and `bench.c` (C probe), 3 decodes per process, RGB, islow,
fancy upsampling; 5 interleaved repetitions; every port output checksum equals
C's. Load 8–11 ([table](evidence-2026-11-12-engine-perf/profiles/jpeg-port-vs-c-timing.md)).

| input | full: port / C ms | ratio | scale 1/2 ratio | scale 1/8: port / C ms | ratio |
| --- | ---: | ---: | ---: | ---: | ---: |
| dog 12 MP 4:2:0 q95 | 63 / 40 | 1.56 | 1.62 | 49 / 28 | 1.76 |
| mountain 24 MP 4:2:0 q95 | 134 / 86 | 1.57 | 1.62 | 109 / 62 | 1.75 |
| elcito 42 MP 4:2:2 q100 | 448 / 278 | 1.61 | 1.66 | 386 / 212 | 1.82 |
| beach 60 MP 4:4:4 q94, DRI | 268 / 220 | 1.22 | 1.16 | 165 / 148 | 1.11 |

Per-stage attribution on the mountain photo, from profiles of both
([port](evidence-2026-11-12-engine-perf/profiles/jpegport-mountain.md),
[C](evidence-2026-11-12-engine-perf/profiles/jpegc-mountain.md)), scaled to the
per-decode times:

| stage | port ms | C ms | port/C |
| --- | ---: | ---: | ---: |
| Huffman (`decode_mcu` + `HUFF_DECODE_FAST`) | ~101 | ~62 | 1.64 |
| IDCT (islow NEON, both passes) | ~20 | ~14 | 1.43 |
| YCC→RGB | ~6 | ~5 | 1.1 |
| h2v2 fancy upsampling | ~4 | ~3 | 1.3 |
| coefficient controller | ~3 | ~2 | 1.3 |

The Huffman decoder is about 80 % of the gap. In the port,
`HUFF_DECODE_FAST` is a separate function taking `get_buffer`, `bits_left`,
`buffer` and `nb` by `&mut`; it is marked `#[inline]` but LLVM does not
inline it, so the bit buffer lives in memory instead of registers. C's
`HUFF_DECODE_FAST` is a macro. **Experiment** (not committed; codec code is
outside this package): `#[inline(always)]` on that one function
([patch](evidence-2026-11-12-engine-perf/jpeg-huffman-inline.patch)), 5
interleaved repetitions at load 21–30, identical checksums across port,
patched port and C:

| input | port ms | patched ms | C ms | patched / port | patched / C |
| --- | ---: | ---: | ---: | ---: | ---: |
| dog 12 MP | 64 | 45 | 40 | 0.71 | 1.11 |
| mountain 24 MP | 141 | 96 | 87 | 0.68 | 1.10 |
| elcito 42 MP | 492 | 306 | 286 | 0.62 | 1.07 |
| beach 60 MP 4:4:4 | 277 | 266 | 223 | 0.96 | 1.19 |
| mountain, scale 1/8 | 117 | 66 | 63 | 0.56 | 1.04 |

The 4:4:4 photo gains little because its gap is elsewhere. Profiles of the
patched port and C on `beach` (4 decodes each,
[port](evidence-2026-11-12-engine-perf/profiles/jpegport-beach-inline.md),
[C](evidence-2026-11-12-engine-perf/profiles/jpegc-beach.md)): Huffman 682
versus 632 ms (1.08), IDCT 404 versus 294 ms (1.37), coefficient controller
95 versus 53 ms (1.8). Full-resolution chroma doubles the IDCT work, and the
port's NEON IDCT calls its second pass as separate functions
(`jsimd_idct_islow_pass2_regular`, `_sparse`, 9.4 % + 2.5 % self) where C
inlines them. Those helpers carry `#[target_feature(enable = "neon")]` and
`#[inline]`, and LLVM does not inline them; `#[inline(always)]` without the
attribute does not compile, because the NEON intrinsics then need `unsafe`.
The same pattern keeps WebP's `load4x4_neon` out of line (below). #74 (AVX2 gains less than
upstream) is the x86 face of the same kernel question and could not be
measured on this host.

**Shrink-on-load (#56).** At scale 1/8 the port saves only 14–24 % of the
decode on the 4:2:x photos (C: 22–28 %), because entropy decoding is not
scaled. After the Huffman fix, 1/8 saves about 31 % (mountain 96 → 66 ms).
Its larger effect is downstream: a 1/2–1/8 decode shrinks the transform's
horizontal pass input by 4–64×.

`av1_highbd_quantize_fp` costs about the same on both sides (the port's
`_facade` corresponds to C's `highbd_quantize_fp_helper_c`).

**#220 explained.** libaom's palette search runs on `elcito` (C spends 25 %
of its encode inside `av1_rd_pick_palette_intra_sby` as well); quality 82
makes it worse than 56. The port's scalar k-means turns that into 1.72× C.
With C's kernels the q82 encode would take about 1.7 s, against rav1e speed 6
at about 1.65 s in the baseline: parity, not an 84 % anomaly. Settings are
not the cause: the port and C use the same libavif defaults (`autoTiling`
and `maxThreads` only when threads ≠ 1, as in `crates/ferrisma-avif-write`),
and the outputs are byte-identical. A palette switch for photographic input
would change output bytes and needs its own quality-matched evaluation.

### AVIF decode: AOM decoder port versus C libavif + libaom 3.15.3

24 MP 8-bit 4:2:0 AVIF, one thread, three runs each, load 12–15: C
`avifDecoderReadMemory` 401–407 ms + nearest-neighbor YUV-to-RGB 85–88 ms
(491 ms, 445 MB RSS); port decode stage 665–676 ms (414 MB RSS for the whole
CLI). Ratio about 1.37. In the port profile, `av1_inv_txfm_add_c` (8-bit

### WebP: libwebp-rs versus libwebp 1.6.0

7 interleaved repetitions, load 20–22. Decode: engine `decode_us` (lossy
WebP to RGB rows, one thread) against `dwebp -v`. Encode: engine `encode_us`

| --- | ---: | ---: | ---: |

| decode WebP 24 MP | 255 | 223 | 1.14 |
| encode 1600×1067 | 181 | 123 | 1.47 (approximate) |

On a 24 MP encode the profiles agree with that ratio (port about 2.3 s of
encode CPU, C about 1.65 s). Port-only costs:

issue #77 cannot be measured on this host; on AArch64 the decode gap is
14–20 %.

## 4. Prototype: AVIF YUV-to-RGB on the transform threads (committed)

Commit `perf(avif): split the AVIF YUV-to-RGB conversion across transform
threads`. `DecodeSource` gains `set_decode_threads` (default no-op); the
pipeline passes the resolved transform thread count before any wrapper; the
AVIF source sets libavif's `avifRGBImage.maxThreads`, which splits the
nearest-neighbor conversion into at most eight row jobs. One transform thread
keeps the serial path, so batch work (one thread per image) is unchanged. A
new test, `codecs::avif::tests::decode_threads_do_not_change_samples`,
decodes 8-bit 4:4:4 and 4:2:0 files and a 12-bit 4:4:4 file with 1, 2, 3 and
8 threads and requires identical samples.

Interleaved A/B ([run-yuvmt.json](evidence-2026-11-12-engine-perf/run-yuvmt.json)),
7 repetitions, load 20–33 (very noisy); every output identical between base
and prototype:

| case | base wall s | prototype wall s | change | max RSS MB base / prototype |
| --- | ---: | ---: | ---: | ---: |
| AVIF 24 MP → WebP 1600, all cores | 1.354 | 1.194 | −12 % | 441 / 441 |
| AVIF 24 MP → AVIF 1600, all cores | 1.326 | 1.211 | −9 % | 531 / 530 |
| AVIF 12 MP → WebP 1600, all cores | 0.897 | 0.741 | −17 % | 245 / 246 |
| AVIF 24 MP → WebP 1600, one thread | 1.417 | 1.430 | (unchanged path) | 436 / 435 |

A quieter direct sweep (load about 12–14) gave the 24 MP decode stage 690 →
590 ms with 8 or 20 threads and unchanged RSS.

**Rejected variant: libaom decoder threads.** Passing the thread count to
libavif's `decoder.maxThreads` as well
([run-avifmt.json](evidence-2026-11-12-engine-perf/run-avifmt.json), load
13–17) cut the 24 MP AVIF → WebP wall from 0.905 to 0.559 s, but max RSS rose
from 440 MB to 1.89 GB, at any thread count from 2 to 20. That is libaom's
row-based multithreading, which keeps coefficient buffers for every
superblock. The commit does not enable it; see solution 6.

## Limits of this evidence

- Loaded host (load 7–33); absolute times are inflated and noisy. Ratios were
  interleaved but contention still differs between moments. No idle-host run.
- One machine (ARM64). x86-64 issues (#74, #77, #124) were not measured.
- C references are Homebrew builds of the same tags (libjpeg-turbo 3.2.1,
  libwebp 1.6.0) and of libaom **3.15.3** against the port's 3.15.2, not the
  ports' pinned oracle builds (submodules not initialized; no network). The
  AOM outputs were byte-identical in 5 of 6 cells, which supports equal work.
- The WebP encode comparison does not reproduce cwebp's exact settings
  (outputs differ by 1.3 %); treat 1.47 as approximate.
- Profiles are single runs at 2–4 kHz; shares below about 0.5 % are noise.
  Inlined functions are attributed to their callers.
- The ICC table was checked exhaustively for five matrix-shaper profiles
  only; LUT-based profiles were not covered and keep the moxcms path.
- AVIF memory: one 24 MP 8-bit 4:2:0 file; other bit depths, 4:4:4 and
  multi-tile files were not snapshotted.
- dav1d as AVIF decoder: not measured (selection failed in this build).
- Stage report `decode_us` excludes the transform callback but includes the
  adapter's own copies; for AVIF it includes AV1 decode plus YUV-to-RGB.

### Fix 16: WebP `encoder_threads` error names the cause

The built-in WebP encoder is serial (`src/webp_sink.rs` accepts exactly one
thread), as is the JPEG XL encoder, which already said so. `0` means
"available cores" for AVIF and is reported as the resolved count, so mapping
it silently to one thread for WebP would make the report wrong. The facade
now rejects any other value for built-in WebP output before decoding with
`InvalidOptions` and *"the WebP encoder is serial; set encoder_threads to 1"*
instead of *"encoder quality/speed or output dimensions are invalid"*; an
external WebP backend still receives and validates its own thread count
(ADR-0024). Test: `webp_output_tests::webp_encoder_threads_other_than_one_name_the_serial_encoder`
(0 and 2 rejected with that message, both accepted by an external backend,
default reports one thread). No timing involved.
