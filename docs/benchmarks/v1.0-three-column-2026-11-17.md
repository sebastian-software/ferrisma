# v1.0 performance against the original in three columns, 2026-11-17

The second complete run of the three-column comparison of decision D2
(ADR-0041), on `main` four days after the
[record of 2026-11-13](v1.0-three-column-2026-11-13.md). Same workflow, same
inputs, same reference builds, same five platforms; the method below is
that record's, unchanged except where stated. There is no performance gate
for v1.0 (D3); this record is evidence, not a release claim.

- **(a)** the original built **scalar**, one thread: the translation loss;
- **(b)** the original's release build **with SIMD**, one thread, restricted
  to the v1.0 SIMD scope of D6 (NEON on AArch64; AVX2 and the lower x86
  levels the original selects itself on x86-64);
- **(c)** that SIMD build with **all threads** the original can use ("n/a"
  where it has no threading for the operation).

Third-party and not-yet-adopted decoders (jxl-oxide, dav1d, the dav1d port)
are context columns, kept apart and off every summary of the port.

- **Source:** `main` at `f4be1596`, with no other change: the run's head
  `12197163` on `bench/main-1117` is an empty commit on it, carrying
  `[bench codecs-only]` (the engine matrix was skipped).
- **Run:** [43978421716](https://github.com/sebastian-software/ferrisma/actions/runs/43978421716),
  workflow "v1.0 CI performance". 18 codec jobs, all successful, 1.5–21.7
  minutes each.
- **Platforms:** GitHub-hosted `ubuntu-24.04` (GH x86-64), `ubuntu-24.04-arm`
  (GH ARM64), `macos-15` (GH macOS ARM64), and Blacksmith
  `blacksmith-4vcpu-ubuntu-2404` (BS x86-64) and `-arm` (BS ARM64). AVIF
  runs only where the libavif/AOM port builds (x86-64 Linux and macOS ARM64).
- **Evidence:** [evidence-2026-11-17-ci-three-column](evidence-2026-11-17-ci-three-column/),
  one directory per workflow artifact (`codec-<codec>-<runner>`), complete
  and unmodified (JSON and host text; the input photograph of the `corpus`
  artifact is not committed).
- **AVIF job script:** the November 13 script predates the dav1d context
  columns of `5e187eb4` (libavif-rs ADR 0062). The AVIF job needed two fixes
  to `scripts/bench/ci-perf/codec_avif.sh`, both on `main` before the run:
  `e8565a44` builds the scalar decode driver without dav1d (the scalar
  reference prefix has none, so every AVIF job failed to compile), and
  `f4be1596` declares `dav1d_set_cpu_flags_mask`, which dav1d exports but
  declares only internally (Apple clang rejected the implicit declaration).
  Neither changes a timed operation.

## Context: the dav1d port and stock dav1d (AVIF decode)

Context only. The engine reads AVIF through the translated libaom, not through
dav1d, and nothing here ranks decoders for the engine (ADR-0031, amendment of
2026-11-16). The cells in the per-platform tables are the port's (libaom)
time divided by each context column's time, as for the reference columns.

- `c-dav1d:t1` / `c-dav1d:tN`: stock libavif with dav1d, its full assembly,
  unrestricted (AVX-512 where the CPU has it), one thread and all threads.
- `c-dav1d-v1:t1`: the same, restricted with `dav1d_set_cpu_flags_mask` to the
  v1.0 SIMD scope (up to AVX2; NEON), the level rebuilt kernels are gated
  against.
- `port-dav1d:t1`: the workspace's dav1d port through libavif-rs's
  `decode_codec` example, with the kernels rebuilt so far. **Caveat:** on
  `main` that is the 8 bpc NEON inverse transforms only (libavif-rs ADR 0062,
  `64ce28a5`); the entropy decoder (msac) and the loop filter are not rebuilt
  on `main`, and nothing is rebuilt for x86-64, where the port runs its
  scalar translation.

platform, unrestricted or not. Decoded RGB was identical across all eight
candidates on every host (below).

## Correctness side checks

Recorded by the scripts, not a gate here (the gate is D4/D8 in the
repository's oracle tests).

- **JPEG:** the scalar original, the SIMD original and the port give the
  same checksum for every input on every host.
- **WebP:** 28 of 28 checks identical on every host.
- **JPEG XL lossy encode (12 MP, e7 d1):** the port's codestream is now
  byte-identical to the original's **SIMD** build, one thread and all
  threads, on all five hosts (2,057,281 bytes on x86-64, 2,057,280 on
  ARM64). On November 13, with the encoder on its scalar path, it was
  identical to the scalar reference instead. The scalar reference (2,057,281
  bytes, `d65d5c60e5aa…`) differs from the SIMD build on every host, as
  before.
- **JPEG XL lossless encode (e2):** as on November 13, the port's codestream
  differs from cjxl's with the flags the script uses; scalar and SIMD cjxl
  agree with each other. Not attributed here.
- **JPEG XL decode:** port against jxl-oxide F32 maximum difference
  1.66e-4 to 1.72e-4 (VarDCT) and 6e-8 (lossless).
- **AVIF encode:** on both x86-64 hosts the port's file is byte-identical to
  both C builds. On macOS ARM64 scalar and SIMD libaom agree with each other
  and the port differs from both, as on November 13 (the likely cause there,
  the C builds' default floating-point contraction, is still not verified).
- **AVIF decode:** decoded RGB identical across every candidate (scalar,
  SIMD and threaded libaom, the port, stock dav1d at both scopes and with
  threads, and the dav1d port) on every host.

## Limits of this evidence

- **One run, shared VMs.** Linux spreads are mostly within a few percent;
  the macOS VM (3 vCPUs, 1-minute load averages 1.6–28.6 during samples)
  has the widest spreads and is the least reliable platform.
- **CPU models differ between jobs.** GH x86-64 gave the AVIF and JPEG XL
  jobs an Intel Xeon 6975P-C, the JPEG job an AMD EPYC 9V45 and the WebP
  job an Intel Xeon Platinum 8370C; BS x86-64 ran JPEG XL on AMD EPYC and
  the rest on Intel Xeon. Ratios are within one job; absolute times across
  codecs or against the November 13 record are not comparable.
- **"Scalar" is not "no vector instructions"** for libjpeg-turbo, libwebp
  and libaom (compiler auto-vectorization at `-O3`); it is for libjxl. See
  the method of the November 13 record.
- **The port side is not restricted.** The port runs its default dispatch.
- **Thread columns use what the original offers:** two threads for libwebp
  `-mt`; all 4 (3 on macOS) vCPUs for libjxl and libaom. AVIF encode (c) uses
  autotiling, so it codes a different bitstream.
- **Two photographs; one 12 MP sample per lossy JPEG XL encode** (3
  repetitions). AVIF encode at 12 MP only. No AVIF on Linux ARM64.

## Method

Unchanged from the [record of 2026-11-13](v1.0-three-column-2026-11-13.md#method):
workflow [bench-v1-perf.yml](../../.github/workflows/bench-v1-perf.yml), job
`codec`; scripts in [scripts/bench/ci-perf/](../../scripts/bench/ci-perf/);
every sample a fresh process, one warm-up round and 7 repetitions (3 for the
12 MP lossy JPEG XL encode, no warm-up), order alternating; medians of each
program's own timer around the core operation; the columns built as that
record's table "How each column is built" describes. The AVIF decode job
adds the context columns above (`5e187eb4`).
