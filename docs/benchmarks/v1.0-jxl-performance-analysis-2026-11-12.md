# JPEG XL performance analysis, 2026-11-12 (indicative; loaded host)

**Question.** Where do the time and memory of the workspace JPEG XL port
(`codecs/libjxl-rs`, used through `crates/ferrisma-jxl-decoder` and the
engine) go, how does that compare with the pinned C++ libjxl it was ported
from, and what would close the gap?

**Every timing in this record is indicative and was taken on a loaded host**
(Apple M1 Ultra shared with other agents; the 1-minute load average is given
per table and ranged from about 5 to 29). Profile *shares* and interleaved
A/B *ratios* are the primary evidence; absolute release-grade numbers come
from a separate CI benchmark run. Byte sizes, hashes, RSS and test results
are not load-sensitive.

## Summary

1. **The gap is almost entirely scalar inefficiency in the port, not missing
   SIMD or threads.** On a typical lossy file (cjxl `-e 7 -d 1`, XYB, EPF and
   Gaborish on), the port takes 7.4× (3.4 MP) and 7.0× (24 MP) the time of
   the *same-arithmetic* scalar C++ build (`HWY_COMPILE_ONLY_SCALAR`, the
   oracle's configuration). Highway SIMD makes the original only a further
   2.2–2.3× faster, and its thread pool another 2.4–5.7×. Of the 870 ms gap
   between the port and jxl-oxide on the 3.4 MP file, about 858 ms (99 %)
   is port-versus-scalar-original overhead.
2. **The earlier 3.2× "VarDCT" figure understates the gap for real lossy
   files.** The only VarDCT input used so far was a JPEG reconstruction
   (YCbCr, no EPF/Gaborish/XYB). On cjxl-encoded lossy files the port is
   8.1–8.2× slower than jxl-oxide, and 15–17× slower than single-threaded
   C++ SIMD.
3. **Three mechanical causes explain most of the port overhead**, and all
   can be removed without changing a single floating-point operation:
   (R1) owner-relative row lookups resolved per sample, through a
   non-inlined, bounds-checked `Plane::row_at` (up to 39 lookups per sample
   in EPF); (R2) Highway-scalar arithmetic emulated by `#[inline(never)]`
   per-element helpers (kept for NaN-payload operand order), which makes the
   XYB stage 22× and YCbCr/chroma upsampling 17–19× the original; (R3) a
   runtime-size recursive DCT/IDCT where the original uses compile-time
   templates (IDCT 5–7× the original; it also dominates the encoder).
4. **The 1.8× RSS on lossless decode was an eager-zeroing artifact**, not a
   design difference: the port memset every plane from the default memory
   manager, making the full-frame modular `i32` channels resident (12 B/px)
   that the original allocates and drops untouched. Fixed in this record
   (prototype 2): 24 MP lossless decode RSS 618.5 → 322.6 MB; the C++ `djxl`
   uses 322.5 MB on the same file.
5. **The lossless writer uses about 70–76 B/px, not 28.** The engine
   reserves 28 B/px, but the admitted one-shot ("buffering 0") profile holds
   tokens for all groups (about 24 B/px) plus input copies. The C++ original
   in the same one-shot mode uses the same (79 B/px measured); its default
   streaming mode uses 27 B/px at 24 MP.
6. **Prototyped and measured (bit-identical outputs, all 1013 port tests
   against the C++ oracle and the conformance corpus pass):** row-span
   hoisting in Gaborish/EPF (−20 % lossy decode at 3.4 and 24 MP) and in
   YCbCr/chroma upsampling (−25 % JPEG-reconstruction decode); lazily zeroed
   default allocations (lossless decode memory at C++ parity).

## Method

- **Host and builds:** see [environment.txt](evidence-2026-11-12-jxl-perf/environment.txt).
  Rust: release profile with `CARGO_PROFILE_RELEASE_DEBUG=line-tables-only`,
  built from the repository root as the engine builds (auto-vectorization on;
  the port's own `.cargo/config.toml` disables it only for builds from its
  directory). C++: the pinned libjxl `a16d32d0` built twice with CMake
  ([cxx_configure.sh](evidence-2026-11-12-jxl-perf/tools/cxx_configure.sh)):
  `cxx-scalar` adds `-DHWY_COMPILE_ONLY_SCALAR=1`, exactly the arithmetic
  configuration of the port's differential oracle (`tools/oracle/CMakeLists.txt`);
  `cxx-simd` uses Highway's default dispatch (NEON here). `djxl`/`cjxl`
  stand in for the oracle, whose hex protocol has no whole-image request.
  The oracle itself was built by `tools/check.py --stage test` for the
  correctness runs below.
- **Inputs** (hashes in environment.txt): `flower-recon`, the 2268×1512
  JPEG-reconstruction JXL of the earlier records; `flower-d1e7` and
  `mountain-d1e7` (6000×4000), made by the pinned C++ `cjxl -d 1 -e 7` from
  the flower JPEG and the EXIF-stripped mountain photo, giving the first
  realistic lossy XYB inputs; `flower-lossless` and `mountain-lossless`, the
  workspace encoder's lossless effort-2 files of the v1.0 baseline.
- **Harnesses:** [jxl_perf_probe.rs](evidence-2026-11-12-jxl-perf/tools/jxl_perf_probe.rs)
  (copy into `crates/ferrisma-jxl-decoder/examples/` to build): `decode`
  (wrapper `inspect` + `decode_into`, F32, optional FNV-1a hash of every
  sample), `lossy` (public encoder API, effort/distance, one thread),
  `lossless` (`LosslessThunderConfig`, the engine sink's profile), and a
  counting global allocator (`JXL_PROBE_ALLOC=1`) that logs every heap block
  of at least 1 MiB. jxl-oxide via `jxl_decode_compare`. Engine via the
  release CLI ([cli_runs.sh](evidence-2026-11-12-jxl-perf/tools/cli_runs.sh)).
- **Timing:** [ab.py](evidence-2026-11-12-jxl-perf/tools/ab.py): fresh process
  per sample under `/usr/bin/time -l`, one warm-up round, 5 repetitions
  (3 for the encoder), candidate order alternating per repetition; the
  internal decode/encode timer (the C++ tools' own MP/s) per decode; median
  and min–max. Raw samples in [timing/](evidence-2026-11-12-jxl-perf/timing/).
- **Profiles:** `samply 0.13.1` (no root), 1 kHz, presymbolicated; each
  summarized by [prof_summary.py](evidence-2026-11-12-jxl-perf/tools/prof_summary.py)
  into top-15 exclusive/inclusive outer symbols and stage shares. A sample's
  stage is the innermost frame that matches a stage pattern
  ([stages.json](evidence-2026-11-12-jxl-perf/tools/stages.json)). Rust
  inlines aggressively, so "outer symbol" means the non-inlined function;
  identical-code folding can attribute a tiny helper to a same-bodied twin
  (for example `stage_noise::promote`). Per-stage milliseconds below are the
  stage share times the interleaved median of the same binary and input.
  Trimmed outputs in [profiles/](evidence-2026-11-12-jxl-perf/profiles/).

### Root causes

- **R1, per-sample row resolution.** The port replaced the original's row
  pointers with owner-relative `Row` descriptors (`RowBuffers::row(row.offset(x))[0]`)
  and resolves them for every tap: an assertion, a plane slice, a
  non-inlined `row_at` with two assertions and a checked add, then a bounds
  check. Gaborish does this 9 times per sample, EPF pass 0 up to 39 times,
  vertical chroma upsampling 5, YCbCr 6, the modular predictor loop several
  per pixel. Forcing `#[inline(always)]` on the accessors made decode *slower*
  (+8 % recon, +28 % XYB; −5 % lossless), so the fix is to resolve spans once
  per row, not to inline the lookup.
- **R2, per-element out-of-line arithmetic.** To keep Highway's scalar
  semantics (products widened to `f64`, and the operand order that decides
  which NaN payload survives), every `add`/`mul`/`promote`/`product` in the
  render stages and `xyb_to_rgb` is `#[inline(never)]`. Each sample of the
  XYB stage makes about 25 such calls. This is the main remaining cost of
  XYB (22×), EPF and Gaborish after prototype 1, and of YCbCr/chroma.
- **R3, runtime-size transforms.** `dct::idct_1d_in_place`/`dct_1d` recurse
  on a runtime `n` with slice offsets; the original instantiates
  `IDCT1DImpl<N, 1>` per size, which the compiler fully unrolls. IDCT is
  5.3–7.2× the original in decode, and DCT/IDCT inside the AC-strategy
  search dominate the encoder (section 4).
- **Not causes:** AC entropy decoding is at parity (1.0–1.3×), and so are
  allocation and copies; the wrapper adds no copy (`wrapper_copied_bytes=0`,
  the decoder writes straight into the engine's budgeted buffer).

## 3. Memory

### Lossless decode: 1.8× RSS (fixed by prototype 2)

The probe's allocation log for flower-lossless (3,429,216 px) shows, in
order: the 3.2 MB input, the 41.15 MB F32 output (12 B/px), then three
13.74 MB blocks (4.0 B/px each): the full-frame modular `i32` channels
created by global-info decoding. Peak heap 86.8 MB. The original allocates
the same channels and releases them in `MaybeDropFullImage` (the port mirrors
that logic exactly), but leaves them untouched, so they never become
resident. The port's `AlignedMemory::create` instead zeroed every block from
a memory manager with an explicit `write_bytes` after the default callback's
uninitialized `alloc`, touching every page.

Prototype 2 requests the identical block through the global allocator's
zeroing path (calloc) when the manager's allocation callback is the default
one. Results (indicative; load 11):

| Case | before | after | C++ |
| --- | ---: | ---: | ---: |
| decode RSS, flower-lossless 3.4 MP | 94.5 MB | 52.3 MB | 55.7 MB |
| decode RSS, mountain-lossless 24 MP | 618.5 MB | 322.6 MB | 322.5 MB |
| decode time, mountain-lossless 24 MP | 1,315 ms | 1,289 ms | 1,036 ms (scalar) |
| engine CLI RSS, 24 MP lossless → WebP | 640 MB | 346 MB | – (jxl-oxide lane: 371 MB) |

What remains per pixel at 24 MP: the F32 output frame (12 B/px, 288 MB,
engine-managed) dominates. jxl-oxide's adapter streams rows, so the engine
manages 31 MB for it against 319 MB for the port (unchanged by this fix).

### Lossless encode: 28 B/px reserved, about 70 B/px used

`src/jxl_sink.rs` reserves 4 B/px (RGBA8 frame) plus `known_codec_frame_bytes`
= 12 (padded `Image3<f32>`) + 12 (modular `i32` channels) = 28 B/px. The
allocation log of the same profile through `LosslessThunderConfig`
(flower, 3.4 MP) shows: a second 3 B/px copy of the input, six 4 B/px planes
(F32 color and `i32` channels; the F32 planes are freed after conversion),
then one 1.57 MB token vector per 256×256 group and channel set (8 B per
sample, about 24 B/px for all groups), then per-group bit-writer storage.
Peak heap 238.9 MB = 69.7 B/px. Measured RSS:

| Writer, lossless effort 2 | RSS | per pixel |
| --- | ---: | ---: |
| port, flower 3.4 MP (probe) | 260 MB | 75.8 B/px |
| engine CLI, mountain JPEG → JXL 24 MP | 1,707–1,719 MB | 71–72 B/px |
| C++ `cjxl --buffering=0` (one-shot, the port's profile), flower | 273 MB | 79 B/px |
| C++ `cjxl` default buffering, flower / mountain 24 MP | 187 MB / 651 MB | 55 / 27 B/px |

So the port matches the original's one-shot profile; the engine's
reservation (672 MB at 24 MP) understates the real peak by about 1 GB, and
the original's default chunked buffering is what reaches 27 B/px. Encode
time is at parity: port 203 ms against C++ scalar one-shot 185 ms (flower).

### Lossy XYB decode

Port 352 MB, C++ 345 MB, jxl-oxide 611 MB at 24 MP: no memory issue.

## 4. Encoder (lossy e7 d1 through the public API)

Flower 3.4 MP, one thread (load 5–8): port 12,722 ms (prototypes: 12,097 ms,
byte-identical output, 464,590 bytes), C++ scalar 3,416 ms (3.7×), C++ SIMD
995 ms (12.8×), C++ SIMD 8 threads 211 ms (60×). Profile stage shares
(innermost match; port 14.5 s sampled run, C++ scalar 3.6 s):

| Stage | port | C++ scalar | ratio |
| --- | ---: | ---: | ---: |
| AC-strategy search incl. its DCT/IDCT | 10.9 s | 2.6 s | 4.2× |
| AR heuristics (3 decode roundtrips, same as the original at d ≤ 4.5) | 2.87 s | 0.23 s | 12× |
| CfL heuristics | 0.19 s | 0.48 s | 0.4× |
| adaptive quantization, XYB, tokens, inverse Gaborish | 0.49 s | 0.28 s | 1.7× |

Top exclusive: `dct::dct_1d` 25.1 %, `enc_ac_strategy::estimate_entropy`
17.3 %, `dct::idct_1d_in_place` 16.6 %, `idct_columns` 5.7 %, Gaborish 5.4 %,
EPF 4.4 %, `dct_columns` 4.0 %. The AR heuristics run three full roundtrip
decodes in both implementations; in the port each costs about 0.96 s (C++
about 77 ms) because they go through the same slow render stages, so every
decode-side fix also speeds up the encoder. The transform fix (R3) is the
largest encoder lever.

## 5. Prototypes in this record

All three keep every floating-point operation and its order; they only move
address computation or change how zero pages are obtained. Each was checked
for bit-identical F32 output (FNV-1a over all samples) on flower-recon,
flower-d1e7 and mountain-d1e7, and byte-identical encoder output.

| Commit | Change | Measured (interleaved; indicative) |
| --- | --- | --- |
| `91e51ec0` perf(jxl): resolve Gaborish and EPF row spans once per row | spans per row, outputs staged in a scratch row | flower-d1e7 1,008 → 802 ms (−20 %); mountain-d1e7 7,640 → 6,044 ms (−21 %); recon unchanged; engine CLI XYB decode 1,000 → 795 ms, 24 MP 7.59 → 6.02 s; lossy encode 12.72 → 12.10 s (−5 %) |
| `1166ebe0` perf(jxl): keep default-allocator planes lazily zeroed | calloc for default-manager blocks | lossless RSS at C++ parity (section 3); −2 % lossless time |
| `5e60a6fa` perf(jxl): resolve YCbCr and chroma upsampling row spans once per row | same technique; YCbCr uses the existing `three_rows_mut` | flower-recon 274 → 205 ms (−25 %) |

Verification: `python3 tools/check.py --stage test` (builds the pinned C++
oracle, then all checked-profile tests): 1013 passed, 0 failed, after the
first two commits and again (1013 passed, 0 failed) with all three. Engine tests with
`--features cli,jpeg-xl-write`: 236 passed; `ferrisma-jxl-decoder`: 7 passed.
`tools/conformance/run.sh`: level 10 27/27, level 5 24/24, wrapper
`--lax` 32/40 (the 8 by-design rejections of ADR-0032), unchanged.

Combined, the port's flower-d1e7 decode is about 800 ms: still 5.8× jxl-oxide.

## 6. Ranked solutions

Gains are per-input estimates from the stage tables above, assuming the
fixed stage reaches the C++ scalar time for the same work; they do not add
up linearly. "Exact" means no floating-point operation or order changes, so
the byte-exact oracle gates hold by construction.

| # | Problem → cause | Fix | Expected gain (basis) | Risk to exact/conformance gates | Effort | Class |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | Render stages 11–22× the original → R1 per-sample row lookups | Resolve spans once per row in every stage (done: Gaborish, EPF, YCbCr, chroma). Remaining: XYB, FromLinear, write, noise, splines, patches, upsampling; modular predictor loop and inverse RCT | done −20 % lossy, −25 % recon; remaining: lossless −10–15 % (row_at ≈ 18 % of decode), small on lossy | none (exact; tests + conformance) | small per stage | b′ (port-internal, mechanical) |
| 2 | XYB 22×, residual EPF/Gaborish/YCbCr cost → R2 per-element `#[inline(never)]` helpers | Move the out-of-line boundary from the element to the row: one non-inlined row kernel per stage that applies the same element operations in the same operand order (both operands stay opaque loads, as today) | lossy decode about −40 % more (XYB 201 → ~10–20 ms, EPF 165 → ~25–40, Gaborish 90 → ~15); recon −20 % | low–medium: exact arithmetic, but NaN-payload order depends on codegen; covered by the existing NaN parity tests and #214's contraction maps | medium | b′ |
| 3 | IDCT 5–7×, encoder DCT-bound → R3 runtime-size recursion | Const-generic `idct_1d::<N>`/`dct_1d::<N>` mirroring `IDCT1DImpl<N,1>`, same operation order (`idct_add` boundary handled as in 2) | decode −15 % (IDCT 182 → ~35–50 ms); encoder roughly −40–55 % (DCT/IDCT ≈ 65 % of encode samples) | none if the operation order is unchanged | medium | b′ |
| 4 | Every crop decodes and budgets the full frame → no region API (#197) | Group-granular region decode: decode DC and global sections fully, AC groups and render only groups that intersect the crop plus a one-group halo for EPF/Gaborish | center crop about 35 % of full time (jxl-oxide's measured ratio) and crop-sized buffers | medium: not oracle-backed (libjxl has no region decode); must equal the full-frame crop exactly | large | c |
| 5 | Crop memory = full F32 frame | Adapter: register `jxl_decoder_set_image_out_callback` and keep only the crop's rows | managed memory ∝ crop (24 MP center crop: 288 → 72 MB F32); time unchanged | low (port callback path is parity-tested) | small–medium | b |
| 6 | Engine holds a full F32 frame for 8-bit integer sources (12 B/px) | Adapter: for lossless/`uses_original_profile` 8-bit sources request `UINT8` output (exact for k/255 samples) and emit `DecodedRow::U8` | 24 MP frame 288 → 72 MB; engine RSS ~346 → ~130 MB (estimate) | medium: changes the engine path (U8 instead of F32); needs golden review and an ADR-0032 note | small–medium | b |
| 7 | Lossless writer peak 70 B/px vs 28 reserved | (a) reserve the measured one-shot peak (about 72 B/px incl. tokens); (b) admit the original's chunked buffering for large images | (a) honest budget, no speed change; (b) 27 B/px at 24 MP (C++ measured) | (a) none; (b) changes bytes, needs oracle evidence for the new profile | (a) small; (b) medium | b / encoder |
| 8 | No SIMD (#96) | Translate the Highway kernels after 1–3 | from the original: scalar → SIMD 2.3× lossy, 1.6× recon, 1.05× lossless | high: SIMD changes FMA contraction and reduction order, so the scalar oracle no longer applies; needs a SIMD-built reference and #215's x86-64 conformance (`alpha_premultiplied` at 80 % of its limit) | large | a |
| 9 | No thread speedup (#100) | Concurrent `RunOnPool` bodies with thread-safe owners | from the original: 5.7× (24 MP lossy), 6.8× (24 MP lossless) on 8 threads | medium: libjxl output is thread-count independent by design; needs the TSan gate the issue names | large | a |
| 10 | Encoder serial (#106) | Concurrent encoder runner | from the original: 4.7× at 8 threads (995 → 211 ms) | medium (as 9) | large | a |

Rejected: `#[inline(always)]` on the row accessors (measured slower, section 2).
Not worth it: the second header parse in `decode_into` (inspect + decode
each create a decoder; well under 1 % of a decode).

Order of work: 1 (finish) → 3 → 2 give the largest exact gains and would
bring single-thread lossy decode from about 800 ms to roughly 150–250 ms
(near C++ scalar and jxl-oxide); then 9, then 8. 5 and 7a are small and
independent; 4 decides the crop gap.

## 7. Existing issues that close the gap

Shares refer to the flower-d1e7 gap to jxl-oxide (port base 1,008 ms vs
138 ms single-thread, 870 ms) unless stated.

| Issue | Share of the gap it addresses (basis) | Still missing beyond it | Recommendation |
| --- | --- | --- | --- |
| #96 SIMD dispatch parity | About 10 % on its own: the original's scalar → SIMD step saves 84 ms of 870 (C++ scalar 151 → SIMD 66 ms). A full translation would rewrite the hot kernels and thereby also remove R1–R3 *in those kernels*, but it is the most expensive and riskiest way to get that | a SIMD-aware parity reference; x86-64 conformance (#215); contraction maps (#214) | Do right after solutions 1–3; do not pull into v1.0 |

## Limits of this evidence

- Loaded host (load 5–29), one machine (ARM64/NEON), no idle-host or x86-64
  run. Ratios between candidates measured in the same interleaved run are
  more robust than absolute numbers; the first decode table ran at higher
  load than the A/B tables (port flower-d1e7 1,121 versus 1,008 ms).
- Two photo-sized lossy inputs, both from one encoder setting (`-e 7 -d 1`);
  other distances change EPF iterations and AR heuristics. Lossless inputs
  come only from the workspace encoder's effort-2 profile.
- Stage attribution uses outer symbols and innermost-pattern matching; the
  C++ inlines the modular entropy and predictor into one function, so only
  their sum compares. Expected gains in section 6 are estimates, not
  measurements, except where a prototype row says "measured".
- The C++ comparison uses `djxl`/`cjxl` built from the pinned source with the
  oracle's scalar define, not the oracle executable itself.
- The port's own `.cargo/config.toml` disables auto-vectorization for builds
  from its directory (sNaN fidelity); the engine and these measurements build
  from the root with vectorization on. The external conformance run builds
  the codec binary from the port directory and the wrapper from the root, so
  both configurations pass, but the parity tests run only the former.

## 8. Crop-sized buffering through the image-out callback (2026-11-12)

*Added after the record above; indicative, loaded host (1-minute load
11.2–11.9 for the lossless table, 13.9–16.5 for the orientation table).*

Solution 5 is implemented ([ADR-0032](../adr/0032-jpeg-xl-workspace-decoder-input.md#region-sized-retained-buffer-2026-11-12)):
the wrapper's `decode_region_into` registers the port's image-out callback
and keeps only the requested upright rows and columns; the adapter uses it
for every request smaller than the frame and the unchanged output-buffer
path (`decode_into`) for full-frame requests. The codec still reconstructs
the full frame, so decode time is not expected to drop beyond skipped copies,
and reports keep `FullFrameFallback` and full-frame `CodecWork`.

Solution 6 (UINT8 output for 8-bit sources) was evaluated and **not
adopted**: the port's 8-bit writer applies libjxl's ordered dither before
rounding, the public API cannot identify the subset whose samples are exact
multiples of 1/255, and a `U8` source changes the engine path. The reasoning
is in ADR-0032.

**Method.** Release CLI built from the repository root before (`aaf768fa`)
and after the change; `--use-rendered-icc --budget-mb=2048
--encoder-threads=1 --transform-threads=1`, WebP output; one warm-up round,
then 4 repetitions, fresh process per sample, before/after order alternating
per repetition ([crop_buffer_ab_crop.sh](evidence-2026-11-12-jxl-perf/tools/crop_buffer_ab_crop.sh),
[crop_buffer_ab_orient.sh](evidence-2026-11-12-jxl-perf/tools/crop_buffer_ab_orient.sh),
[crop_buffer_summarize.py](evidence-2026-11-12-jxl-perf/tools/crop_buffer_summarize.py);
raw samples in [timing/crop-buffer/](evidence-2026-11-12-jxl-perf/timing/crop-buffer/)).
Inputs: the lossless effort-2 flower (3.4 MP), dog (12.2 MP, upright
3024×4032) and mountain (24 MP) files of the [v1.0 baseline](v1.0-baseline-2026-11-12.md)
(hashes there), and `mountain-o6-recon.jxl` (6,322,862 bytes, SHA-256
`b362cd6e…852577c`), made by the pinned C++ `cjxl` (default lossless JPEG
transcode, effort 7) from the baseline's `jpeg24-o6.jpg` (`02ae043c…`): a
24 MP VarDCT file with EXIF orientation 6, whose upright output reaches the
callback one pixel per call. Center crops are half the upright width and
height. "Managed" is the engine's peak managed bytes; RSS is
`/usr/bin/time -l` maximum resident set size.

| Input, request | decode ms before → after (median) | managed MB before → after | max RSS MB before → after | known full frames |

| flower 3.4 MP, full | 183 → 187 | 52.3 → 52.3 | 59.1 → 59.6 | 1 → 1 |
| flower 3.4 MP, center crop | 185 → 179 | 46.9 → 16.0 | 57.7 → 27.1 | 1 → 0 |
| dog 12.2 MP, full | 633 → 630 | 173.6 → 173.6 | 188.4 → 188.5 | 1 → 1 |
| dog 12.2 MP, center crop | 629 → 613 | 158.4 → 48.6 | 176.6 → 66.6 | 1 → 0 |
| mountain 24 MP, full | 1,297 → 1,299 | 318.8 → 318.8 | 346.7 → 346.0 | 1 → 1 |

| mountain o6 recon 24 MP, center crop | 1,737 → 1,716 | 306.8 → 90.8 | 333.7 → 117.3 | 1 → 0 |

Reading:

- **Memory follows the request.** At 24 MP the center crop's managed peak
  falls by 216 MB, exactly the 288 MB F32 frame minus the 72 MB F32 crop the
  analysis estimated; process RSS falls by the same amount (343 → 126 MB),
  because with lazily zeroed planes (prototype 2) the codec's own lossless
  state is small. The VarDCT orientation-6 file behaves the same (334 →
  117 MB RSS). A 24 MP JPEG XL crop now fits the CLI's default 256 MB budget;
  before, it failed with "managed buffer needs 288000000 bytes".
- **Full-frame reads are unchanged by construction** (same buffer path; the
  differences are within the min–max ranges in the raw samples). In an
  earlier run in which full-frame reads also went through the callback, the
  orientation-6 full read was about 4 % slower (1,707 → 1,777 ms, ranges not
  overlapping), which is why full-frame requests keep the buffer path.
- **Crops are 1–3 % faster**, from skipping the copy of rows and columns
  outside the region; the full reconstruction remains (solution 4, #197).
- **Outputs are byte-identical** before and after for full and crop
  requests on flower, dog (including an odd-offset crop) and the
  orientation-6 file.

Verification for this change: `ferrisma-jxl-decoder` tests (11, including
callback-versus-buffer bit equality on 24 fixtures, region validation, an
injected callback panic), the engine's JPEG XL adapter, orientation, color
and decoder-work tests, and `tools/conformance/run.sh`: level 10 27/27,
level 5 24/24, wrapper `--lax` 32/40 through the callback path (the eight
rejections are the by-design ones: five animations, three unsupported
layouts).
