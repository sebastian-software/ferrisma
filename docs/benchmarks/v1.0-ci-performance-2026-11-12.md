# v1.0 CI performance: stage breakdown and port versus original, 2026-11-12

This record moves the indicative [v1.0 baseline](v1.0-baseline-2026-11-12.md)
(a loaded M1 Ultra) onto otherwise idle hosted runners. It answers two
questions: where the engine's time goes per input and output format, and how
far each of the four workspace codec ports is from the pinned C/C++ original
it translates, on the same machine in the same job. It is a measurement, not a
release-grade performance claim: hosted runners are shared virtual machines,
and the limits in section 5 apply to every number. Sections 1–5 record
commit `93c5281f`; a rerun after the first performance fixes (`3051f042`)
is compared in
[the last section](#after-the-performance-fixes-commit-3051f042-2026-11-12).

## Runs, hosts and method

- **Source:** integration commit `93c5281f` plus the measurement tooling of
  this record (`scripts/bench/ci-perf/`, the workflow
  `.github/workflows/bench-v1-perf.yml`, and four small example binaries).
  No engine or codec library code was changed. The runs used branch commits
  `bcd79f36` and `d924b3ee`, which differ only in the workflow's runner
  matrix; the scripts in this commit add the split decode part and partial
  records, which the recorded runs did not use.
- **Runs** on the throwaway branch `bench/v1.0-perf`:
  [43271303915](https://github.com/sebastian-software/ferrisma/actions/runs/43271303915)
  (GitHub-hosted `ubuntu-24.04`, `ubuntu-24.04-arm`, `macos-15`) and
  [43273895209](https://github.com/sebastian-software/ferrisma/actions/runs/43273895209)
  (Blacksmith `blacksmith-4vcpu-ubuntu-2404` and `-arm`). The one-job
  Blacksmith probe [43271303545](https://github.com/sebastian-software/ferrisma/actions/runs/43271303545)
  was picked up within seconds (AMD EPYC, 4 vCPUs, one thread per core).
- **Hosts** (per job in `host-before.txt` of each evidence directory):

  | Label | Runner | CPU seen | vCPUs |
  | --- | --- | --- | ---: |
  | GH x86-64 | `ubuntu-24.04` | AMD EPYC 9V45 (Zen 5), AMD EPYC 7763 (Zen 3) or Intel Xeon 6975P-C, varying per job; 2 cores × 2 SMT threads where `lscpu` shows it | 4 |
  | GH ARM64 | `ubuntu-24.04-arm` | Neoverse-N2 | 4 |
  | GH macOS ARM64 | `macos-15` | Apple M1 (Virtual), macOS 15.8.2 | 3 |
  | BS x86-64 | `blacksmith-4vcpu-ubuntu-2404` | AMD EPYC (family 26, Zen 5), one thread per core | 4 |
  | BS ARM64 | `blacksmith-4vcpu-ubuntu-2404-arm` | Ampere-1a, one thread per core | 4 |

- **Toolchain:** the pinned `rustc 1.100.0-nightly (5a2be9f5f 2026-09-06)`,
  repository release profile, no `RUSTFLAGS`. C/C++ originals with Clang 18
  (Linux; GCC 13 for libjpeg-turbo, libwebp and libavif) or Apple Clang 17.
- **Runner:** [run_interleaved.py](../../scripts/bench/ci-perf/run_interleaved.py).
  Every sample is a fresh process under `/usr/bin/time` (`-v` on Linux, `-l` on
  macOS). One warm-up round, then 7 repetitions; within a repetition each
  candidate runs once and the order alternates forward and reversed. C and port
  candidates of one operation are in the same plan, so they interleave on the
  same machine. Tables give the median; min–max and every raw sample are in
  the JSON evidence. Load averages before and after each sample are recorded.
- **Inputs:** two real photographs as 8-bit RGB masters: `photo12` is the
  libavif test photograph `dog_exif_extended_xmp_icc.jpg` (4032×3024, stored
  order) and `photo24` the verified `mountain` photograph of
  [corpus-photos.json](../../scripts/bench/corpus-photos.json) (6000×4000),
  both decoded once with `djpeg` ([make_masters.sh](../../scripts/bench/ci-perf/make_masters.sh)).
  Every derived input is encoded from these masters, so all formats carry the
  same pixels and no ICC profile. The "camera" rows use the original JPEG files
  (dog: EXIF orientation 6 and an sRGB ICC profile, rendered with
  `--use-rendered-icc`; mountain is accepted with `--assume-srgb`).
- **Engine runs** ([engine.py](../../scripts/bench/ci-perf/engine.py)): the
  release CLI (`--features cli,jpeg-xl-write`; on Linux ARM64, where the
  generated libavif/AOM code does not build, the same `cli::run` through
  `examples/cli_subset.rs` without AVIF input and the AOM writer). Part
  *decode* transcodes every input to lossy WebP (the cheapest encoder, constant
  across rows); part *encode* transcodes the JPEG q90 input to AVIF (default
  workspace AOM writer and `--avif-encoder=rav1e`), lossy WebP and lossless
  JPEG XL (effort 2, the only admitted output profile). Each runs resized to
  2048 px wide and not resized, with `--transform-threads=1` (t1) and `=0`
  (tN). `--encoder-threads` follows the thread mode for AVIF; the WebP and
  JPEG XL writers are serial and accept only 1. Stage times are the CLI
  `report:` medians; stages add up, so an input × output cell is decode(input)
  + transform + encode(output) from the two parts.
  System encoders made the inputs (Ubuntu: libjpeg-turbo 2.1.5, cwebp 1.3.2,
  cjxl 0.7.0, avifenc 1.0.4; macOS: Homebrew builds; versions per job in
  `engine-inputs-*.json`): JPEG `cjpeg -quality 90`, WebP `cwebp -q 75` and
  `-lossless`, JPEG XL `cjxl -e 7 -d 1` (VarDCT) and `-e 7 -d 0`, AVIF
  `avifenc -q 60 -s 6` (8-bit 4:2:0).
- **Port versus original** (`codec_<name>.sh`): each script builds the pinned
  original from the repository's own copy with upstream release flags (CMake
  `Release`, default SIMD/dispatch), builds the port's example with the
  release profile, creates inputs with the original's encoder, and times both
  through the interleaved runner. "internal" is each program's own timer around
  the core operation (file I/O outside on both sides); process wall time is
  also recorded. Specifics:
  - JPEG: libjpeg-turbo 3.2.1 (`7b499378`, `tools/build_oracle.py` variant
    `simd`: Release, `WITH_SIMD=1`, keeps `-ffp-contract=off`), its bench probe
    `tools/oracle/probes/wp9/bench.c` against the port's `examples/bench.rs`;
    3 full decodes to RGB from memory per process; the FNV-1a checksums of C
    and port are identical for all inputs on all hosts.
  - WebP: libwebp 1.6.0 (`4fa21912`), CMake Release with SIMD, `dwebp -ppm`
    and `cwebp -q 75` / `-lossless` (internal timer from their `-v` output)
    against `codecs/libwebp-rs/examples/cli_bench.rs`. `mt` is libwebp's `-mt`
    (at most two threads). Encoded files and decoded pixels are identical
    between C and port in every case.
  - JPEG XL: libjxl `a16d32d0` (v0.12 snapshot), CMake Release with Highway
    dynamic dispatch, `djxl --disable_output` (F32) and `cjxl -e 7 -d 1`
    against `crates/ferrisma-jxl-decoder/examples/jxl_decode_compare` (port and
    jxl-oxide, F32) and the new `codecs/libjxl-rs/examples/encode_lossy.rs`
    (the public encoder at effort 7, distance 1, cjxl's PPM call sequence). The
    port encoder is serial; its encode runs only at 12 MP with 3 repetitions
    (one sample takes about 45–70 s).
  - AVIF: libavif 1.4.2, libaom 3.15.2, dav1d 1.5.4 from the tracked snapshots,
    CMake/meson release with SIMD and asm. Encode: `tools/encode_still.c`
    against `codecs/libavif-rs/examples/encode_still.rs` at the engine's
    defaults (10-bit 4:4:4, quality 75, speed 6, `maxThreads` = threads,
    autotiling when threads ≠ 1), timing `avifEncoderWrite` only, 12 MP only.
    Decode: a small C libavif driver with libaom or dav1d against the new
    `crates/ferrisma-avif-read/examples/decode_still.rs` (the engine's reader:
    libavif port with its AOM decoder, one thread), timing create + parse +
    decode + YUV→RGB. Decoded RGB is identical across C+aom, C+dav1d and the
    port on every host.

## 1. Where the time goes (engine stages)

Medians in ms from the CLI report. The [appendix](#appendix-generated-tables)
has every size, resize and thread mode on all five hosts. "Transform" is
orientation, color handling and resize together. Blacksmith jobs ran on one
CPU model per architecture; GitHub-hosted x86-64 jobs landed on three
different CPU models, so absolute GH x86-64 values are not comparable across
tables.

**Input side, 24 MP, resized to 2048 px wide, one thread** (decode /
transform; the lossy WebP encode adds 0.3–0.7 s to every row):

Readings:

- **The encoder dominates every AVIF output.** With the default AOM writer
  the encode stage is 83–97 % of wall at 24 MP; without a resize it is
  11.4 s on one thread and 3.5 s on all four cores (BS x86-64). rav1e at
  speed 6 took 1.9–2.9× the AOM encode time on x86-64 and 1.3–1.7× on macOS
  ARM64 (CLI default quality for both; no quality matching, so this is not an
  efficiency comparison).
- **The default JPEG XL reader is the largest input-side cost.** libjxl-rs
  spends 7.3–10.4 s on a 24 MP VarDCT file where jxl-oxide spends 1.1–3.3 s
  (3.1–7.7×), 82–89 % of the whole transcode. On lossless input the two are
  within 10–15 %. libjxl-rs also holds 415.8 MB of managed memory at 24 MP
  (jxl-oxide 132 MB; process RSS 469 versus 699 MB on GH x86-64).
- **Color handling is most of "transform" whenever an ICC transform runs.**
  JPEG XL inputs need `--use-rendered-icc` (both decoders report a rendered
  ICC profile) and pay 603–1,563 ms of transform at 24 MP on one thread,
  against 85–216 ms for the same pixels as JPEG with `--assume-srgb`. The
  12 MP camera JPEG with its sRGB ICC profile pays 344–886 ms against
  66–137 ms. With all cores the transform drops to 16–71 ms behind jxl-oxide
  but stays at 124–488 ms behind libjxl-rs on every host: the transform after
  the workspace JPEG XL reader does not scale (cause not attributed here).
- **Serial writers set the floor for WebP and JPEG XL output.** Both encoders
  take one thread, so a 24 MP lossy WebP stays at 3.0–3.3 s of encode in both
  thread modes (88–94 % of wall).
- **JPEG decode stays single-threaded** (78–125 ms at 24 MP in both modes).
  Behind a 2048 px AVIF encode on all cores it is 11 % of wall (BS x86-64:
  68 of 608 ms); behind WebP it is 13–24 %.
- **Opaque codec memory:** AVIF output at 24 MP without resize peaks at
  900–913 MB RSS against 272–276 MB managed; lossless JPEG XL output at
  1,690 MB RSS against 672 MB managed; AVIF input at 24 MP at 610 MB RSS
  against 200 MB managed (GH x86-64).

Reference points beyond one-thread parity:

- **djxl with its default thread pool** decodes the 24 MP VarDCT file in
  124–256 ms (Blacksmith x86-64 and ARM64, 173 ms on GH x86-64); the port,
  which runs its pool tasks serially (#100), needs 8.4–12.9 s, 50–68× longer.
  For the 12 MP lossy encode, `cjxl` with threads takes 1.0–2.9 s against
  the port's 45–83 s.
- **dav1d** (through C libavif) decodes the AVIF inputs 1.6–1.8× faster than
  C libavif with libaom on one thread. The engine's reader runs the AOM
  decoder port on one thread, so it is 2.4–2.6× slower than C with dav1d on
  one thread (x86-64 12 MP: 383 versus 153 ms, 416 versus 159 ms) and
  3.4–3.7× slower than C with dav1d and threads (383 versus 111 ms, 416
  versus 113 ms). C libaom's decoder became slower with threads on GH x86-64
  (437 versus 276 ms at 12 MP).
- On GH ARM64 the C `cjxl` selected Highway's SVE2_128 target and took
  10.9 s for the 12 MP encode against 2.7 s on GH x86-64, which flatters that
  ratio (5.75); BS ARM64 (Ampere-1a) gives 9.30.

### Correctness side checks (all hosts)

- **JPEG XL lossy encode, byte-exact gate on x86-64: passes for this input.**
  The port's 12 MP effort 7, distance 1 codestream (2,057,281 bytes, SHA-256
  `d65d5c60e5aa…`) is identical on all five hosts and byte-identical to `cjxl`
  built in the repository's differential-oracle configuration
  (`HWY_COMPILE_ONLY_SCALAR`, `-fno-slp-vectorize -fno-vectorize`, Clang 18)
  on GH x86-64 (AMD EPYC 9V45) and BS x86-64, as on every ARM64 host. The
  SIMD release `cjxl` differs, as ENCODER_EXPANSION.md allows: on x86-64 in
  content at equal size, on ARM64 by one byte (2,057,280). This extends the
  gate, which so far ran only on macOS AArch64, to native Linux x86-64 for one
  photograph; no code was changed.
- **AVIF encode:** the workspace AOM writer's output is byte-identical to the
  C libavif + libaom 3.15.2 release build (SIMD) on both x86-64 hosts, with
  one thread and all cores. On macOS ARM64 it differs, as expected: the
  port's Neon kernels reproduce libaom's C paths, while the release build uses
  libaom's own Neon/dotprod/i8mm kernels. Decoded AVIF RGB is identical across
  C+aom, C+dav1d and the port on every host.
- **WebP:** 90 of 90 checks identical (encoded files and decoded pixels, port
  against C, all hosts). **JPEG:** C and port checksums identical for every
  input on every host. **JPEG XL decode:** port against jxl-oxide F32 maximum
  difference 1.7e-4 (VarDCT) and 6e-8 (lossless); djxl's lossless round trip
  is pixel-identical to the master.

## 3. Ranked gaps, with the open issue that addresses each

Ranked by what they cost a realistic transcode or by the port/original ratio,
whichever is larger. One-thread medians unless noted.

1. **JPEG XL VarDCT decode, libjxl-rs: 9–22× the C++ original, 3.1–7.7×
   jxl-oxide,** and 82–89 % of a 24 MP JPEG XL → WebP transcode (7.3–10.4 s).
   Against djxl with threads the distance is 50–68×. It is the default reader
   (ADR-0032). Issues: **#96** (SIMD dispatch parity), **#100** (concurrent
   RunOnPool tasks), **#93** (parity measurement and release; this record
   supplies its first idle-host numbers), **#197** (crops decode the full
   frame).
2. **JPEG XL lossy encode e7 d1: 13–18× `cjxl` on x86-64 and macOS
   (5.8–9.3× on Linux ARM64),** 45–83 s for 12 MP. Not yet an engine output
   (ADR-0039 admits lossless effort 2 only). **#106** covers only the
   parallel runner; **no open issue** covers SIMD or vectorization of the
   lossy encoder.
3. **AVIF output: 11.4 s on one thread and 3.5 s on all cores for a 24 MP
   still; the workspace AOM writer is 1.33–1.51× C libaom** at the engine's
   settings. Issues: **#121** (translation overheads), **#124** (x86 dispatch
   follow-ups), **#125** (remaining Neon/x86 hotspots), **#60** (row-to-YUV
   streaming); **#203** (ARM64 versus x86-64 output: here x86-64 equals the C
   release build, ARM64 does not).
4. **WebP lossy encode on x86-64: 2.2–2.8× libwebp** (1.3–1.7× on ARM64);
   it is the whole encode stage of every WebP output (3.2 s at 24 MP).
   Issues: **#89** (WP19 SIMD x86 encoder), **#83** (remaining WebP SIMD
   wave). That the WebP and JPEG XL writers use one core in an all-core run
   has **no open issue**.
5. **AVIF decode: 1.36–1.51× C libavif + libaom, 2.4–3.7× C with dav1d,**
   59–63 % of an AVIF → WebP transcode, process RSS about 3× the managed peak.
   Issues: **#140** (evaluate dav1d/rav1d per library), **#121**/**#125**
   (AOM overheads and hotspots), **#199** (decode memory outside the budget).
6. **Rendered ICC transform: 0.6–1.6 s per 24 MP on one transform thread**
   for every JPEG XL input and ICC-tagged JPEG files (5–10× the transform
   without ICC). Issue: **#219**. That the transform stays at 124–488 ms with
   all cores behind the libjxl-rs reader (16–71 ms behind jxl-oxide) has
   **no open issue**; #59 (row pipeline past the serial driver) may cover it.
7. **JPEG XL lossless decode: 1.42–1.62× djxl (libjxl-rs), 1.23–1.42×
   (jxl-oxide),** 4.7–6.7 s per 24 MP on one thread in the engine. Issues:
   **#96**, **#100**.
8. **WebP lossy decode on x86-64: 1.30–1.51× libwebp** (1.05–1.24× on
   ARM64); **WebP lossless decode: 1.22–1.36×** everywhere. Issues: **#77**
   (SIMD variants slower than the vectorized C translation), **#83**.
9. **WebP lossless encode: 1.06–1.32×** (largest on the GH x86-64 EPYC
   7763). Issues: **#89**, **#83**.
10. **JPEG decode: 1.10–1.18× libjpeg-turbo on x86-64, 1.20–1.30× on Linux
    ARM64** (1.46–1.68× on the noisy macOS VM). Small per image, but the
    decode is single-threaded and 11–24 % of a 2048 px all-core transcode.
    Issues: **#76** (shared decoder code), **#74** (AVX2 gain), **#221**
    (single-threaded decode), **#56** (shrink-on-load would remove most of it
    for downscales).

## 4. Proposed follow-ups

- A SIMD/vectorization plan for the libjxl-rs lossy VarDCT encoder (gap 2;
  no issue yet).
- Parallel or multi-image use of the serial WebP and JPEG XL writers in the
  engine (gap 4; no issue yet).
- Why the transform stage does not scale behind the libjxl-rs reader (gap 6;
  no issue yet, or fold into #59 or #219).
- Revisit the default JPEG XL reader (ADR-0032) with these ratios until
  #96 and #100 land.
- Keep this workflow as an on-demand measurement for #93 and the codec SIMD
  issues. Blacksmith gives one CPU model per architecture; GitHub-hosted
  x86-64 does not.

## 5. Limits of this evidence

- **Shared VMs.** Hosted runners are virtual machines with neighbors. Within
  a job, interleaving cancels slow drift, and Linux spreads are mostly within
  ±3 %. Some Blacksmith x86-64 engine cells reach ±20 %, and the macOS VM
  (3 vCPUs, start-up load averages up to 92) has the widest spreads; macOS
  rows are the least reliable.
- **CPU heterogeneity.** GitHub's `ubuntu-24.04` jobs ran on AMD EPYC 9V45,
  AMD EPYC 7763 and Intel Xeon 6975P-C; absolute times differ by up to 1.7×
  between them (24 MP WebP encode 3.2 versus 5.5 s). Port/original ratios
  always come from one job on one CPU; absolute engine times across GH x86-64
  tables are not comparable. "All cores" means 4 vCPUs, which on GitHub
  x86-64 are 2 cores with SMT (3 vCPUs on macOS).
- **Two photographs.** One 12 MP and one 24 MP photograph; content effects
  (see the 42 MP `elcito` case of #220) are not covered. No 48 MP input.
- **Inputs from older system encoders** (cjxl 0.7, avifenc 1.0.4, cwebp
  1.3.2 on Ubuntu) for the engine part; the codec part uses inputs made by
  the pinned originals. A JPEG XL file from a newer cjxl may decode at a
  different speed.
- **Timer scopes.** Each side's internal timer covers the same API
  operation, but not always identical work: djxl/cjxl times come from their
  printed MP/s (3 significant digits); the AVIF port's parse also scans the
  sequence headers; the WebP C timer has 1 ms resolution. Process wall ratios
  are in the JSON and agree within a few percent except for the shortest
  operations.
- **Threads.** The port-side JPEG XL and AVIF decoders have no thread knob;
  their all-core rows are C-only references. libwebp's `-mt` uses at most two
  threads.
- **Not measured:** AVIF on Linux ARM64 (the generated libavif/AOM/dav1d
  code builds only on macOS ARM64 and GNU Linux x86-64); JPEG XL lossy output
  through the engine (not admitted); crops and shrink-on-load;
  quality-matched encoder comparisons (see [encoder-adoption](encoder-adoption.md));
  the libvips/Sharp comparison (#61).
- **Rerun.** A third run ([43278553592](https://github.com/sebastian-software/ferrisma/actions/runs/43278553592))
  re-ran the 24 MP Blacksmith engine decode in two halves while the first
  attempt ran close to the 50-minute job limit; both first attempts
  finished, so the rerun was cancelled and none of its data is used. The
  workflow now splits that part (`decode-a`, `decode-b`), and the runner
  writes its record after every repetition.

## After the performance fixes (commit 3051f042), 2026-11-12

The same workflow, scripts and inputs, rerun after the fixes listed below,
to show what they changed. All of sections 1–5 and the appendix stay as
recorded for `93c5281f`; this section adds the comparison.

- **Source:** integration commit `3051f042`, force-pushed to
  `bench/v1.0-perf`. Fixes since `93c5281f` that this run can see: JPEG
  Huffman fast-path inlining (`4207c4d3`); a per-channel table for 8-bit
  rendered-ICC matrix-shaper profiles (`1e0a5092`, owner review requested,
  see the correctness re-check); tiled orientation gather (`1d7d05b8`);
  banded RGB→YUV across encoder threads in the AVIF writer (`12bbc073`); threaded AVIF YUV→RGB
  (`c3f21193`); for libjxl-rs row spans and row kernels in the render stages
  and the modular decoder, per-size DCT/IDCT **on AArch64 only**
  (`79b8846d`; x86-64 keeps the old transform code), lazily zeroed planes
  and crop-sized buffering in the decoder wrapper. JPEG XL lossy output is
  now an engine output and the `.jxl` default (distance 1.0).
- **Run:** [43293971731](https://github.com/sebastian-software/ferrisma/actions/runs/43293971731),
  GitHub-hosted and Blacksmith runners in one run, 49 jobs. The scripts
  are the ones committed with this record; unlike the earlier runs, the
  engine decode part is split into `decode-a` (JPEG, WebP) and `decode-b`
  (JPEG XL, AVIF) as section 5 describes, and the tables merge them.
- **Not compared:** the encode part's `jxl-lossless-e2` row, which now
  measures lossy output (see the output side). Engine cells whose job
  landed on a different CPU model than before (most GitHub-hosted x86-64 jobs: the runner gave
  AMD EPYC 7763, EPYC 9V74, Xeon Platinum 8370C and 8573C this time) are
  compared only through ratios within one job.
- **Hosts this time:** GH ARM64 Neoverse-N2, BS ARM64 Ampere-1a (one WebP job
  on a Neoverse-N1), BS x86-64 AMD EPYC family 26 model 68, GH macOS
  Apple M1 (Virtual). Same CPU model does not mean same speed: on BS x86-64
  the unchanged C references ran 15–60 % slower in three codec jobs and

### Correctness re-check

These checks apply to commit `3051f042` as built in run 43293971731. On
x86-64 that includes the JPEG XL float row kernels that were disabled for
non-AArch64 targets afterwards (`691d6ebf`, `b1781469`); the byte-identity
checks below use finite image data, so they do not exercise the NaN case
those commits fix, and they have not been rerun at the fixed commit.

The codec scripts' check files (`*-checks.json`) of run 43293971731 are
byte-for-byte equal to those of the earlier runs on every host that ran in
both (the BS ARM64 WebP checks are new, because that job moved to a
Neoverse-N1, and all 18 passed):

- **JPEG XL lossy encode, effort 7, distance 1, 12 MP: unchanged.** The
  port's codestream is still 2,057,281 bytes, SHA-256 `d65d5c60e5aa…`, on
  all five hosts, and still byte-identical to `cjxl` in the
  differential-oracle configuration (scalar Highway, no auto-vectorization)
  on every host. The GH x86-64 job ran on an AMD EPYC 7763 this time (AMD
  EPYC 9V45 before), so the x86-64 gate now holds on three x86-64 CPU models
  (EPYC 9V45, EPYC 7763, Blacksmith EPYC family 26). The AArch64-only
  DCT/IDCT instantiation did not change any byte of this output. The SIMD
  release `cjxl` still differs as before.
- **JPEG XL decode:** port against jxl-oxide F32 maximum difference
  unchanged (1.66e-4 VarDCT, 6e-8 lossless, same mean); djxl lossless round
  trip still pixel-identical to the master.
- **AVIF:** codec-level encode still byte-identical to C libavif + libaom
  on both x86-64 hosts (one thread and all cores) and still different on
  macOS ARM64 (Neon kernels, as before); decoded RGB still
  identical across C + aom, C + dav1d and the port on every host.
- **WebP:** every port output identical to C on every host. **JPEG:** C and
  port checksums identical for every input on every host.

The engine runs record the SHA-256 of every output. Of the engine cells
present in both runs, every output on a host with the same SIMD kernel level
is unchanged, including all AVIF outputs (workspace AOM writer with the new
banded RGB→YUV conversion, one thread and all cores, and rav1e), all lossy
WebP outputs and every JPEG XL and AVIF input row, with these exceptions:

1. **Rendered-ICC JPEG, resized, ARM64: 14 of 16.8 million samples change
   by one code.** The 12 MP camera JPEG (EXIF orientation 6, sRGB ICC,
   `--use-rendered-icc`) resized to 2048 px gives a new output on GH ARM64,
   BS ARM64 and macOS ARM64 (`36661772802a…` → `c94ccee2b2bc…`, one thread
   and all cores). Unresized output and all x86-64 outputs are unchanged.
   Reproduced locally (macOS ARM64) with `cli_subset`: the parent of
   `1e0a5092 perf(icc): evaluate 8-bit matrix-shaper profiles through a
   channel table` gives the old bytes, that commit the new ones. A lossless
   WebP of the same 2048×2731 output differs in 14 of 16,779,264 samples, each
   by exactly 1. This is the documented bound of that commit, which requests
   owner review (ADR-0016, ADR-0023: "a final rounding can flip"); it is an
   expected change, not a regression, and still needs that review.
2. **Resized output depends on the x86-64 kernel level, which was already
   the case.** The 24 MP lossy WebP input resized to 2048 px gives
   `0cc761419631…` with AVX2 or Neon and `b21143169355…` with AVX-512 in both
   runs. GH x86-64 moved from an AVX2 host (EPYC 7763) to an AVX-512 host
   (Xeon Platinum 8573C), so the hash changed with the host, not the code.
   The 12 MP JPEG XL input rows on GH x86-64 moved the other way (AVX-512
   Xeon 6975P-C → AVX2 EPYC 7763) and also differ in their eight resized
   cells (both decoders, VarDCT and lossless, one thread and all cores); the
   same cells are unchanged on the AVX-512 BS x86-64 host and on both Linux
   ARM64 hosts, and no earlier AVX2 hash exists for them. The same applies
   to seven resized AVIF output cells on GH x86-64 (12 MP AVX2 → AVX-512,
   24 MP AVX-512 → AVX2): BS x86-64 (AVX-512 in both runs) reproduces its
   AVIF bytes exactly, and every full-size AVIF output on GH x86-64 is
   unchanged across the kernel-level switch, so the difference enters in the
   resize. That resized pixels can depend on the x86-64 kernel level for
   some inputs is not new, but it is not recorded elsewhere yet.
3. **The encode part's `jxl-lossless-e2` row is no longer lossless**: the
   CLI now defaults `.jxl` output to lossy distance 1.0 (`--jxl-lossless`
   selects effort 2 lossless), and the benchmark script passes no flag. Its
   new outputs and times are lossy VarDCT e7 d1 and are not comparable with
   the earlier row (see the output side below).
