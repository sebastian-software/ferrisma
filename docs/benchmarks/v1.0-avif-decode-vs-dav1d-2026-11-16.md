# AVIF decode against stock libavif with dav1d, hosted run 43789376239

**Question.** The port's AVIF decode goes through its libaom translation;
since libavif-rs [ADR 0061](../../codecs/libavif-rs/docs/adr/0061-build-the-root-with-avif-codec-dav1d-off.md)
dav1d is not in the runtime at all (engine
[ADR-0031](../adr/0031-workspace-libavif-input-experiment.md), owner decision
of 2026-11-15). How does that compare with what most users of libavif get:
stock libavif decoding with dav1d and its assembly?

**Answer, for these hosts and these two inputs.** Single-threaded, the port's
decode took **1.75 to 2.1 times as long** as C libavif with dav1d (assembly
on, one thread). The decoded RGB was identical in all three (port, C libavif
with libaom, C libavif with dav1d) on every host and input. For comparison,
the same decode took 1.12 to 1.23 times as long as C libavif with libaom's SIMD
build, the original it is a translation of.

The benchmark harness is `scripts/bench/ci-perf/codec_avif.sh` through
`.github/workflows/bench-v1-perf.yml`; the `c-dav1d` columns are context
only (not the port's original), with dav1d 1.5.4 built from the pinned
upstream snapshot by Meson in Release with its assembly (AVX-512 included
on x86-64). There is no performance gate for v1.0 (ADR-0041); this record
is evidence, not a release claim.

## Results

Internal decode time (decoder create, parse, AV1 decode, YUV to RGB8; file
read and write excluded), medians of 7 repetitions after 1 warm-up, in ms.
`photo12` (4032×3024, libavif's test photograph) and `photo24` (6000×4000)
are the masters of `scripts/bench/ci-perf/make_masters.sh`, encoded at
quality 60.

| Host (CPUs) | Input | port, 1 thread | C + libaom SIMD, 1 thread | C + dav1d, 1 thread | C + dav1d, all threads | port ÷ C + dav1d (1 thread) |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| GitHub `ubuntu-24.04`, x86-64 (4) | photo12 | 326.1 | 280.6 | 153.3 | 112.3 | 2.13 |
| GitHub `ubuntu-24.04`, x86-64 (4) | photo24 | 628.5 | 561.4 | 309.6 | 222.3 | 2.03 |
| Blacksmith 4 vCPU, x86-64 (4) | photo12 | 216.0 | 184.5 | 105.2 | 72.0 | 2.05 |
| Blacksmith 4 vCPU, x86-64 (4) | photo24 | 418.5 | 362.3 | 206.4 | 140.6 | 2.03 |
| GitHub `macos-15`, AArch64 (3) | photo12 | 250.4 | 215.8 | 142.8 | 92.5 | 1.75 |
| GitHub `macos-15`, AArch64 (3) | photo24 | 497.3 | 404.2 | 260.3 | 166.3 | 1.91 |

Source: the `codec-avif-*` artifacts of run 43789376239,
`avif-decode-12.json` and `avif-decode-24.json`, `summary.<column>.internal_median_ms`;
the SHA-256 of each column's output is in the same records.

## What it means

- The gap is the decoder, not the port: libaom's decoder is itself slower
  than dav1d on these files, and the port is within 12 to 23 percent of the
  libaom build it translates.
- The port does not get dav1d's speed back by any setting. Reaching it
  would need a dav1d-based decoder in the runtime, which the owner decided
  against (ADR-0031); the dav1d translation stays an independent
  cross-check in the tests (`avif-dav1d.yml`).
