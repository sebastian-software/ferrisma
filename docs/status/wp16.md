## Checkpoint (2026-11-09)

ADR 0007 proposes `webp::api::decode`: `Features::parse` (the features probe);
`Config` (a colorspace and `WebPDecoderOptions` with typed, chainable setters,
`validate` and `output_size`); `decode` into library memory (`Image`, which
owns it) and `decode_into` caller rows or YUVA planes (`Output`);
`IncrementalDecoder<'a>` with `append`, `update` (`Ok(Status::NeedsMoreData)`
for C's `SUSPENDED`), `decoded_rows`, `rows` and `planes` lent between calls,
and `into_image`; `Container<'d>` over the demuxer (`ICCP`, `EXIF`, `XMP`,
any chunk, canvas, flags, loop count, background color, frame count);
`AnimationDecoder<'d>` (`next_frame`, `reset`, `has_more_frames`, `info`)
in the four modes WP14 supports; and `DecodeError` with one variant per
`VP8StatusCode` from 1 to 7, `FrameFailed` and the API's validation errors.
Every decoding calls the translation with the stored options, so its output is
the translation's, which WP12 and WP14 proved against C. A throwaway prototype
of the three interface changes (decision 2, 3) and the lifetimes of
`IncrementalDecoder<'a>`, `Container<'d>` and `AnimationDecoder<'d>` compiled,
with `Container` and `AnimationDecoder` `Send` and `Sync`; it is not committed.

### Decisions needed (recommendation first)

1. Accept ADR 0007 as is, or change names and shapes.
2. **Options of an incremental decoder that owns its output.** The translation
   sets `params.options` only in `webp_i_decode(data, Some(&'a mut config))`,
   which also borrows `config.output` mutably for the decoder's life, so an
   API object cannot own both the configuration and the decoder.
   (a) A crate-visible `WebPIDecoder::set_options(&mut self, &'a
   WebPDecoderOptions)` in `src/dec/idec_dec.rs` (WP12's module), one line,
   its own commit; the API then creates the decoder over its own buffer
   (`webp_i_new_rgb`, `webp_i_new_yuva`, `webp_i_new_decoder`) and borrows only
   `&'a Config`. (b) No change: the caller holds a separate target object
   (owning a `WebPDecoderConfig`) that the decoder borrows mutably, which maps
   one to one onto `webp_i_decode` but is two objects for every caller.
3. **Container and animation decoder from `&[u8]`.** `webp_demux` and
   `webp_anim_decoder_new` borrow the `WebPData` value (WP8's decision), so an
   API constructor that receives `&'d [u8]` cannot build one that outlives the
   call. (a) Crate-visible `demux_bytes(buf: &'a [u8], allow_partial, version)`
   in `src/demux/demux.rs` (WP8) and `anim_decoder_new_bytes(bytes: &'a [u8],
   options, version)` in `src/demux/anim_decode.rs` (WP14), holding the
   current bodies, with the translated functions calling them with
   `&data.bytes`; one commit each, no behavior change. (b) No change: the
   constructors take `&'d WebPData<'_>` and the API re-exports `WebPData`.
4. **Odd crop offsets.** libwebp snaps `crop_left` and `crop_top` to even values
   for lossy images only (`WebPIoInitFromOptions` with a YUV source; WP12's
   matrix has odd origins), so a lossy crop moves silently by one pixel while
   a lossless crop is exact. (a) Refuse odd offsets with `InvalidCrop` for
   every image [one rule, and the incremental decoder does not know the format
   when it is created]; a caller crops at the even position below and skips one
   column or row. (b) Accept them as libwebp does and document the snapping.
   (c) Refuse them only for lossy images in `decode` and `decode_into`.
5. **Scaling.** (a) Both sides required, each 1 to 16383 [keeps a library
   output under 1 GiB; with C's rule a derived side or a side up to
   `i32::MAX / 2` makes libwebp reserve and zero up to 16 GiB, and the
   incremental decoder cannot check a derived side before the header]; WP12's
   derived-side cases are replayed with the side computed by the translation's
   `webp_rescaler_get_scaled_dimensions`. (b) C's rule: one side may be 0.
6. **Slow memory.** (a) Not offered [it only defers the writes into caller
   memory for premultiplied output, at the cost of a temporary buffer of the
   whole image, and the own-buffer incremental decoder of decision 2a cannot
   select it]. (b) A flag on `Output` for `decode_into` only.
7. **Premultiplied output of a mode without alpha** is unrepresentable:
   `ColorMode` has C's 13 colorspaces (four `Premultiplied` variants), not a
   layout plus a flag, so the brief's error case for it has no input. The
   alternative is a layout and a `premultiplied` flag with `InvalidParameter`.
8. **Order of errors in `decode` and `decode_into`.** (a) The API checks the
   crop, scale and caller memory against the features before calling
   `webp_decode` [precise errors, no panic risk]; recorded deviation: C
   reports a bitstream error in a frame header before the `INVALID_PARAM` of a
   bad crop or buffer, the API reports its validation error. (b) Pass them to
   libwebp and return its `InvalidParam`.
9. **Animation canvases.** WP14's decoder allocates and zeroes two canvases of
   `4 * canvas_width * canvas_height` bytes in `new`, up to 16 GiB each for a
   canvas that a tiny file can declare. (a) Document it and point to
   `Features::parse` or `Container` for the canvas size first [no behavior of
   the API's own]. (b) A `max_canvas_bytes` field in `AnimationOptions` refused
   with a new error before allocation.
10. **Evidence.** (a) No probe of its own, as WP17 (its decision 7): the tests
    replay commands of WP12's probe `tools/oracle/probes/wp12/decode.c`
    (`features`, `decode`, `simple`, `into`, `incremental`) and WP14's probe
    `tools/oracle/probes/wp14/anim.c` through the API and compare the C output
    on every printed key that the API exposes. (b) A probe under
    `tools/oracle/probes/wp16/`.
11. **`FrameFailed`.** (a) Its own variant without a C code, because
    `WebPAnimDecoderGetNext` returns no status. (b) Report a failed frame as
    `BitstreamError`.

### Evidence planned

- `tests/wp16_decode.rs`: `Features::parse` on the 131 vectors whole, cut at 0
  to 48 bytes, half and one short, against `features`; `decode` in all 13 modes
  on every vector against `decode` with library memory; the options matrix of
  WP12 (even crops, scales with both sides, flip, `bypass_filtering`,
  `fancy_upsampling(false)`, threads, dithering) with library memory and with
  caller rows and planes padded and surrounded by WP12's guard bytes;
  `decode` with `Config::new(mode)` against the simple API and `...Into`
  commands; truncated and invalid inputs (status and untouched guard bytes).
  Compared: status, output size, the digests of the library memory or of the
  caller blocks with their guards.
- `tests/wp16_incremental.rs`: `append` and `update` at WP12's chunk sizes and
  with its options, in library and caller memory, against `incremental` with
  the configuration kind: status of every step, `decoded_rows`, and the digest
  of the rows lent after every step; the final buffer.
- `tests/wp16_animation.rs`: `AnimationDecoder` and `Container` on the
  animations of `tests/wp14_support` and the still vectors against `anim`:
  info, the eight `WebPDemuxGetI` values that the API exposes, the `ICCP`,
  `EXIF` and `XMP` walks, `has_more_frames`, every frame's timestamp and
  canvas digest, `reset`.
- `tests/wp16_misuse.rs`: every documented error (zero and odd crops, crops
  outside the picture, zero, too large and derived scales, zero and short
  strides, short and mismatched planes, a missing or extra alpha plane, a
  mode mismatch, dithering above 100, `into_image` before completion) and a
  seeded property test of 2,000 rounds under `catch_unwind`; `Send` and `Sync`
  assertions.
- Doctests for every public item; `cargo doc --no-deps` without warnings for
  `src/api`.
