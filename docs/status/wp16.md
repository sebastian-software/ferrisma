  (integrator, 2026-11-09, with three changes) and implemented as
  `webp::api::decode` in `src/api/decode.rs`. Every decoding calls the

## Decisions applied

The checkpoint of 2026-11-09 proposed ADR 0007 with eleven decisions; the
integrator accepted all of them as recommended, with three changes to names
and shapes:

1. ADR 0007, accepted, with these changes, all applied:
   - `Features::format` is `Option<Format>` with `Format { Lossy, Lossless }`.
     A successful parse reports libwebp's 0 only for an animation
     (`ParseHeadersInternal` returns at the animation flag; a prefix that ends
     before the image chunk is `NOT_ENOUGH_DATA`), so `None` says that the
     frames carry the format; the rustdoc says so.
   - `Container::format_flags` is gone; `Container::has_alpha` and
     `Container::has_animation` read the two bits, and `ICCP`, `EXIF` and
     `XMP ` are answered by their accessors.
   - `background_color` (on `Container` and `AnimationInfo`) is documented as
     `0xAARRGGBB`, the `ANIM` chunk's bytes read as a little-endian `u32`,
     reported and not applied.
2. `WebPIDecoder::set_options`, crate-visible, in `src/dec/idec_dec.rs`
   (below).
3. `demux_bytes` in `src/demux/demux.rs` and `anim_decoder_new_bytes` in
   `src/demux/anim_decode.rs` (below). No exception entries in
   `tools/units.*` were needed: the provenance check lists translated items,
   and the helpers belong to the modules they are in.
4. Odd crop offsets are refused for every image with `InvalidCrop`; the
   rustdoc of `Config::crop` and the WP21 notes give the recipe (crop at the
   even position and skip a column or row). Exact lossless odd crops are a
   review trigger of the ADR.
5. Both scaled sides are required, each 1 to 16383 (deviation 2); WP12's
   derived-side cases are replayed with the side from
   `webp_rescaler_get_scaled_dimensions`.
6. Slow memory is not offered; the review trigger stays.
7. `ColorMode` has C's 13 colorspaces, so the brief's error case
   "premultiplied output asked of a mode without alpha" has no input: there is
   no such mode to ask for.
8. `decode` and `decode_into` validate the configuration and the caller
   memory against the features before `webp_decode` (deviation 4); the outputs
   stay byte-identical, which the replays show.
9. The canvases of the animation decoder are documented, with no
   `max_canvas_bytes`: the rustdoc of `AnimationDecoder::new` and the WP21
   notes give the formula and point to `Features::parse` and
   `Container::canvas_width`/`canvas_height` for the check before
   construction.
10. No probe of its own: the tests replay WP12's and WP14's commands.
11. `DecodeError::FrameFailed` has no C code.

The integrator's two further requirements are applied: every stride in the
API (`Output::Rows`, `YuvaPlanes`, `Frame::stride`, `Rows::stride`) says "in
bytes" in its rustdoc, and `tests/wp16_misuse.rs` covers each documented
error, with the inputs whose raw form makes the translation panic in
`the_translation_panics_where_the_api_refuses`. The API has no callbacks, so
WP17's point about panicking callbacks does not apply.

One change after the acceptance, from the misuse tests: an empty
`IncrementalDecoder::append` before any data returns `NeedsMoreData` without
calling the translation, whose `debug_assert` (C's assertion, WP12 exclusion 2)
would otherwise panic in the dev and `checked` profiles (deviation 6). ADR 0007
says so.

### Interface changes outside the package

Each is its own commit with the reason in the message, and none changes
behavior; the integrator agreed to all three (decisions 2 and 3):

1. `refactor(dec): let a decoder over its own buffer take decoding options`:
   the crate-visible `WebPIDecoder::set_options` in `src/dec/idec_dec.rs`
   (WP12) does what `WebPIDecode` does with `idec->params.options =
   &config->options`. The translation set the options only in `webp_i_decode`,
   which also borrows the configuration's output buffer for the decoder's
   life, so an API object could not own the decoder and its configuration.
2. `refactor(demux): let the demuxer parse a byte slice`: the crate-visible
   `demux_bytes` in `src/demux/demux.rs` (WP8) holds the body of
   `webp_demux_internal` over the bytes, which calls it with `&data.bytes`.
   The demuxer borrowed the `WebPData` value, so a `Container` built from
   `&'d [u8]` inside the API could not outlive the call.
3. `refactor(demux): let the animation decoder borrow a byte slice`: the
   crate-visible `anim_decoder_new_bytes` in `src/demux/anim_decode.rs` (WP14)
   holds the body of `webp_anim_decoder_new_internal` over the bytes, with
   `webp_demux(webp_data)` written as `demux_bytes(bytes, false,
   WEBP_DEMUX_ABI_VERSION)`, which is what `webp_demux` calls.

The translated functions keep their `// upstream:` markers. WP12's and WP14's
tests, which drive the unchanged public functions, pass.

## Not-applicable checks

1. **Source correspondence.** WP16 translates no upstream unit, so there are no
   `// upstream:` markers, no `tools/rust_name.py` names and no probe of its
   own (decision 10).
2. **`NULL` arguments** do not exist in the API (references and slices).
3. **Callbacks.** The API takes no callbacks, so a panicking callback (WP17's
   test) cannot occur.
4. **I/O hooks, slow memory, `WebPCopyDecBuffer`, `WebPGrabDecBuffer`, the
   demuxer's frame iterators, `WebPGetInfo` and the simple functions** are not
   in the API (ADR 0007); the simple functions are compared through `decode`.
   WP12's `fconfig` commands (features first, which matters only for slow
   memory) and its constructor cases that the API cannot express
   (`WebPINewRGB` with a YUV mode, YUVA memory without a V plane) are not
   replayed.
5. **Plane offsets and buffer descriptions** (`valid=`, `input=`, `rgba=`,
   `yuva=` and the offsets in the incremental lines) are not exposed and not
   compared; the samples, sizes, strides and guard bytes are.
6. **Undefined behavior in C.** WP12's exclusions hold. The API passes the
   bitstream to the translation, so crafted lossy streams whose coefficients
   overflow `int` in `TransformOne_C` (WP12 exclusion 1) still panic in the
   dev and `checked` profiles and wrap in release; the API cannot detect them
   before decoding. `WebPIAppend` of zero bytes before any data (exclusion 2)
   no longer reaches the translation (deviation 6). Negative strides and
   overlapping input and output memory (exclusions 4, 5) cannot be expressed.
7. **Allocation failures** are not injected; `OutOfMemory` is reached only
   through the translation's fallible reservations.
8. **32-bit targets** are not run; the `usize` overflow of a plane's extent maps
   to `InvalidStride` and is reachable there only.
9. **The two largest vectors** get the features, two modes and the simple API
   in the decode tests and are left out of the incremental tests, as in WP12.
10. **`cargo doc --no-deps`** reports no warning from `src/api` or from the
    three helpers.

## Recorded deviations

Differences between the API and C's decoder API, each stated in ADR 0007:

1. **Odd crop offsets** are refused with `InvalidCrop`. libwebp moves an odd
   `crop_left` or `crop_top` of a lossy image to the even position below it
   (`WebPIoInitFromOptions` snaps when the source is YUV) and crops a lossless
   image exactly. 1,062 replayed commands that C decodes.
2. **Scales** need both sides, each 1 to 16383. libwebp derives a side given as
   0 and accepts outputs up to `i32::MAX / 2`, for which it reserves and zeroes
   up to 16 GiB of library memory.
3. **Dithering strengths above 100** are refused with `InvalidParameter`, as
   `WebPValidateDecoderConfig` refuses them; `WebPDecode`, which does not
   validate, clamps them. 258 replayed commands.
4. **Order of errors.** `decode` and `decode_into` check the configuration
   first, then the features, then the crop, scale and caller memory against
   them, and call `webp_decode` last. C reports a bitstream error in a frame
   header before the `VP8_STATUS_INVALID_PARAM` of a crop, scale or buffer that
   does not fit, and a features error before any configuration error. The
   samples of every accepted decoding are libwebp's.
5. **Caller memory** has one stride for both chroma planes, and the API refuses
   an alpha plane for `Yuv` (`OutputMismatch`); C takes separate U and V
   strides and ignores an alpha plane in `MODE_YUV`.
6. **An empty `append` before any data** returns `NeedsMoreData` without
   calling the decoder. C asserts against it (WP12 exclusion 2), and the
   translation's `debug_assert` panics in the dev and `checked` profiles;
   release builds of both return `SUSPENDED`.
7. **The incremental decoder owns its output buffer** (C's `WebPINewRGB`,
   `WebPINewYUVA` and `WebPINewDecoder` buffers) and takes the options as
   `WebPIDecode` does; C's `WebPIDecode` decodes into the configuration's
   buffer, which keeps the memory after `WebPIDelete`. The samples are equal
   (the replays compare them); `into_image` moves the library memory out.
   Slow memory is not offered.
8. **Errors without a C status.** `AnimationDecoder::new` and `Container::new`
   classify a failure by running `Features::parse` and the partial demuxer on
   the data; C returns `NULL` and the demuxer reports a non-WebP file as a
   header in progress. A failed `next_frame` is `FrameFailed`. On failure
   `Features::parse` returns no features, where C writes what it parsed.
9. **`IncrementalDecoder::output_size`** is `None` while libwebp's decoded area
   exists with a width of 0 (between a lossless header and the allocation of
   the output); `rows` then lends the caller's memory with 0 rows, as C's
   getter returns the caller's pointer.
10. **The canvas of a failed frame** is not exposed: the borrow of the previous
    frame ends at the next call (WP14 deviation 6).

## Upstream behavior preserved

- A whole-image decoding of a truncated file returns libwebp's status:
  `BitstreamError` when the file ends before the image's dimensions (C maps
  the features' `NOT_ENOUGH_DATA`), and the decoder's `NotEnoughData` or
  `BitstreamError` later; caller memory then holds the rows decoded so far.
- The incremental getters follow libwebp's pointer and stride: while a flipped
  decoding runs, row 0 is the bottom row of the output and the stride is
  negative; once complete, the stride is positive. With a scale, chroma and
  alpha rows lag behind the luma rows.
- After a failed incremental step every later step returns `BitstreamError`.
- A still image through the animation decoder is one frame with timestamp 0,
  loop count 1 and background `0xFFFFFFFF`.

## ADR-0018 gate (e): the decoder's semantics

- **Lossy color.** `VP8 ` frames are Y'CbCr 4:2:0 after ITU-R BT.601 in limited
  range (Y 16 to 235, Cb and Cr 16 to 240). The RGB modes convert with the
  fixed-point matrix of `src/dsp/yuv.h` (`VP8YUVToR`, `VP8YUVToG`,
  `VP8YUVToB`), the encoder's matrix (ADR 0006), with fancy upsampling of the
  chroma unless `fancy_upsampling(false)` or a scale, which upsamples in the
  rescaler; the in-loop filter runs unless `bypass_filtering` or a scale below
  3/4 in both directions. `Yuv` and `Yuva` return the planes as decoded, in
  limited range, for the caller to convert with the same matrix.
  `dithering` adds libwebp's dither.
- **Lossless color.** `VP8L` stores ARGB exactly; the RGB modes reorder it (the
  16-bit modes keep the high bits); `Yuv` and `Yuva` convert it with
  `WebPConvertARGBToY` and `WebPConvertARGBToUV` (limited range, chroma from
  2 by 2 averages).
- **Alpha.** Straight in `Rgba`, `Bgra`, `Argb`, `Rgba4444` and the alpha plane
  of `Yuva`; premultiplied in `PremultipliedRgba`, `PremultipliedBgra`,
  `PremultipliedArgb` and `PremultipliedRgba4444`. A lossy image's alpha comes
  from its `ALPH` chunk; `alpha_dithering` smooths quantized alpha. Modes
  without alpha drop it without blending.
- **Depth.** 8 bits per channel at most; `Rgba4444` and `Rgb565` pack 4 or 5
  and 6 bits per channel into two bytes, red first (`WEBP_SWAP_16BIT_CSP` off).
- **Color signal.** None besides an `ICCP` chunk, whose payload
  `Container::icc_profile` returns unparsed; without one, readers assume sRGB.
  The samples are as stored, never color-managed.
- **Orientation.** None besides an `EXIF` chunk, whose payload
  `Container::exif` returns unparsed; the orientation tag is the reader's to
  apply.
- **Animation.** Full canvases after blending and disposal, premultiplied
  blending in the premultiplied modes, a transparent black start, the
  background color reported and not applied, timestamps as end times in
  milliseconds.

## Notes for the packages that build on WP16

### WP21 (Ferrixel `webp-read`)

- **Probing a header.** `Features::parse(prefix)` describes the source before
  decoding: `width`, `height`, `has_alpha`, `has_animation` and `format`
  (`None` for an animation). `Err(DecodeError::NotEnoughData)` means read more
  bytes; the dimensions are known once the prefix reaches the `VP8 `/`VP8L`
  header, or the `VP8X` chunk of an animation. The sample type is 8-bit
  unsigned in every mode; choose `ColorMode::Rgba` (straight alpha) or
  `ColorMode::Rgb` from `has_alpha`, or `Yuv`/`Yuva` for planar output.
- **Decoding a region into budgeted memory.** Build
  `Config::new(mode).crop(left, top, width, height)` with even `left` and
  `top`; for a region at an odd position, crop at `left & !1`, `top & !1` with
  the width and height grown by one and skip the first column or row.
  `config.output_size(&features)` returns the output size before anything is
  allocated; reserve `(height - 1) * stride + width * bytes_per_pixel` bytes
  (or the planes of `YuvaPlanes`) from the budget and call
  `decode_into(&file, &config, Output::Rows { data, stride })`. Only the
  output is caller memory. libwebp's internal memory is not observable and not
  bounded by the crop: a lossless image allocates its whole ARGB image
  (`width * height * 4` bytes plus cache rows, `AllocateInternalBuffers32b`),
  and the alpha of a lossy image a plane of `width * crop_bottom` bytes
  (`AllocateAlphaPlane`) besides its own lossless decoder; a lossy image
  otherwise keeps macroblock-row caches. Report that as unbounded, as the
  AVIF source does.
- **What the crop measurement allows to claim** (WP12's table): a cropped
  `decode`/`decode_into` decodes the rows from the top down to the crop's
  bottom (plus 2 or 8 rows of filter margin for lossy), so it saves the rows
  below the crop and never the rows above; a horizontal crop saves nothing;
  the incremental decoder parses every macroblock row of a lossy image; a scale
  runs after decoding at full resolution. A `CodecRegionRequest` class can
  claim only "rows below the region are not decoded" for whole-file decoding;
  anything else is `FullFrameFallback` in cost, though the output memory is
  the region's.
- **Streaming rows.** `IncrementalDecoder::with_output(&config, output)` over
  the budgeted rows, then `append` (or `update` with the whole data so far)
  per read; after each call `decoded_rows()` and `rows()` lend the rows decoded
  so far, top to bottom unless `flip(true)`, until the next call. `Status::
  NeedsMoreData` is the normal state; an error ends the decoding. The decoder
  borrows the `Config`, so keep the configuration alive beside it; it is not
  `Send`.
- **ICC and EXIF.** `Container::new(&file)` (or `Container::partial(prefix)`,
  which suffices for `ICCP`, written before the image data) and
  `icc_profile()`, `exif()`, `xmp()`, or `chunks(*b"EXIF")` for every chunk.
  Read the EXIF orientation (1 to 8) from the payload as the JPEG adapter does
  (Ferrixel ADR-0019); the API parses neither chunk.
- **Alpha and color.** See gate (e) above: limited-range BT.601 for lossy,
  exact ARGB for lossless, straight alpha unless a `Premultiplied` mode is
  chosen, no color signal besides the ICC profile.
- **Animations.** Budget the canvases first: `AnimationDecoder::new` allocates
  two canvases of `4 * canvas_width * canvas_height` bytes and zeroes them, and
  a small file can declare a canvas of up to 2^32 pixels; read the size from
  `Features::parse` (`width`, `height`) or `Container::canvas_width`/
  `canvas_height` before. Then `next_frame()` once for the first frame, or in a
  loop until `Ok(None)` for all frames; each `Frame` lends the whole canvas
  (`stride = 4 * canvas_width` bytes) and its end time in milliseconds until
  the next call. `AnimationInfo` gives the loop count and the background color
  (`0xAARRGGBB`, not applied). `AnimationDecoder` and `Container` are `Send`
  and `Sync`.
