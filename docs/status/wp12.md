# WP12: decoder integration

- Status: every unit of the WP12 inventory is translated, including the
  slow-memory paths, which `WebPDecBuffer::slow_memory` now represents
  (integrator decision of 2026-11-07). The C ABI of `decode.h`, `WebPMalloc`
  and `WebPFree` is exported.
  Upstream's `dwebp`, `webpinfo` and `imageio`, unmodified and linked against
  the Rust library, pass `test_dwebp.sh` (480 checksums) and `test_lossless.sh`
  (33 vectors, 330 comparisons). The `fuzz/` crate exists with four targets.
- Sub-wave: 3a
- Model: Claude Opus 5.5 (`claude-opus-5-5`)
- Depends on: WP6, WP7 (and through them WP1 to WP4); takes over their modules
  for integration fixes
- Probes: `tools/oracle/probes/wp12/`; tests: `tests/wp12_*.rs`

Written by the package session; the integrator aggregates it into
[PORT_STATUS.md](../PORT_STATUS.md). See the package's row in

## Decisions

The brief fixed the shape (ADR 0003, "Decoding context per call"; ADR 0004).
One question went to the integrator:

- **Slow external memory (decided 2026-11-07, option A).** C's
  `is_external_memory >= 2` changes observable behavior: `WebPDecode` decodes
  into a temporary buffer and copies at the end (so it reports the bitstream
  status before an invalid caller buffer and leaves the caller's buffer
  untouched when the decoding fails), and the incremental decoder's getters
  return `NULL` until its final copy. ADR 0003 had called the value a
  performance hint. `WebPDecBuffer` (WP1's type) now has `slow_memory`,
  meaningful only with `External` storage, and ADR 0003's "Buffers and planes"
  says so; that change is its own commit. WP12 translates `WebPAvoidSlowMemory`,
  the temporary-buffer branch of `WebPDecode`, `final_output` in `NewDecoder`
  and the copy in `FinishDecoding`, and the C ABI maps the value both ways
  (1 is `External` without the flag, 2 or more with it; the C buffer keeps the
  caller's integer).

These choices were left to WP12 and stay inside those records:

- **Incremental decoder.** `WebPIDecoder<'a, 'b>` keeps `io`, `params`, the
  decoder (`enum` of a boxed `VP8Decoder` and `VP8LDecoder`), `mem` and its own
  output buffer as plain fields. `'a` is what the caller lends for the decoder's
  life (the options and output buffer of a `WebPDecoderConfig`, the output
  buffer of `WebPINewDecoder`, the hooks of `WebPISetIOHooks`); `'b` is the
  caller memory that an output buffer borrows. C's `params.output` is the
  caller's buffer (`user_output`) or the decoder's own. Two lifetimes are
  needed because a mutable borrow is invariant: one lifetime would keep the
  configuration borrowed for its whole existence. Dropping the decoder is
  `WebPIDelete`.
- **Input positions.** The input of a step is `mem.buf` in append mode and the
  caller's whole buffer in map mode, which `WebPIUpdate` passes and the decoder
  does not keep. Every C pointer into it is an index: the VP8 readers (set up at
  `mem.start` by `vp8_get_headers_at`, integration fix 2), the token partitions
  and the alpha chunk. `DoRemap` moves them by the index delta that C adds to
  its pointers: `-old_base` when append mode reallocates, and 0 otherwise,
  including map mode, where the bytes keep their positions in the caller's
  growing buffer. Partition #0 is read from `mem.part0_buf` once
  `CopyParts0Data` copied it in append mode. The VP8L reader reads the input from
  `mem.start` on, which does not move for VP8L.
- **Output buffers.** `PlaneStorage::Internal` is `private_memory`,
  `External` the caller's memory. A plane is C's `NULL` when the buffer holds no
  memory of its own or when its region does not exist in caller storage; the
  member of the `u` union that the colorspace does not select reads as zeroed.
  ADR 0003 records both (amended 2026-11-07).
- **Simple API.** `WebPDecodeRGBA` and friends return `Vec<u8>`,
  `WebPDecodeYUV` returns the owned `WebPDecBuffer` with its planes, and the
  `...Into` functions take the caller's slices and return the luma or RGB slice
  on success (C: the pointer).
- **C ABI memory (ADR 0004).** Decoded samples that C receives are platform
  `malloc` blocks: the simple API copies the translation's buffer into one (C
  releases it with `WebPFree()` or `free()`), and a buffer whose memory the
  library allocates receives one as `private_memory` after the call that
  allocated it; `WebPFreeDecBuffer()` releases it. The ABI keeps the size of
  every such block, so that a buffer that still holds one can be decoded into
  again, as C allows. Caller memory is lent to the Rust buffer for the duration
  of one call: the incremental decoder detaches it before it returns and
  attaches it again at the next call, so no Rust borrow of C memory survives
  while C reads or writes it. Library samples of the incremental decoder move
  into a block after the call that allocates them and are lent the same way.
- **Consumer build.** `tools/oracle/probes/wp12/oracle.cmake` copies upstream's
  `dwebp`, `webpinfo`, `imageioutil`, `exampleutil`, `imagedec` and `imageenc`
  targets with their own sources, include directories and definitions, and
  replaces `libwebp` with the Rust static library. Upstream's targets get
  `upstream/libwebp/src` only through the public include directories of the
  `webp` and `exampleutil` targets they link, so the copies add it explicitly
  and search it first, ahead of the dependency include directories, where a
  system libwebp (Homebrew's, for example) could otherwise supply `webp/*.h`.
  `tools/build_oracle.py --rust-lib` builds the library (`cargo rustc
  --release --lib`, which also reports the native libraries it needs) and
  passes both to CMake; `tools/check.py --oracle` uses the option. Without it
  the oracle builds as before.
- **`fuzz/`.** A separate crate with its own workspace and `libfuzzer-sys` 0.4
  as its only dependency besides the library; ADR 0005 is amended to name it.

### Integration fixes in WP6 and WP7 modules

Each is its own commit with the reason in the message:

1. `src/dec/io_dec.rs` (WP6), commit `fix(dec): give CustomIo separate lifetimes
   for params and output`: `CustomIo<'p, 'o, 'a>` borrows `WebPDecParams<'o>`
   and `WebPDecBuffer<'a>`. `WebPDecode` borrows `config.options` for one call
   while `config.output` borrows caller memory for longer; with one lifetime and
   an invariant mutable borrow, `DecodeInto` could not pass both. The emit
   functions already took independent lifetimes. No behavior change.
2. `src/dec/vp8_dec.rs` (WP6), commit `fix(dec): let VP8GetHeaders start inside
   a larger input`: the crate-visible `vp8_get_headers_at(dec, io, data, start)`
   sets the readers up at positions of the whole input, as C's readers point into
   the owner's buffer; `vp8_get_headers` calls it with 0 and is unchanged. The
   incremental decoder needs it so that `DoRemap` can move the readers by index
   deltas of its buffer (decision "Input positions").

No WP7 module changed.

The test covers 72 decodings (six vectors, six crops, with and without
scaling); the table shows a representative subset, and the test prints all of
them. What they show, which the source predicts (`src/dec/frame_dec.c`,
`vp8_dec.c`, `io_dec.c`, `vp8l_dec.c`):

- **VP8 parsing** always starts at macroblock row 0 and stops at
  `br_mb_y = (crop_bottom + 15 + extra) >> 4`, where `extra` is 0, 2 or 8 rows
  of filter margin for no, simple and complex filtering. A crop saves the rows
  below it, never the rows above it.
- **VP8 filtering**: the complex filter (type 2) filters every row from 0 to
  `br_mb_y`, because of its dependency chain; the simple filter (type 1) filters
  from `(crop_top - 2) >> 4` on. Scaling below 3/4 in both dimensions bypasses
  the in-loop filter (`WebPIoInitFromOptions`), which changes the pixels.
- **VP8 output**: `put()` receives only the cropped rows, at full resolution;
  scaling runs after reconstruction, inside the emit functions.
- **Horizontal cropping saves nothing** in VP8 or VP8L: every macroblock or
  pixel of the parsed rows is decoded.
- **VP8L** decodes every row from 0 to `crop_bottom` (`last_row`) and outputs
  only the cropped rows; scaling runs after full-resolution decoding.
- **The incremental decoder** parses every macroblock row of a VP8 image,
  whatever the crop: `DecodeRemaining` loops to `mb_h`, not to `br_mb_y`, and
  `VP8ProcessRow` emits nothing below the crop (source reading;
  `WebPIDecoder` exposes no counters).
- **Alpha** (`ALPH` chunk of a lossy image): `VP8DecompressAlphaRows` decodes
  alpha rows from 0 up to the last row it is asked for, so the same rows as the
  luma; with alpha dithering (pre-processed levels) it decodes the whole plane
  at once (source reading).

## Not-applicable checks

1. **`NULL` pointers** exist only at the C ABI (PORTING rule 8); every `NULL`
   case of `decode.h` is compared there (`abi_answers_null_and_invalid_arguments_as_c`).
2. **Pointer values.** The probes print plane positions relative to the memory
   that holds them, never addresses.
3. **Uninitialized library memory.** C allocates output buffers with `malloc`;
   Rust initializes every allocation (ADR 0003). The tests digest library memory
   only after a complete decoding, and during incremental decoding only the luma
   (and RGB) rows up to `last_y`: with rescaling, the U, V and alpha rows lag
   behind and are uninitialized in C. Caller memory is filled with a pattern and
   digested whole, including guard bytes.
4. **The two largest vectors** (`bryce.webp`, 11158 x 2156, and
   `lossless_big_random_alpha.webp`, 2048 x 2048) get the features, one default
   decoding in two colorspaces and the simple API in the Rust matrix, because a
   debug build takes minutes per decoding; the upstream scripts decode them
   through the Rust-linked `dwebp` (`bryce.webp` is in `libwebp_tests.md5`).
5. **`WebPGrabDecBuffer`** has no caller in libwebp v1.6.0 and is not exported
   (`webpi_dec.h` is internal); it is translated and not compared.
6. **The `huffman_fuzzer` smoke run** reached only a few hundred executions in a
   minute; most inputs ask for up to 65,535 Huffman tree groups, as in C.

### Inputs excluded from the oracle (PORTING rule 8)

1. **Signed overflow in `TransformOne_C`** (`src/dsp/dec.c:78`, WP6's
   `dsp/dec.rs`): crafted lossy streams whose dequantized coefficients exceed
   the range that upstream's comments assume (fuzzing finding above). C is
   undefined (UBSan reports it); the translation's `checked` and fuzz builds
   panic, and release builds wrap.
2. **`WebPIAppend` of zero bytes before any data**: C asserts `mem->buf !=
   NULL` and calls `memcpy` with a `NULL` destination.
3. **`WebPISetIOHooks` with a lossless image**: C's `VP8LDecodeImage` reads the
   caller's user data as `WebPDecParams`; Rust uses the decoder's parameters
   (deviation 9, ADR 0003).
4. **Caller memory with a negative stride**: C writes before the pointer,
   outside the buffer that `decode.h` describes; the C ABI rejects it
   (deviation 15).
5. **Input that overlaps caller output memory**, and overlapping planes passed
   to `WebPDecodeYUVInto` or `WebPINewYUVA`: the C ABI rejects them
   (deviation 15).
6. **`WebPMalloc(0)`**: C asserts `nmemb * size > 0` in debug builds; the ABI
   returns `malloc(0)`.

## Recorded deviations

1. **The slow copy of the incremental decoder.** After `FinishDecoding`
   copies into the caller's buffer, C copies the caller's buffer structure into
   its own `output` (`*output = *idec->final_output`), which `params.output`
   points at. Safe Rust cannot hold a second view of the caller's memory, so
   `params.output` becomes the caller's buffer, which has the same contents;
   the C ABI returns C's copy of the structure from `WebPIDecodedArea`, as C
   does. In the C ABI the decoder's own block stays allocated until
   `WebPIDelete` (C frees it at the copy).
2. **Simple API.** `Decode` returns the buffer where C returns its first plane
   and copies the side information into `keep_info` with `WebPCopyDecBuffer`;
   `WebPDecodeYUV` returns the buffer with its U and V offsets and strides.
3. **`...Into` functions.** A pointer and its size are one slice, and the
   functions return that slice where C returns the pointer.
4. **`WebPCopyDecBuffer`** gives `dst` a shared view of every region of `src`
   (`PlaneStorage::Shared`, ADR 0003), where C copies the pointers and marks
   `dst` external. **`WebPGrabDecBuffer`** moves the storage to `dst` and leaves
   `src` an empty storage of the same kind with its plane descriptions; in C,
   `src` keeps pointers into the memory that `dst` now owns, which safe Rust
   cannot express. No caller in libwebp v1.6.0.
5. **Freeing.** `WebPFreeDecBuffer` drops library memory; `WebPInitDecBuffer`
   and `WebPInitDecoderConfig` drop the old storage, where C zeroes the
   structure without freeing it.
6. **Mismatched union member.** A Rust buffer whose `u` holds the member that
   the colorspace does not select reads as a zeroed member (ADR 0003), so
   `CheckDecBuffer` rejects it and the incremental getters write zeros, as C does
   for its zeroed union before allocation. C would reinterpret arbitrary bytes
   of the other member; only Rust callers can build such a buffer, and the C ABI
   reads the member that the colorspace selects.
7. **`DoRemap` and the last partition.** With one partition, `mem.start`
   follows the token reader, which near the end of the input can be past its
   `buf_max`; C then moves `buf_max` (and `buf_end`) before the new buffer, a
   pointer that it never dereferences, and `VP8BitReaderSetBuffer` replaces both
   at once. Positions cannot be negative, so for the last partition only `buf`
   moves and the reset computes the other two, which is C's final state.
8. **Alpha chunk position.** The incremental decoder keeps C's
   `dec->alpha_data` as a position in its input. Once the alpha plane is
   decoded, C no longer moves it with the input and never reads it again; the
   stale position then gives whatever bytes are there, or none, and is not read
   either.
9. **Hooks.** `WebPISetIOHooks` takes a `Box<dyn VP8IoHooks>` (C: three
   function pointers and `user_data`, ADR 0003). With a lossless image the
   decoder's own parameters reach `VP8LDecodeImage` (C: undefined, exclusion 3).
10. **`WebPIDelete` is `Drop`.** It synchronizes the worker and tears the io
    down for a lossy decoding in progress. In map mode the caller's buffer is
    gone, so the alpha chunk is not passed; no row is pending at that point,
    because every call ends with the worker synchronized.
11. **Incremental getters.** `WebPIDecGetRGB` and `WebPIDecGetYUVA` return the
    region that holds a plane and the position of its first row (`PlaneRows`),
    where C returns pointers; the rows follow at the stride, which is negative
    for a flipped output.
12. **Allocation sizes.** `CopyParts0Data` tests `WebPSafeMalloc(1, size)` as
    `size` elements of one byte (the same decision). `NewDecoder`, `VP8New` and
    `VP8LNew` cannot fail; a refused host allocation of a fixed-size object
    aborts.
13. **`WebPHeaderStructure`** holds the input as a slice and `alpha_data` as a
    position in it; after a successful parse, `have_all_data` is false, as C's
    `*headers = hdrs` leaves it.
14. **C ABI memory.** One extra copy per decoding: the simple API copies the
    translation's buffer into a `malloc` block; a library buffer of `WebPDecode`
    and of the incremental decoder moves into one after the call that allocated
    it. If that `malloc` fails, the incremental decoder keeps the translation's
    memory and hands out pointers into it, which live as long as the decoder.
    Plane pointers of a library buffer whose memory was never allocated, or was
    released after a failed decoding, keep their previous C values (C: pointers
    to the freed memory).
15. **C ABI rejects** caller memory with a negative stride, input that overlaps
    caller output memory, and overlapping planes passed as separate slices
    (`WebPDecodeYUVInto`, `WebPINewYUVA`), with C's failure result (`NULL` or
    `VP8_STATUS_INVALID_PARAM`): Rust cannot form those slices (exclusions 4, 5).
    Overlapping planes of a `WebPDecBuffer` (`WebPDecode`, `WebPIDecode`,
    `WebPINewDecoder`) share one region and decode as in C.
16. **C ABI configuration copies.** `WebPIDecode` and `WebPINewDecoder` convert
    the caller's options and output buffer when the decoder is created; later
    changes by the caller are not seen, where C reads through its pointers. The
    caller's buffer receives the dimensions, strides, plane pointers and
    `private_memory` after every call.
17. **`VP8GetCPUInfo`** is exported from `src/abi/decode.rs`, because `dwebp`
    assigns it and no ABI module exports `src/dsp/cpu.h`. It points at the
    translation's query on x86 and is `NULL` elsewhere, as in the reference
    configuration; no dispatch reads it before wave 4.
18. **Consumer link shim.** `imageio/webpdec.c` references the demux API (WP8,
    exported by WP14) and `WebPPictureAlloc`/`WebPPictureFree` (exported by
    WP13), which `dwebp` never calls. `tools/oracle/probes/wp12/consumer/link_shim.c`
    defines them for the linker only; each aborts if called. It is test
    harness, not library, and goes away when WP13 and WP14 export the real
    functions. (Integrator, 9 November 2026: WP14 exported the demux API and
    deleted the file in PR 20; the copied upstream targets now link
    `libwebpdemux` as the Rust library, `tools/oracle/probes/wp12/oracle.cmake`.)
19. **Fuzz targets.** FuzzTest domains become one `arbitrary` tuple (the
    colorspace is taken modulo `MODE_LAST`), and `kFuzzPxLimit` keeps its value
    without sanitizers. The targets keep upstream's names, which nightly cargo's
    `non_kebab_case_bins` lint warns about.

## Notes for the packages that build on WP12

- **WP8 (demux).** Frame validation: `webp_get_features(data, &mut features)`
  in `src/webp/decode.rs` (C: `WebPGetFeatures`), or
  `webp_get_features_internal(data, &mut features, version)` in
  `src/dec/webp_dec.rs`; both return `Result<(), VP8StatusCode>` and write the
  features also on failure, as C does. `webp_parse_headers` and
  `WebPHeaderStructure` locate the VP8/VP8L chunk and the `ALPH` payload.
- **WP13, WP14 (fuzz targets).** Add a `[[bin]]` per target to
  `fuzz/Cargo.toml` with `test = false`, `doc = false` and `bench = false`, a
  file in `fuzz/fuzz_targets/` with `#![no_main]`, upstream's notice and
  `#[path = "fuzz_utils.rs"] mod fuzz_utils;` for `FuzzHash` and
  `kFuzzPxLimit`, and a row in `fuzz/README.md`. Structured inputs use
  `libfuzzer_sys::arbitrary`; no new dependency. Build with `cargo +nightly fuzz
  build`, which enables overflow checks: triage a panic on arithmetic against the
  asan-ubsan oracle, which reports C's undefined overflow (exclusion 1).
- **WP13, WP14 (ABI pattern).** One module per header; `#[repr(C)]` mirrors with
  a layout probe (`tools/oracle/probes/wp12/layout.c` and
  `tests/wp12_abi_layout.rs` show the pattern); `NULL` and invalid arguments
  first, with C's result; one unsafe operation per block. Memory that C
  releases with `WebPFree()` comes from `crate::abi::types::malloc_copy` or
  `platform_malloc`. Lend caller memory per call (`Lent` in `src/abi/decode.rs`)
  instead of keeping Rust borrows of it in a long-lived object. When WP13
  exports `WebPPictureAlloc`/`WebPPictureFree` and WP14 the demux API, delete the
  corresponding stand-ins from `consumer/link_shim.c` (or the file), or the
  consumer link fails on duplicate symbols. The decode probe also builds as
  `probes/wp12/decode_rs`; `tools/oracle/probes/wp12/oracle.cmake` shows how a
  probe is linked against the Rust library.
- **WP16 (safe decoder API).** What the translation offers:
  - Features: `webp_get_features(data, &mut WebPBitstreamFeatures)`.
  - Advanced API: `webp_decode(data, &mut WebPDecoderConfig)`. For a caller
    `&mut [u8]` or planar slices, set `config.output.storage =
    PlaneStorage::External(slices)` and the `u` member that matches the
    colorspace (plane regions and offsets, strides, sizes); the buffer is
    checked with C's rules, where the sizes are the struct fields, so keep them
    equal to the slice lengths. Library memory is `PlaneStorage::Internal`.
    Cropping, scaling, flip, threads and dithering are `config.options`.
    `config.output.slow_memory = true` on external storage selects C's slow
    path for premultiplied output of an image with alpha: decode into a
    temporary buffer, copy at the end.
  - Simple API: `webp_decode_rgba(data, ...) -> Option<Vec<u8>>` and friends,
    `webp_decode_yuv` (owned buffer), `webp_decode_*_into(data, &mut [u8],
    stride)`, `webp_decode_yuv_into`.
  - Incremental: `webp_i_decode(&[], Some(&mut config))` (or
    `webp_i_new_decoder`, `webp_i_new_rgb`, `webp_i_new_yuva`), then
    `webp_i_append(&mut idec, chunk)` or `webp_i_update(&mut idec, all_so_far)`,
    which return `Err(VP8_STATUS_SUSPENDED)` until the image is complete.
    `webp_i_decoded_area(&idec, ...)` returns the output buffer and the number
    of rows decoded so far (`params.last_y`); `webp_i_dec_get_rgb` and
    `webp_i_dec_get_yuva` return `PlaneRows` (region and first-row position).
    The decoder borrows the configuration until it is dropped; the output
    buffer, with its memory, stays in the configuration afterwards.
  - Cropping: see the measurement above. A cropped decoding saves the rows
    below the crop for VP8 (`WebPDecode`) and VP8L, nothing for horizontal
    crops, and nothing in the incremental decoder for VP8 parsing.
