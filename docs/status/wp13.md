# WP13: encoder integration

- Status: every unit of the WP13 inventory is translated, and the C ABI of
  `encode.h` is exported. `WebPEncode` writes byte-identical files with
  identical `WebPAuxStats` to the C oracle over the encoder matrix of
  [PORT_PLAN.md](../PORT_PLAN.md) (Phase 3), through the Rust API and through
  the C ABI. Upstream's `cwebp`, unmodified and linked against the Rust
  library, passes `test_cwebp.sh` on every test-data file it reads, in three
  option sets, with the oracle's output bytes. The `fuzz/` crate has
  `enc_fuzzer` and `enc_dec_fuzzer`.
- Sub-wave: 3b
- Model: Claude Opus 5.5 (`claude-opus-5-5`)
- Depends on: WP9, WP10, WP11, WP12 (all merged); takes over the WP9, WP10 and
  WP11 modules for integration fixes
- Probes: `tools/oracle/probes/wp13/`; tests: `tests/wp13_*.rs`, with the shared
  support in `tests/support/wp13_cases.rs` (records and the Rust replay) and
  `tests/support/wp13_matrix.rs` (the case groups)

Written by the package session; the integrator aggregates it into
[PORT_STATUS.md](../PORT_STATUS.md). See the package's row in
[WORKPLAN.md](../WORKPLAN.md) for its verification inputs. The inventory
comes from `tools/units.json`, including the function- and type-level

## Decisions applied

The brief settled these before the translation; the recorded deviations say how
they are applied.

- **`webp_encode(config: &WebPConfig, pic: &mut WebPPicture<'_>) -> bool`**
  follows `WebPEncode` step by step, with WP10's lossy sequence and WP11's
  `vp8l_encode_image`. The progress hook and the writer run on the calling
  thread.
- **Views are encodable.** Where `WebPEncode` writes into the picture (the
  transparent-area cleanup, `show_compressed`), a `PlaneStorage::Shared` view
  first gets its own copy of the planes (deviation 1). The C ABI never makes a
  shared view: caller memory is lent as `External` storage, so C callers see
  C's behavior.
- **Simple API**: `Encode` and the eight `WebPEncode*` functions return
  `Option<Vec<u8>>`; the C ABI hands out `malloc` memory that C releases with
  `WebPFree()`.
- **C ABI** (ADR 0004): `repr(C)` mirrors of `WebPPicture` and
  `WebPMemoryWriter`; `WebPConfig` and `WebPAuxStats` are shared, after a layout
  probe. A C picture is converted per call, after WP12's `WebPDecBuffer`
  pattern, and written back after every call. Memory that `WebPPictureAlloc`
  allocates and `WebPPictureFree` releases is a platform `malloc` block of C's
  size in `memory_` and `memory_argb_`.
- **Consumer build**: `rs_cwebp` (upstream's `examples/cwebp.c`, unmodified) in
  `tools/oracle/probes/wp13/oracle.cmake`, through WP12's `libwebp_rs` target and
  `wp12_consumer()`, next to WP12's tools as `probes/wp12/cwebp`; the encode and
  api probes also build against the Rust library as `probes/wp13/encode_rs` and
  `api_rs`.

## Not-applicable checks

1. **`NULL` arguments** exist only at the C ABI (PORTING rule 8); the ABI test
   compares every one with C.
2. **`WEBP_DISABLE_STATS`** is undefined, so `StoreStats` copies the statistics
   and has no progress report of 100 percent, and `GetPSNR` and `FinalizePSNR`
   exist.
3. **`WEBP_REDUCE_CSP` and `WEBP_REDUCE_SIZE`** are undefined, so the BGR
   functions of the simple API exist, and so do `WebPPictureCopy`, `Crop` and
   `Rescale` in the C ABI.
4. **SIMD**: none in the reference configuration. The fuzz targets drop
   `SetOptimization`, which only selects SIMD paths.
5. **Floating point.** `log10` in `GetPSNR`, the float conversion of
   `FinalizePSNR`, the dithering amplitude of `WebPEncode` and every float of the
   statistics are compared bit for bit on this host (ARM64, Apple clang,
   `-ffp-contract=off`); equality on other hosts is recorded, not assumed
   (PORTING).
6. **Allocation failures.** No compared input reaches `WEBP_MAX_ALLOCABLE_MEMORY`,
   and host allocation failures (the translation's or the ABI's `malloc`) are not
   injected.
7. **Threads**: nothing new; `thread_level` 0 and 1 are matrix dimensions, and the
   alpha worker (WP10) and the lossless side thread (WP11) are compared through
   them.
8. **32-bit targets** are not run.
9. **Input formats.** The oracle on this host reads PNG (libpng) but not TIFF;
   the tools test selects the inputs that the oracle's `cwebp` reads, so a host
   without libpng runs the script on the other files. The encoder matrix reads
   `grid.pam` and `peak.pam`, the pictures of `grid.png` and `peak.png`.
10. **`cwebp -metadata` on WebP input** calls the demux API, which WP14 exports;
    WP12's link stand-ins abort there, and no test uses it.

## Recorded deviations

Deviations are changes of representation that the ADRs allow, or behavior that
the Rust side cannot reproduce exactly. Each records the reason.

1. **Views in `webp_encode`.** A view (`PlaneStorage::Shared`, WP9 deviation 8)
   cannot be written. Where `WebPEncode` writes into the picture's planes (the
   transparent-area cleanup unless `exact`, `show_compressed`, the replacement of
   transparent pixels before a lossless encoding), the view first gets its own
   copy of the planes, with the same strides and samples (`own_shared_yuva`,
   `own_shared_argb`), so the encoding is byte-identical; C writes through the
   view into the source picture, which the translation leaves untouched. The copy
   reserves fallibly and records `VP8_ENC_ERROR_OUT_OF_MEMORY` when the host
   refuses, an allocation that C does not make. The C ABI lends caller memory
   exclusively, never as a view, so C callers see C's writes.
2. **Simple API.** `Encode` returns the written bytes as a vector of the writer's
   `size`, where C hands out the writer's buffer of `max_size` bytes; the C ABI
   copies them into a `malloc` block of `size` bytes (one copy per call). C's
   `WebPMemoryWriterInit` follows the writer assignment; the closure borrows the
   writer, so the translation initializes it just before.
3. **C ABI pictures per call.** The library's blocks (`memory_`,
   `memory_argb_`) are copied into the translation's storage for each call and
   back afterwards (one copy of the picture per call; the copy reserves fallibly,
   and a refused reservation fails the call with `VP8_ENC_ERROR_OUT_OF_MEMORY`
   where the function records errors). Caller planes are lent only where C's
   path reads or writes them, with the extent that their dimensions and strides
   address, `(height - 1) * stride + width` samples: as `PlaneStorage::External`
   to a call that writes them and as `PlaneStorage::Shared` to one that only
   reads them (`WebPPictureCopy`'s source, `Distortion`, the input of a
   conversion), so that a source and a reference may share memory.
   `WebPPictureHasTransparency` lends only the alpha plane of a YUV picture or the
   ARGB plane of an ARGB picture. `WebPPictureView` only computes addresses: it
   lends each plane as an empty region with the plane at a large offset, so that
   the translation's offsets give C's pointer arithmetic for any stride. Calls
   that do not touch a storage (`WebPPictureAlloc`, `Free`, the importers, a
   conversion's output, the storage that `use_argb` does not select) lend
   nothing there. `WebPEncode` lends the planes of C's path: the YUVA planes for
   a lossy encoding of a YUV picture (written by the cleanup and
   `show_compressed`), the ARGB plane for a lossy encoding that converts it, the
   ARGB plane for a lossless encoding (written when transparent pixels are
   replaced) or the YUVA planes when it is `NULL` and C converts them, and nothing
   when the configuration or the picture fails C's validation. It never reads
   the caller's `*stats` or `extra_info`, which may be uninitialized (`cwebp`
   passes an uninitialized `WebPAuxStats` and a `WebPMalloc`ed map): the
   translation gets zeroed copies; the statistics go back to `*stats` once
   `WebPValidateConfig`, `WebPValidatePicture` and the dimension limit have
   passed, where C resets and fills them. The map goes back to `extra_info`
   whenever the lossy encoder ran, also after a user abort or a write failure:
   C fills it one macroblock at a time (`StoreSideInfo` in `VP8EncLoop` and
   `VP8EncTokenLoop`), so the filled prefix is C's, and the unfilled entries are
   zero where C leaves them untouched. After a lossless encoding the map goes
   back only on success, where C zeroes it; after a failed validation nothing
   is written, as in C. The encode probe zeroes the map before the call, so the
   ABI test compares every case byte for byte, the failed lossy encodings with a
   partly filled map included. A C callback that reads `picture->stats`, `extra_info`
   or another picture field during the encoding sees the values from before the
   call; no upstream callback reads them (ADR 0003, "Concrete callback forms").
   The callbacks receive the caller's picture pointer.
4. **C ABI rejects** a plane that a call reads or writes when it has a negative
   stride over more than one row (Rust cannot lend memory before the pointer),
   planes that a writing call would write and that overlap, and such an ARGB plane
   when it is not aligned for `uint32_t`: Rust cannot lend those slices (as WP12,
   deviation 15). Planes that the call does not touch are never checked (the
   unselected storage, any plane for `WebPPictureView`, the luma and chroma
   planes for `WebPPictureHasTransparency`, the planes outside C's path in
   `WebPEncode`; `abi_accepts_the_layouts_that_c_never_reads` covers misaligned
   pointers with negative strides there, and upside-down planes for views).
   Functions that record errors return 0 with
   `VP8_ENC_ERROR_INVALID_CONFIGURATION`; `WebPPictureCopy`, `Distortion` and
   `HasTransparency` return 0; `WebPCleanupTransparentArea` and `WebPBlendAlpha`
   do nothing. Packed input rows with a negative stride (the importers, the
   simple API) are copied into rows with a positive stride, which hold the same
   bytes, so C's results stay; the copy reserves fallibly, and a refused
   reservation fails the import with `VP8_ENC_ERROR_OUT_OF_MEMORY` (the simple
   API returns 0). Rows with a positive stride are lent as they are. Rows of a
   picture without width are passed with the stride 0, since `Import` reads none
   of them.
5. **`WebPPictureIsView`** passes C's `memory_` and `memory_argb_` to the
   translation as the ownership of the storage, which is what the translation
   reads. A picture whose `memory_` is set while its planes point elsewhere
   converts as caller memory in the other functions (they never read
   `memory_` apart from releasing it, which the ABI does as C does).
6. **`WebPPictureCopy` and `WebPPictureView` in the C ABI** copy the C struct
   itself (`PictureGrabSpecs`), so a C copy or view shares the writer,
   `custom_ptr`, progress hook, `user_data`, `stats` and `extra_info` of its
   source, as in C; WP9 deviation 9 (no callbacks) holds for the Rust API only. As
   in C, the copy does not release the memory its destination held before.
7. **New samples in the C ABI** go into a new `malloc` block (or into the block
   the picture holds when the sizes agree). If that `malloc` fails, the old
   memory is released, the planes are `NULL` and the call returns 0 with
   `VP8_ENC_ERROR_OUT_OF_MEMORY`.
8. **`WebPMemoryWrite` in the C ABI** gives the translation a copy of the
   written bytes and copies the new ones back, or the whole buffer into a new
   block of the translation's capacity when it grows (one copy of the written
   bytes per call). The copy reserves fallibly; a refused reservation returns 0,
   as C does when its buffer cannot grow.
9. **`WebPPictureDistortion` in the C ABI** writes `result` only on success; C
   writes the channels it measured before an allocation failure.
10. **`WebPConfigInitInternal` in the C ABI** reads the reserved
    `use_delta_palette` as possibly uninitialized bytes and writes it back, so the
    caller's value stays, as in C (WP9 deviation 14).
11. **Undefined `NULL` arguments.** `WebPMemoryWriterInit(NULL)` returns and
    `WebPMemoryWrite` with a `NULL` picture returns 0, where C dereferences them.
12. **Fuzz targets.** The FuzzTest domains become one `arbitrary` tuple; the 24
    values of `ArbitraryWebPConfig` pick their field's range by modulo. The
    optimization index is dropped (not-applicable check 4). imageio's PNG, JPEG,
    TIFF and PNM readers have no Rust counterpart, so `enc_fuzzer` reads WebP
    input only, with a port of `ReadWebP` that decodes into the library's memory
    and copies the samples into the picture's planes, where C decodes into them.
    The source images of `img_*.h` are read from upstream's headers at compile
    time. The targets keep upstream's names (cargo's `non_kebab_case_bins`
    warning, as WP12 records).
13. **`SharpYuvGetVersion`.** `cwebp -version` prints SharpYUV's version, which
    the Rust library does not export (ADR 0004 exports no SharpYUV header); the
    consumer build links a stand-in that aborts if called. No test calls
    `-version`.
14. **Lint expectations** name the C construct (ADR 0005): the float conversions
    of `GetPSNR` and `FinalizePSNR`, and the arguments of the ABI helpers that
    mirror C's signatures.
15. **Re-entrant callbacks.** While `WebPEncode` runs, the caller's planes are
    lent exclusively to the translation, so a writer or progress hook must not
    call a library function on the picture being encoded, which C allows (for
    example `WebPPictureHasTransparency(picture)` or
    `WebPPictureDistortion(picture, ...)` from the hook): it would lend memory
    that a live `&mut` slice covers. No upstream callback does it. Pictures in
    library memory are not affected, since the translation works on a copy of
    their block (deviation 3). The module documentation of `src/abi/encode.rs`
    states the restriction.
16. **Picture blocks.** The C ABI records the address and size of every block it
    gives a picture as `memory_` or `memory_argb_`, and assumes, as `encode.h`
    requires, that C releases it only through `WebPPictureFree` or the functions
    that replace the planes. A block that C frees itself stays recorded; caller
    memory that later lands at the same address in `memory_` would be copied at
    the recorded size.

## Undefined behavior excluded from the oracle

Rule 8 of PORTING: the C code has undefined behavior on these inputs, so they
are excluded from the comparison, in every variant. WP10's exclusions hold for
`WebPEncode` (1 to 3), and WP9's for the importers (4):

1. **Uninitialized lossless statistics of uncompressed alpha**
   (`alpha_compression` 0): the encoder tests request no statistics for such
   pictures, and `cwebp -alpha_method 0` reports are compared only up to the
   lossless-alpha block, which C prints from uninitialized memory (for example a
   size of 2139062143) and the translation does not print.
2. **`extra_info_type` 6**, which reads uninitialized bit counts: not used.
3. **Statistics of threaded alpha encodings that fail** (data race): not
   requested.
4. **`WebPPictureImportRGBA` into an ARGB picture with misaligned rows** (and
   `WebPEncodeLosslessRGBA`, which uses it): `VP8LConvertBGRAToRGBA` loads the
   rows as `uint32_t`, which is undefined when a row start is not 4-byte aligned
   (`docs/status/wp9.md`); the asan-ubsan oracle reports it. The ABI and simple
   API tests generate no such rows.

C assertions excluded from the oracle:

1. **`WebPPlaneDistortion` with an `x_step` other than 1 on an empty plane**
   calls `WebPSafeMalloc` with a size of 0, which fails
   `assert(nmemb * size > 0)` in the debug oracle; the ABI test does not
   generate it. The release oracle and the translation both go on.

Uninitialized samples are not compared: the planes that `WebPPictureAlloc`
allocates hold `malloc` memory in C (the asan-ubsan oracle fills it with a
pattern) and zeros in the translation, so the api probe prints only which
planes exist after `alloc`.

The `asan-ubsan` and `debug` oracle variants found case 4, the assertion and
the uninitialized samples, and nothing else; see "Local runs".

## Upstream behavior preserved

- `WebPEncode` does not report 100 percent itself (the encoders do, or not, as
  WP10 and WP11 record), and it resets `error_code` before it validates.
- `WebPPictureAlloc(NULL)` and `WebPPictureInitInternal(NULL, version)` return 1;
  `WebPPictureCopy(pic, pic)` returns 1 without copying.
- `WebPMemoryWriterInit` does not release the previous buffer.
- `WebPConfigPreset` with an invalid quality writes the configuration and
  returns 0, so the simple API returns 0 without writing `*output`; every other
  failure writes `NULL`.
- With `exact` off, `WebPEncode` cleans the transparent area of a YUV picture
  (lossy) or replaces transparent ARGB pixels by 0 (lossless) in the caller's
  planes, which the caller sees afterwards (the `pic=` and `caller=` digests).

## Mutation checks

Fifteen mutations of the translation were tried, each against
`tests/wp13_encode.rs` and `tests/wp13_simple.rs`. Fourteen are caught: the 99 dB
cap of `GetPSNR`, the sample count of the overall PSNR (`size * 3 / 2`) and of the
alpha PSNR, the dithering amplitude, the `preprocessing` bit that selects sharp
YUV, the transparent-area cleanup, the color that replaces transparent pixels,
the source of `segment_level`, the dimension limit (`>` against `>=`), the reset
of the statistics, `LOSSLESS_DEFAULT_QUALITY` (70 against 69, 71 and 75, once the
simple-API test had a repetitive picture), `use_argb` of the lossless simple API,
the size of the simple API's output, and the copy of a view's planes for
`show_compressed`. One is equivalent: freeing the bit writers early on failure
(`VP8EncFreeBitWriters`), which the drop of the encoder does anyway.

## Notes for the packages that build on WP13

- **WP15 (mux and animation encode).** `webp_encode(&config, &mut pic)` in
  `src/enc/webp_enc.rs` encodes a picture through `pic.writer`, a
  `Box<dyn FnMut(&[u8]) -> bool>` (`webp_memory_write` into a
  `WebPMemoryWriter` behind a `RefCell` is the memory writer). The picture API is
  WP9's: `webp_picture_copy` and `webp_picture_view` give pictures without
  callbacks (WP9 deviation 9), so set the writer on each picture you encode; a
  view (`PlaneStorage::Shared`) can be encoded, and gets its own planes where
  `WebPEncode` writes (deviation 1). `anim_encode.c` blends and compares frames
  with `WebPPictureDistortion`-like code on views: those are read-only. For the
  C ABI of `mux.h`, `src/abi/encode.rs` has the `WebPPicture` mirror (public) and
  the per-call conversion (`picture_to_rust`, `picture_to_c`, private); if
  `src/abi/mux.rs` needs to convert pictures, ask the integrator to make them
  `pub(crate)` rather than copying them.
- **WP17 (safe encoder API).** What the translation offers:
  - Configuration: `webp_config_init`, `webp_config_preset` (`src/webp/encode.rs`),
    `webp_config_lossless_preset`, `webp_validate_config`
    (`src/enc/config_enc.rs`).
  - Pictures: `webp_picture_init`; import from strided RGB, RGBA, RGBX, BGR, BGRA
    or BGRX rows (`webp_picture_import_*`, `src/enc/picture_csp_enc.rs`, into YUV
    or ARGB as `use_argb` selects); YUVA planes in caller memory as
    `PlaneStorage::External` (one slice per plane, Y, U, V, A, each with its
    stride), or owned planes from `webp_picture_alloc`; views with
    `webp_picture_view`. Negative strides panic (WP9 deviation 7).
  - Output: `pic.writer = Some(Box::new(|bytes| ...))`, which returns `false` to
    fail with `VP8_ENC_ERROR_BAD_WRITE`; or `WebPMemoryWriter` with
    `webp_memory_write`.
  - Progress and abort: `pic.progress_hook = Some(Box::new(|percent| ...))`;
    `false` aborts with `VP8_ENC_ERROR_USER_ABORT`, and the output written so far
    stays with the writer.
  - Errors: `webp_encode` returns `false` and `pic.error_code` holds the
    `WebPEncodingError` (C's first-error rule); allocation failures are
    `VP8_ENC_ERROR_OUT_OF_MEMORY` (the translation reserves fallibly).
  - Statistics: `pic.stats = Some(&mut stats)`, `pic.extra_info` and
    `extra_info_type`.
  - Threads: `thread_level` 1 uses scoped threads and the alpha worker inside the
    call; the writer and the hook run on the calling thread and need not be
    `Send`.
  - Simple API: `webp_encode_rgb` and friends (`src/enc/picture_enc.rs`) return
    `Option<Vec<u8>>`.
- **WP19, WP20 (SIMD).** Nothing new beyond WP10's and WP11's dispatch notes:
  `WebPEncode` and the simple API call no DSP function of their own.
