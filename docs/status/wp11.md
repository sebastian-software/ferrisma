## Decision: the side context of `VP8LEncodeStream` on a scoped thread

The integrator decided on 2026-11-07 (WP6 adds the ADR 0003 "Threads"
amendment in its pull request): `VP8LEncodeStream` runs the side
`StreamEncodeContext` on a `std::thread::scope` thread when `thread_level > 0`
splits the crunch configurations, because WP1's `WebPWorker::reset` requires
`Send + 'static` jobs and the side context borrows the picture and the
configuration. The main context runs on the calling thread, as C's `Execute`
does; thread creation failure is C's failed `Reset` (`VP8_ENC_ERROR_OUT_OF_MEMORY`),
the join of the scope is the two `Sync` calls, and a panicking side context
counts as a failed hook. Deviation 9 records how the picture is shared. The
contexts share nothing they write, and the probe compares threaded encodings
byte for byte.

## Not-applicable checks

These checks do not apply to WP11, or cannot be made on this host, with the reason:

1. **SIMD variants.** `lossless_enc_sse2.c`, `lossless_enc_sse41.c`,
   `lossless_enc_avx2.c`, `lossless_enc_neon.c` and the `_SSE` pointers of
   `lossless.h` are wave 4 (WP18 to WP20). MIPS (`lossless_enc_mips32.c`,
   `lossless_enc_mips_dsp_r2.c`, `lossless_enc_msa.c`) is excluded in
   `tools/units.json`.
2. **`VP8LEncDspInit`** calls `VP8LDspInit` and assigns portable pointers; both
   only assign pointers, so ADR 0003 omits them. The tables are static arrays
   with the entries of the C initialization, including the sentinels at 14 and
   15, and the dispatch functions call the portable code.
3. **`WEBP_HAVE_SLOW_CLZ_CTZ`.** GCC and Clang define `BitsLog2Floor` with the
   builtin, so the shifting loop of `FastLog2Slow_C` and `FastSLog2Slow_C` is
   compiled out; only the `BitsLog2Floor` branch is translated.
4. **`WEBP_NEAR_LOSSLESS == 0`.** The reference configuration enables
   near-lossless; the other branch of `near_lossless_enc.c` defines only the
   empty `VP8LNearLosslessStub`, and `predictor_enc.c` and `vp8l_enc.c` lose
   their near-lossless code.
5. **`WEBP_DISABLE_STATS`** is unset in the reference configuration, so the
   statistics code is translated and compared.
6. **`NULL` arguments.** `VP8LEncodeImage` with a `NULL` picture (returns 0) or
   configuration exists only at the C ABI (PORTING rule 8); the Rust functions
   take references.
7. **Host refusals of an allocation.** The size tests of `WebPSafeMalloc` and
   `WebPSafeCalloc` are reproduced with the C totals (deviation 3), but a refusal
   by the host of an accepted size cannot be provoked here; the Rust code fails
   where C fails (`try_reserve`). The fixed-size structures that C allocates
   once (`VP8LEncoder`, `CostManager`, `CostModel`, `Histograms`) are Rust values
   or boxes; their size tests always pass in C.
8. **Thread creation failure** (C's failed `WebPWorker` `Reset`) and a panicking
   side context cannot be provoked; deviation 9 says what the Rust code does.
9. **Floating point.** `GetBinIdForEntropy` computes in `double`, and the slow
   logarithms use `log` above 65,535. They are compared bit for bit on this
   host (macOS on Apple Silicon, Apple clang, `-ffp-contract=off`), through the
   clustering and the encoded files; equality on other hosts is recorded, not
   assumed.
10. **Type sizes on other hosts.** The `C_SIZE` constants follow the 64-bit
    layout; this host (arm64) checks them, and the x86-64 CI host checks them
    again. 32-bit targets are not built.
11. **Uninitialized C memory.** The transform buffer, the histograms, the queue
    and the block storage are `malloc`ed in C and zeroed in Rust (ADR 0003).
    Every compared output is written before it is read; the predictor probe
    fills its scratch rows with 0xa5 bytes against the Rust zeros and still
    matches.
12. **LeakSanitizer** does not run on macOS; Linux CI runs it with the
    asan-ubsan oracle. The probes free what they allocate.
13. **Big-endian hosts.** The `max_diffs` bytes of the predictor scratch are
    written by `MaxDiffsForRow` and read by `GetResidual` only, both in native
    byte order, so the byte order cannot change a result; the host is
    little-endian.

### Inputs excluded from the oracle (PORTING rule 8)

The C code is undefined, asserts, or calls a `NULL` pointer on these inputs, so
no test issues them:

1. Pictures large enough that the `int` progress products overflow, such as
   `percent_range * pos` in `VP8LHashChainFill` (about 100 million pixels);
   the tests stay far below.
2. A picture without a writer: C calls the `NULL` pointer; Rust panics.
3. `thread_level > 0` with `use_argb == 0` but an ARGB plane: the side
   picture, a view, gets no ARGB plane and C reads through `NULL`.
4. Configurations and pictures that `WebPValidateConfig` and
   `WebPValidatePicture` reject (quality outside 0 to 100, where the `int`
   conversion is undefined for NaN and infinities; method outside 0 to 6;
   dimensions outside 1 to 16,383), and an `extra_info` shorter than the
   macroblock count, which C overruns.
5. `VP8ApplyNearLossless` with quality 100 (C asserts `limit_bits > 0`; the
   encoder calls it only below 100), `VP8LExtraCost` with an odd or short length,
   `VP8LResidualImage` and `VP8LColorSpaceTransform` with bits outside 2 to 9,
   and the prefix encodings with negative distances.

## Recorded deviations

Deviations are changes of representation that the ADRs allow, or behavior that
the Rust side cannot reproduce exactly. Each records the reason.

1. **Encoder context per call.** `VP8LEncoder` stores neither `config` nor
   `pic`, as ADR 0003 decides for the decoders ("Decoding context per call"):
   every function that reads them takes `config: &WebPConfig` and
   `pic: &mut WebPPicture` per call. `VP8LEncoderNew` returns a value; C's
   failed allocation of the fixed-size encoder cannot happen (not-applicable
   check 7).
2. **Transform memory.** `transform_mem` is one `Vec<u32>` with C's total size,
   and `argb`, `argb_scratch` and `transform_data` are positions in it (ADR 0003,
   pointers); `transform_regions` splits it into the three regions. C aligns the
   addresses with `WEBP_ALIGN`; the Rust positions are aligned as for an aligned
   base, which only moves scratch data. The `max_diffs` bytes of the predictor
   live in the scratch words behind the two pixel rows, as in C, and are read
   and written in native byte order (`byte_at`, `set_byte_at`).
3. **Allocation totals.** Where C allocates one block and carves several arrays
   from it (the reference blocks, the histogram sets, the cost model, the
   Huffman code arrays of `GetHuffBitLengthsAndCodes`, WP3 deviation 7), the
   Rust code applies the size test of `WebPSafeMalloc` to the C total, including
   `sizeof` of the header and `WEBP_ALIGN_CST` padding, before it allocates
   separate buffers (`safe_malloc_test` reserves zero-sized elements, so it
   allocates nothing). The `C_SIZE` constants are compared with the C compiler.
4. **Backward references.** `VP8LBackwardRefs` keeps its used blocks in a vector
   in the order of the C chain and its free blocks in another, with the head of
   the C free list last; `tail` and `last_block` always point at the end of the
   chain in C, so they are derived. `VP8LClearBackwardRefs` moves the used blocks
   ahead of the free ones, as C links them. `VP8LRefsCursor` holds the block
   index and positions, and `VP8LRefsCursorNext` and `VP8LRefsCursorNextBlock`
   take the references, which C reaches through the block's `next` pointer.
   `BackwardRefsSwap` swaps the values; C's fix-up of the `tail` pointers has no
   counterpart. `error` is a `bool`.
5. **Histogram sets keep C's pointer array.** `VP8LHistogramSet` owns its
   histograms in `memory` and keeps `histograms` as C's array of pointers into
   it, as indices (`None` for `NULL`). `HistogramSetRemoveHistogram` copies the
   last pointer, so the slot behind `size` still refers to the moved histogram,
   which `HistogramCombineStochastic` reads before it renumbers its pairs.
   `HistogramSwap` swaps the box of `cur_combo` with the box that
   `histograms[first]` points to; no other slot below `size` points there. A
   histogram's `literal` array holds the codes of the cache bits it was
   allocated with; `HistogramClear` zeroes `VP8LHistogramNumCodes(palette_code_bits)`
   of them, as the C `memset` covers, and `VP8LHistogramSetClear` zeroes
   everything and resets the pointers, as C clears the whole block.
   `HistogramAdd` takes `None` for `h2` where C passes `h2 == hout`.
6. **Free-only functions.** `VP8LFreeHistogram`, `VP8LFreeHistogramSet` and
   `VP8LEncoderDelete` only free; their owners drop the values at the same
   points, as for `VP8LHtreeGroupsFree` (WP3 deviation 6). `DeleteIntervalList`
   is kept, but the intervals live in the manager's arena until
   `CostManagerClear` drops it.
7. **Cost manager.** The intervals are an arena of `CostInterval` values with
   `previous` and `next` as indices; its first `COST_MANAGER_MAX_FREE_LIST`
   entries are C's `intervals[]` array, and the intervals C allocates one by one
   are pushed behind them (a failed reservation serializes the interval, as a
   failed `WebPSafeMalloc` does). `cost_cache` is a heap vector of `MAX_LENGTH`
   entries, and the manager borrows `dist_array`, which C stores as a pointer.
   `CostManagerInit` returns the manager or `None`, where C fills the calloc'd
   manager and returns 0 after clearing it.
8. **Out-parameters and positions.** `VP8LPrefixEncodeBits`,
   `VP8LPrefixEncode`, `VP8LHashChainFindCopy`, `GetPopulationInfo` and
   `TraceBackwards` return tuples; `TraceBackwards` returns the position of the
   chosen path in `dist_array`. `GetBestPredictorsAndSubSampling` returns the
   subsampling index whose modes C returns as a pointer, and the modes of every
   subsampling are positions in one `modes_raw` vector. `VP8LHashChainFill`
   reads the hash chain that it keeps in `offset_length` as `int32_t`, as C does
   through its cast.
9. **Threads (integrator decision of 2026-11-07, ADR 0003 "Threads" amendment
   of WP6).** The side context runs on a `std::thread::scope` thread, the main
   context on the calling thread. `WebPPicture` holds the writer and progress
   closures, which are not `Send`, so the side picture, a view of the whole
   picture as in C, crosses the thread as `PictureViewParts` (its fields
   without the four that a view has as `None`) and is rebuilt on the thread.
   While the side thread borrows the planes, the main context works on a second
   view of the picture whose progress hook forwards to the picture's hook; the
   picture's `stats` and progress hook leave the picture for that time and come
   back afterwards, and the view's error code is recorded on the picture after
   the join, before C's test of `picture->error_code`. With one context the
   main context works on the picture itself. A thread that cannot be created is
   C's failed `Reset` and records `VP8_ENC_ERROR_OUT_OF_MEMORY`. A panicking side
   context counts as a failed hook; its error code is then unknown, which C
   asserts cannot happen: the Rust code debug-asserts and otherwise behaves as C
   does when the side's error code is `VP8_ENC_OK`.
10. **Bit writer copies.** `VP8LBitWriter bw_init = *bw` copies a struct whose
    buffer pointer C never reads through the copy; `bit_writer_snapshot` copies
    the pending bits, the cursor and the error flag without a buffer.
11. **`ApplyPalette`** returns the error code that C records on the picture
    after its row allocation fails, and `MapImageFromPalette` records it, because
    the source pixels are borrowed from the picture. The outcome is the same.
    `APPLY_PALETTE_FOR` is a function over the color-to-index closure.
12. **Return types (ADR 0003, errors).** Functions whose every failure records
    an error return `Result` with the recorded code; those that end with
    `return pic->error_code == VP8_ENC_OK` return that state as a `Result`
    (`VP8LGetHistoImageSymbols`, `EncodeImageNoHuffman`, `EncodeImageInternal`,
    `VP8LEncodeStream`, `VP8LEncodeImage`). Functions with a failure that records
    no error stay `bool`: `VP8LResidualImage` and `ApplyPredictFilter` (a failed
    modes allocation), `VP8ApplyNearLossless`, `EncoderAnalyze`, `EncoderInit`,
    `GetHuffBitLengthsAndCodes`, the write helpers and `EncodeStreamHook`.
13. **`VP8LEncodeImage`** takes `&mut WebPPicture`, because C records the error
    and writes `stats` and `extra_info` through its `const` pointer. A missing
    writer panics where C calls `NULL` (excluded input 2).
14. **Integer conversions kept.** The `int` reads of pixels (`AddSingleSubGreen`
    shifts arithmetically, as Clang and GCC do), the `uint32_t` progress sums of
    the second pass of `VP8LHashChainFill` and of `GetBestPredictorsAndSubSampling`
    (which wrap), the `uint64_t` products converted to the `int64_t` arguments
    of `DivRound` in `BitsEntropyRefine` and `PredictionCostBias`, and the
    truncations to `uint8_t` and `uint16_t` are explicit casts or wrapping
    operations. `ShannonEntropy_C` reads each count into an `int` and back, which
    keeps the bits, so the count is used unconverted.
15. **Predictor signatures.** The encoder form of the batch predictors,
    `PredictorSubFunc`, is `(data, in, upper, num_pixels, out)`: the input row and
    the row above are positions in one buffer (the scratch rows), and the
    residuals go to a separate slice (WP3 deviation 15). C passes `NULL` as the
    row above to modes 0 and 1, which do not read it; position 0 stands for it.
    The C `assert(upper != NULL)` has no counterpart.
16. **`NearLossless`** takes `None` as its source where C passes the destination
    as the source too, and skips the copies of a row onto itself.
17. **`use_delta_palette`.** v1.6.0 declares the field "reserved" in
    `encode.h` and reads it nowhere, so the Rust encoder does not read it either;
    the probe shows identical bytes for both values. `WebPConfigInit` does not
    write it (WP9 deviation 14).
18. **Lint expectations.** Item-level `#[expect]`s name the C construct (ADR 0005):
    the C enumerator names (`non_upper_case_globals`), C-style signatures
    (`too_many_arguments`), functions translated whole (`too_many_lines`), C
    names (`similar_names`, `many_single_char_names`), the C condition forms
    (`if_not_else`, `comparison_chain`, `bool_to_int_with_if`), the `float`
    comparison `config->quality == 100` (`float_cmp`), pointer parameters of
    small structs (`trivially_copy_pass_by_ref`), the four C flags of
    `VP8LEncoder` (`struct_excessive_bools`), the C index loop of
    `HistogramRemap` (`needless_range_loop`) and the truncating, wrapping and
    sign-changing conversions of C.

## Upstream behavior preserved

- `VP8LResidualImage` returns 0 without recording an error when its modes
  cannot be allocated, and `EncodeStreamHook` then returns success because it
  tests only `picture->error_code`; `VP8LEncodeImage` goes on to write the
  partial stream. The Rust code keeps this (not reachable in the tests).
- The side picture's error code reaches the picture only when the main context
  succeeded, as C's `if (picture->error_code == VP8_ENC_OK)` decides.

## Mutation checks

Sixteen mutations were tried, each in a copy of the tree, against the test that
covers the unit. Thirteen are caught:

- the streak threshold of `GetEntropyUnrefinedHelper` (`streak > 3` to `>= 3`);
- the mix of `BitsEntropyRefine` (627 to 628);
- the second band of `VP8LDistanceToPlaneCode` (`yoffset < 7` to `< 8`);
- the trimming threshold of `StoreFullHuffmanCode` (12 to 11 trailing bits);
- the cache cost factor of `AddSingleLiteralWithCostModel` (68 to 67);
- the bankers' rounding of `FindClosestDiscretized` (the odd-bit term dropped);
- the left extension of `VP8LHashChainFill` (one length step shorter);
- the top-right update of `GetResidual` (`upper_row[width]` not written);
- the configurations given to the side thread (the first half instead of the
  second);
- the seed of `HistogramCombineStochastic` (1 to 2);
- the interval limit of the cost manager (500 to 5);
- the spatial predictor bias (15 to 14);
- the header size statistic (`data_size` stored as `lossless_hdr_size`).

One is equivalent: the tie bias of `NearLosslessComponent` (`<` to `<=`), because
equality means a zero residual, where both forms choose the lower value. Two
survive, because no generated picture reaches them: the zero-entry trimming of
`EncodePalette` (`palette_size > 17` to `> 16`) needs a 17-color palette whose
modified Zeng order ends in 0 and wins the brute-force search (eight 17-color
pictures with the color 0 are encoded, without that outcome), and the palette
cost of `AnalyzeEntropy` (8 to 9 bits per entry) changes the chosen mode only when
another mode's entropy is within `palette_size` bits.

Before these, the tests found one real defect of the first translation, the
histogram set described under evidence.

## Notes for the packages that build on WP11

- **WP10 (`alpha_enc.c`).** `EncodeLossless` calls
  `vp8l_encode_stream(config, &mut picture, &mut bw)` with a `WebPPicture` that
  holds the alpha values in its ARGB plane (`PlaneStorage::Internal` from
  `webp_picture_alloc`, or caller slices) and a `VP8LBitWriter` from
  `vp8l_bit_writer_init`; it returns `Err` with the code that the picture holds.
  With `thread_level > 0` and several crunch configurations the call spawns a
  scoped thread: the picture's planes must be readable from it (they are, for
  every `PlaneStorage`), and the picture's progress hook stays on the calling
  thread. When WP10's alpha worker runs the alpha encoding on its own thread,
  the scoped thread of `vp8l_encode_stream` nests inside it; nothing else is
  needed.
- **WP13 (`WebPEncode`).** `vp8l_encode_image(config, picture)` writes the
  whole RIFF file through `picture.writer`, which must be set (`WebPPictureInit`
  installs the discarding writer), resets and fills `picture.stats` as C does,
  and clears `picture.extra_info`. It needs an ARGB plane (`picture.argb`);
  without one it records `VP8_ENC_ERROR_NULL_PARAMETER`. It does not write into
  the picture's planes, so a view (`PlaneStorage::Shared`) can be encoded.
- **Both.** The encoder reads the configuration only; `use_delta_palette` has
  no effect. The `C_SIZE` constants of `VP8LHistogram`, `PixOrCopy` and
  `PixOrCopyBlock` are the 64-bit C sizes.
